## 2. 席位 A — 算法与实验

**为什么给他**：这是全项目最重、最需要连续投入的技术块，且与课程"算法"角色直接对应。

### A-1 特征工程：6 维 → 完整 Kamei 14 维

现有 [backend/jit_baseline/config.py](backend/jit_baseline/config.py) 用的是 Kamei14 的 **6 个子集**：
`ns, nd, nf, ent, la, ld`。完整 Kamei14 见 [产品设计文档 §5.1.2](产品设计文档.md) 与 [openapi 的 `Kamei14Features`](api/openapi.yaml)，
为 `ns, nd, nf, entropy, la, ld, lt, fix, ndev, age, nuc, exp, rexp, sexp`；**要补齐的 8 项**是：

| 维度 | 含义 | 数据来源 | 状态 |
|---|---|---|---|
| `fix` | 该变更是否修复缺陷 | 发布者原生列 `fixcount`，按发布者规则 `fixcount > 0` 转换 | 可用 |
| `ndev` | 该文件此前被多少开发者改过 | 发布者原生列 `ndev`（History 家族） | 可用 |
| `age` | 距该文件上次修改的时间（实数） | 发布者原生列 `age` | 可用 |
| `nuc` | 该文件此前变更次数 | 发布者原生列 `nuc` | 可用 |
| `exp` | 作者此前变更经验 | 发布者原生列 `aexp`（Author 家族） | 可用 |
| `sexp` | 作者在相关子系统的经验 | 发布者原生列 `asexp` | 可用 |
| `lt` | 变更前所涉文件代码规模 | 固定快照不含该列（Size 家族只有 `la`、`ld`），不能用 `la+ld` 替代 | **不可得** |
| `rexp` | 按历史变更年龄加权的作者经验 | 同名列 `rexp` 是 Reviewer 经验；候选 `arexp` 只给标签、无定义，无法核验 | **不可得** |

数据来源说明：以上均为**发布者固定快照的原生列，逐字段语义已核验**；**不自建 Git 提交历史聚合或路径聚类**（见"已定的方向取舍"）。

`lt` 与 `rexp` 在固定快照中**不可得**，因此**本轮先落地 12 个已核验字段**
（`ns, nd, nf, ent, la, ld, fix, ndev, age, nuc, exp, sexp`）；补齐这两项需要第二个公开数据集或发布者提取实现，另立后续 change。

**关于时间泄漏**：本轮沿用发布者原生列，这些列在发布者数据中已按"截至该提交之前"的口径给出；
不得自行用全量历史重新聚合，也不得引入提交之后的任何信息。缺失值**不得填零**——来源缺少必需字段的行必须显式排除并记录数量与原因
（`fix` 由发布者规则 `fixcount > 0` 定义，是唯一例外）。

**交付**：更新后的 `data.py`（按具名 schema 取列）+ 一份特征来源与语义说明（含三份发布者文件的 SHA-256）+ 缺失准入与按 schema 校验的回归检查。

### A-2 模型：1 个 → 8 个以上，覆盖两类

- **经典机器学习（≥4）**：逻辑回归（已有，作为基线）、Gaussian 朴素贝叶斯、决策树、随机森林、梯度提升树（具体实现按依赖预算选定）
- **深度学习（≥4）**：多层 MLP、表格 ResNet、FT-Transformer（每字段一个 token）、Wide&Deep（线性 + MLP 双塔）——均为表格型。LSTM／GRU／一维 CNN **不在当期方法内**——本数据集是"每提交一行"的表格而非序列，这类方法需要真实 diff／消息／源码序列素材，列为后续数据路线。

> **深度 4 项已落地**（change `add-deep-tabular-methods`）：超参与 epoch 在训练前冻结、**不使用早停**；
> 复现容差按两次独立训练的实测差声明（本轮观测为 0），**不声称逐字节可复现**；运行见 `backend/artifacts/deep/`。

**经典 5 项已落地**（change `generalize-model-registry-and-run-contract` 建立注册表，`add-classic-methods-and-comparison` 补齐到 5 个）：
[backend/jit_baseline/algorithms.py](backend/jit_baseline/algorithms.py) 的具名条目声明类别、冻结超参、所需依赖、复现口径与解释口径；
估计器实现见 [model.py](backend/jit_baseline/model.py) 的 `ESTIMATORS`；运行身份由 (schema, 方法) 共同决定，产物校验按运行声明比对超参。
当前经典方法：逻辑回归、决策树、随机森林、高斯朴素贝叶斯、梯度提升树；并列比较用 `compare-methods`（口径一致才声明可直接排名）。
**新增模型仍必须走 `artifacts.py` 的运行身份与 `manifest.json` 校验——不能绕过产物校验。**

**跨机器交付的运行**（例如 GPU 席位训练的深度方法）：产方＝GPU 席位，在加速设备上训练、以设备中立形态保存，开 `feature/` 分支把**整个产物目录**提交到 [backend/artifacts/external/](backend/artifacts/external/README.md)，在 PR 中说明方法与产方环境；校验方＝算法与实验席位，在无 GPU 机器上用与本机运行**同一个** `verify` 入口校验，并**登记方法条目**——产方只提供方法与冻结超参，避免同一件事在两处各自登记而漂移；审阅方＝任一非作者席位（见本文档协作约定）。两者共用仓库既有流程，**不另造打包或收包协议**，产方环境如实声明、不得为迎合本机而省略依赖。

### A-3 指标：补齐 effort-aware 一族

[backend/jit_baseline/metrics.py](backend/jit_baseline/metrics.py) 已有 ROC-AUC、AP、P/R/F1（effort-unaware）
和 Recall@20%LOC（effort-aware，命名必须完整保留，[PROTOCOL.md](backend/PROTOCOL.md) 明确写了它不是 Popt）。
要补：**Popt**、**IFA（Initial False Alarm）** 等标准 effort-aware 指标，并写明各自定义与"未定义时返回 null + 原因"的既有约定。

### A-4 预测解释

实现缺陷归因：**SHAP** 为主（树模型用 TreeSHAP，深度模型用 DeepSHAP/梯度解释），输出单个提交的
特征贡献排序。解释必须与 `PROTOCOL.md` 的立场一致——**度量不等于解释，历史标签不等于已确认缺陷**。

**节奏**（硬约束：所有功能必须在 Sprint 2 结束前完成，Sprint 3 只做测试）：
第 5-6 周启动 14 维特征（最耗时，先开工）；第 7-9 周完成 8 个模型 + Popt/IFA + SHAP 解释。

## 3. 席位 B — 数据与在线服务

2026-10-14 增量 `register-existing-models-and-predict-json` 已实现后端最小链路：
SQLite 目录及显式迁移、CLI／管理员 HTTP 登记、成员／管理员权限、模型／schema 查询、六字段单条预测及重开。
同一运行的多个产物位置共用身份，正常失败不发布模型；只登记实际交付运行，不从五种方法条目虚构模型。
当前交付可由 C 按 OpenAPI 接管理员与预测页面；CSV、完整数据集管理、训练任务、解释、LAN 与 CI 尚未由本轮完成。
本轮依据新增开发证据冻结并归档；任务 7.4 按组长 2026-10-14 指示默认通过，记录决定来源，不代填非作者签署。冻结证据见 [本轮冻结清单](evidence/register-existing-models-and-predict-json/冻结清单.json)。

**为什么给他**：数据层是 A 和 C 的共同上游，必须早启动；在线预测是产品的对外能力。

### B-1 数据集管理

**已定：不自建 Git 采集解析管线，直接使用开源数据集。**
现在的做法是把 OpenStack 快照硬编码在
[backend/jit_baseline/config.py](backend/jit_baseline/config.py)（`SOURCES` / `COHORT` / `REVISION`）。
B 的工作是把它从"写死一个数据集"升级成"可管理的数据集层"：

- **数据集注册**：来源、版本、校验值、字段定义、纳入规则各自独立成描述文件，新增数据集不改代码
- **保留现有的完整性校验语义**——校验不匹配必须失败、不静默修补，这是已经做对的地方，别退化
- 这是后面 A 做多模型对比、C 做趋势看板的基础：没有数据集抽象，多数据集实验无从谈起
- 顺带接一个第二个开源数据集做跨项目验证（**可选，看时间**）

### B-2 数据持久化

现在数据是文件产物（`backend/data/`、`backend/artifacts/`）。要补**数据库设计与落库**：
表覆盖 数据集 → 提交 → 变更文件 → 特征 → 标签 → 模型 → 预测结果 → 实验运行。
给出 ER 图与建表语句。这也是 Sprint 0 就点名的设计交付物。

### B-3 在线预测服务

现在是 `GET /api/review-batch` 返回**冻结测试批次**（`backend/jit_baseline/api.py`）。
要补真正的**在线预测**：接收一条提交的特征（或提交标识 → 现场提特征）→ 实时返回缺陷概率 + 解释。
**保留现有的产物校验、503/500 语义、只监听 127.0.0.1 的约定**，不要为了"在线"把校验拆掉。

### B-4 工程化

- **CI/CD**：GitHub Actions，在 PR 上执行后端 pytest + 前端 typecheck/test/lint/build
  （现成素材：`frontend/scripts/verify.ps1` 已经把整条验证链写好了，搬到 CI 即可）
- **分支规范**：`feature/`、`fix/`、`docs/`、`chore/`，分支保护规则要求 PR 才能进 main
- **插件化**：把模型与特征做成可注册插件，配合 A 的模型扩展

**节奏**：第 5-6 周先把 **CI/CD 与分支保护**搭起来（过程证据越早攒越好）+ 启动数据集管理；
第 7-9 周完成数据库与在线预测接口。插件化按时间弹性安排，不作为硬目标。

## 4. 席位 C — 前端可视化 + 测试负责人

**为什么这两件事合给一个人**：前端是端到端测试的入口，看板/可视化的验收标准就是浏览器行为，

### C-1 前端新功能

- **缺陷引入趋势看板**（课程原文点名）：按时间/模块聚合缺陷引入率、模型风险分布趋势
- **模型对比视图**：8 个模型的指标对比表 + 图（接 A 的实验产物）
- **解释可视化**：把 A 的 SHAP 结果渲染成单提交的特征贡献条形图
- 维护现有评审工作台（列表 / 详情 / 优先审查清单 / 基线记录）

现有前端结构清晰（[frontend/src/App.tsx](frontend/src/App.tsx)、`domain.ts`、`shortlist.ts`、
`historicalContract.ts`、`useDataset.ts`），新页面沿用同一套数据契约与
「加载/错误/重试」约定（已有 `BaselineRecord.tsx` 可作样板）。

### C-2 测试负责人（这是 40 分那一项）

职责不是"自己写完全部测试"，而是：
1. 产出**测试计划文档**（测试设计是明确的评分点）
2. 搭建测试分层：单元 → 集成 → 系统，明确每层的覆盖目标
3. 组织**至少 1 条核心端到端链路的集成/系统测试**（现有 playwright 链路可扩展）
4. 组织**≥2 项非功能需求测试**（见下）
5. 维护**缺陷/问题记录**：现象、复现条件、优先级、处理状态、关联提交
6. 汇总测试报告

**立即启动**：非功能需求现在 **0 项**，要求 ≥2 项。建议选：
- **易用性/无障碍**——现有工作台已有键盘操作与焦点管理，扩充成可测量的检查即可，成本最低
- **性能**——推理服务响应时间、前端首屏加载，可给出测量方法与实测数字

（可选第三项：可靠性——服务不可用→恢复重试链路已经测过，沉淀成文档即可。）

**节奏**：第 5-6 周产出测试计划 + 启动非功能需求测试（现在 0 项）；
第 7-9 周完成看板、模型对比、解释可视化；第 10-14 周执行全部测试并汇总报告。

## 5. 席位 D — 文档与演示（外国同学，轻任务）

### 设计原则

给他的任务要同时满足四个条件，才叫"轻"且"不可替代"：

1. **不依赖读中文资料**——不需要读 OpenSpec 规格或课程 PDF 才能开工
2. **不需要等别人**——不阻塞、也不被别人阻塞
3. **产物本身就是课程交付物**——不做无用的活
4. **有可核验的个人贡献记录**——课程明确要求"保留可核验的个人贡献记录"，
   所以他的任务必须是**独立 commit / 独立 PR / 署名文档**，不能是"帮忙看看"

### 任务清单

| 任务 | 产出 | 为什么轻 | 对应要求 |
|---|---|---|---|
