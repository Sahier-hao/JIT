# 项目进展汇报 · 大纲 v1

- 场景：面向老师的项目进展汇报（第 8 周，Sprint 2 中期）
- 时长：约 5 分钟，共 9 页
- 原则：一页一个信息；每页文字不超过 3 行；主体是产品真实截图；数字均有出处，不夸大
- 视觉：16:9 白底，沿用产品自身配色——正文近黑 `#0E1524`，强调深绿 `#277452`，风险只用琥珀/红 `#B54708` / `#B42318`；标题与正文用微软雅黑；不加装饰图形、渐变和图标墙

## 页面

### P1 封面（约 15 秒）

- 呈现：项目名「JIT 缺陷预测 · 提交评审」，副标题「项目进展汇报」，课程名「软件开发与测试综合实训」，日期 2026-10-30
- 图片：无，或产品项目页淡色截图铺底
- 口播：一句话说明这是什么——给代码评审员用的本机工具，模型给提交打风险分，帮评审员决定先看哪里

### P2 解决什么问题（约 30 秒）

- 标题：评审 PR 时，先看哪个提交？
- 三行短句：
  - 一个 PR 几十上百个提交，排序靠经验
  - 工具用已训练的模型给提交打分并排序
  - 分数是模型估计，不是缺陷结论
- 图片：项目列表页（项目卡片 + 顶部「项目 / 我的审查」）
- 口播：强调只做辅助排序，不自动判定 bug

### P3 现在有哪些功能（约 30 秒）

- 呈现：能力全景，五个区块各一行：
  1. 项目工作台：仓库概览、分支分析、分析结果对比
  2. 风险趋势：同一口径聚合的折线与下钻
  3. PR 审查：只读详情 → 个人工作单
  4. 后台自动分析：定时检查开放 PR，站内提醒
  5. 管理工作区：模型、数据集、验证记录
- 图片：右侧放 3 张缩小界面图（概览、PR 详情、工作单），左侧文字结构
- 口播：按用户实际使用顺序过一遍

### P4 项目工作台：概览与分支分析（约 40 秒）

- 图片 1：项目概览——近 52 周提交曲线、语言环形图、最近提交
- 图片 2：分析结果——提交分数列表；叠一张单条提交的模型解释弹窗
- 文字：分析可取消、重试、与历史结果对比；结果保存模型身份
- 口播：分支分析是 PR 审查的同一套模型底座

### P5 风险趋势（约 30 秒）

- 图片：两张单轴折线（平均模型风险分、高分占比）+ 等价数据表
- 文字：只读项目自身成功分析；同口径去重；无评分的时间段断开，不画零
- 口播：趋势用于复盘，不做 PR 合并决定

### P6 PR 审查（约 50 秒，核心场景）

- 图片 1：PR 只读详情——模型风险概览、高风险提交、按最高分排序的文件
- 图片 2：工作单——左侧提交队列、模型线索、问题与证据、Markdown 结论
- 文字：先看只读详情，「开始审查」才创建个人工作单；后台发现不自动改写草稿
- 口播：完整走一遍「从 PR 到意见」

### P7 后台自动分析与提醒（约 25 秒）

- 图片：项目 PR 页的「自动分析」对话框，或站内提醒页
- 文字：固定 base/head 快照与模型；失败按 1/5/15 分钟重试；提醒只写公开事实
- 口播：说明无人值守部分的能力边界

### P8 模型与实验（约 50 秒）

- 图片 1：管理区模型页截图——9 个已登记模型
- 图片 2：9 种方法的真实指标点图（ROC-AUC / AP）
- 关键数字：OpenStack 测试集 1,853 条（正例 286）；9 种方法 ROC-AUC 0.7375–0.7710，AP 0.3288–0.3899
- 诚实说明：
  - 排序能力与逻辑回归基线接近，深度方法没有明显更好
  - 阈值 0.5 下多数方法 F1 很低（正例约占 15%），排序类指标更可信
  - 分数未做概率校准，不宣称缺陷率
- 口播：讲我们怎么如实评价，不只报最好看的数

### P9 下一步（约 30 秒）

- 三条：
  - 本周：项目图表升级（ECharts、52 周活跃度、语言环形图）
  - 11 月 15 日前：功能封版，进入 Sprint 3
  - 之后：系统测试、≥2 项非功能需求验证、缺陷处置记录；12 月结题
- 收尾：谢谢，请老师提问
