# 训练模型包部署与恢复

原始模型运行目录和 `backend/storage/catalog.sqlite3` 是本机运行数据，均被 Git 忽略。经维护者选择并通过完整性校验的压缩模型发布包位于 `backend/model-packages/`，随普通 Git 仓库交付；部署环境不复制整份 SQLite 目录库。目录库迁移、备份与回退见[运维与升级](运维与升级.md)。

当前交付有两个明确不同的包：

- `jit-nine-models-v1.zip`：既有六字段兼容模型，保留用于旧 schema 数据。
- `jit-current-v2-models-v1.zip`：当前 `kamei14-git-v2` 四项目正式基线，只收录通过 `jit-release-v1` 的模型。

新环境先尝试导入当前 v2 包，再导入六字段兼容包。当前 v2 包在空目录中按人工批准记录设置默认候选；已有目录不会覆盖原默认、启用或停用策略。两个包都不能把训练成功直接解释为发布合格。

## 边界

- 模型包只包含明确选择的已登记运行，以及每个运行的模型文件、`manifest.json`、摘要、数据集版本、schema、依赖声明、运行身份和逐文件哈希。
- 导出不包含 SQLite、项目、管理员账户、会话、源环境默认模型、启停策略或“最佳模型”标记。
- 导入会逐项重新校验文件、运行身份、完整产物和模型能否加载；有效项独立登记，冲突、损坏或依赖缺失项逐项失败。
- 版本化 ZIP 与 `.sha256` 一起进入 Git；解包运行目录、SQLite 和运行期证据不进入 Git。已发布的包不得原地替换，模型或清单变化时使用新版本。
- 普通用户只能看到已登记、启用、产物可用且 schema 兼容的模型。完整产物或训练报告不会自动成为可用模型。
- 模型卡的分区诊断和收益报告是独立只读证据，不写入模型 ZIP；报告必须按 `artifactRunId`、模型 SHA-256 和数据版本匹配。模型包升级后在目标环境重新核对报告身份，不能沿用旧模型的收益结论。
- 当前 v2 包必须至少包含 4 个经典和 3 个深度方法，共不少于 8 个模型；每个模型必须带匹配的 `release-report.json`，全部报告均为发布合格，并恰好有一个 `release-approval.json` 人工默认候选。
- 包清单记录数据版本、manifest/CSV 哈希、完整切分摘要、标签成熟规则、方法、依赖、指标、基线差值、失败门槛、服务兼容性和发布报告身份。任一模型、数据、切分或策略与报告不一致时，整次当前 v2 包预检失败，不先登记部分模型。

## 生成模型包

在训练环境的 `backend` 目录选择目录中已登记、确认要交付的模型 ID。管理员模型详情可核对 ID、运行身份和指标。

```powershell
./.venv/Scripts/python.exe -m jit_baseline.cli export-models `
  <MODEL_ID_1> <MODEL_ID_2> <MODEL_ID_3> `
  --database storage/catalog.sqlite3 `
  --artifact-root artifacts `
  --output ../release/jit-models.zip
```

命令输出 `packageSha256`、模型数、文件数、解压大小和包大小，并生成 `jit-models.zip.sha256`。输出已存在时拒绝覆盖；校验或写校验文件失败时不留下可误认为完整的包。

只导出标准服务模型，不把复现副本、离线基准、语义向量输入模型或聚合报告自动加入。若所选模型当前不可加载，导出失败。

### 当前 v2 正式基线

先在四项目真实运行中完成九方法训练和逐项目发布判定。覆盖数和人工默认候选满足后，用最终确认命令重新评估发布报告并生成版本化包：

```powershell
./.venv/Scripts/python.exe -m jit_baseline.cli finalize-current-schema-baseline `
  --output artifacts/current-v2-release `
  --artifact-root artifacts `
  --database artifacts/current-v2-release.sqlite3 `
  --dataset-root data/datasets `
  --approve-default-method <人工批准的方法> `
  --approved-by <批准人>
```

命令会按冻结项目和当前规则重算每个模型的发布报告，原子替换同一证据下的旧报告，再生成 `jit-current-v2-models-v1.zip` 和 `.sha256`。确认包内模型与报告后，把二者复制到 `backend/model-packages/`。默认候选不能按测试指标自动选择；当前建议仅用于人工核对，不是系统自动结论。

## 发布和传输前核对

```powershell
$expected = (Get-Content .\jit-models.zip.sha256).Split()[0].ToLower()
$actual = (Get-FileHash .\jit-models.zip -Algorithm SHA256).Hash.ToLower()
if ($actual -ne $expected) { throw '模型包 SHA-256 不匹配' }
```

将 ZIP 和 `.sha256` 提交到 `backend/model-packages/` 的同一版本。压缩包会进入 Git 历史，因此发布前必须检查敏感信息、许可、来源、大小和模型加载结果；不要提交 SQLite、解包运行目录或运行期证据。

## 新环境或升级环境导入

1. 停止旧后端，避免导入与登记读写交叉。
2. 备份目标环境的 `catalog.sqlite3` 和全部被引用产物目录。
3. 用新代码执行目录库前向迁移。旧库升级会先在同目录生成 `catalog.sqlite3.before-v<旧版本>-<随机>.sqlite3`；备份失败则不升级。
4. 执行标准目录初始化；它会在迁移后自动校验并导入仓库内置模型包，并输出逐项结果。
5. 启动单个后端，核对管理页和用户模型选择。

```powershell
cd backend
./.venv/Scripts/python.exe -m jit_baseline.cli catalog-init
./.venv/Scripts/python.exe -m jit_baseline.cli serve --port 8000
```

`catalog-init` 输出 `currentSchemaPackage` 与 `bundledPackage`，包含包名、SHA-256、`completed`、`partial`、`skipped` 或 `failed` 状态，以及新建、复用、已登记、冲突和失败计数。当前 v2 包先完成 SHA、结构、schema、方法覆盖、发布报告和默认批准一致性预检，再开始登记。相同 SHA 已成功应用且预期模型都 ready 时跳过重复导入。已有目标策略不被源包覆盖；只有空目录才采用当前 v2 包中的人工批准候选作为默认。六字段兼容包随后导入时也不覆盖已有默认。

只初始化隔离目录库、不需要内置模型时可显式跳过两个包：

```powershell
./.venv/Scripts/python.exe -m jit_baseline.cli catalog-init --skip-bundled-models --skip-current-schema-models
```

自定义或测试包必须同时提供同名 `.sha256`，可用 `--bundled-package <path> --artifact-root <path>` 指向隔离位置。普通部署不应覆盖默认内置包路径。

依赖缺失时不会登记该模型。先在目标环境安装同一运行声明的 Python/包版本，再重新导入；不要修改包内清单或把失败模型手工写进目录库。

## 部署后核对

```powershell
$models = Invoke-RestMethod http://127.0.0.1:8000/api/v1/models
$release = Invoke-RestMethod http://127.0.0.1:8000/api/v1/models/<MODEL_ID>/release
$coverage = Invoke-RestMethod http://127.0.0.1:8000/api/v1/models/coverage
$choices = Invoke-RestMethod http://127.0.0.1:8000/api/v1/repository-models
```

管理页应显示已登记数、`ready` 数、用户可选数、最近导入结果和逐项失败原因；训练覆盖矩阵应区分无产物、训练失败、完整未登记、已登记可用和不可服务。用户选择只包含 `repositoryPredictionSupported=true` 的真实模型。后端不可达时页面显示连接错误，不解释为“没有训练模型”。

模型 ID、`artifactRunId`、数据集版本和 schema 应与发布清单一致。发布响应应区分 `qualified`、`unqualified` 和 `not-evaluated`，并给出最差项目、未通过门槛和基线差值。包中记录的是源模型 ID；导入时保留该 ID 以保持谱系，不复制源默认和启停设置。

发布包之外的当前验证证据：

- `docs/evidence/model-diagnostics/<artifactRunId>.json`：train/validation/test 指标、split 摘要和数据/模型哈希。
- `docs/evidence/model-card-benefits/<artifactKey>/benefit-report.json`：与当前模型包运行身份匹配的收益评估。
- 运行目录中的 `release-report.json`：当前 schema 项目的逐门槛结果、基线差值、最差项目，以及数据、切分、模型和成熟策略身份。

模型卡读取失败、报告缺失或身份不符时显示明确原因，不从历史报告、另一模型或当前在线结果回填。

## 回滚

1. 停止新后端，另行保存导入后的目录库、产物和逐项导入记录。
2. 恢复部署前的 SQLite 目录库和对应产物目录。
3. 切换到与新数据库版本匹配的代码，再启动单个后端。
4. 重做模型选择、默认模型和用户可见性核对。

模型包不可变，可以重新导入，但已部分成功的数据不会因为重新导入而回滚。需要完整恢复到导入前状态时，必须恢复数据库与产物的同一份备份。

## Git 存储边界

当前六字段九模型包约 5.93 MiB。当前 v2 包另含四个项目的冻结测试输入、参考预测和九个方法的发布证据，提交前必须实测包大小、文件数和许可边界。直接使用普通 Git 时仍不提交 SQLite、原始仓库、散装运行目录或截图缓存；若 pack 明显增长、单包接近托管平台文件上限、更新频率显著提高或部署不再以源码克隆为入口，应单独评审改用 GitHub Release、制品库或 Git LFS。
