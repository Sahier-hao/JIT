## \[即时软件缺陷预测系统\]

即时软件缺陷预测（Just\-in\-Time Defect Prediction, JIT） 是软件工程领域的前沿研究方向：与传统“按模块/文件粒度”预测不同，JIT 在每次代码提交的粒度上预测该提交是否会引入缺陷。它能在缺陷真正进入主干前就发出预警，指导代码评审员优先审查高风险提交，将质量保障左移。

本次实训要求以团队为单位，开发一个完整可用的 JIT 缺陷预测系统：从真实开源仓库（如 GitHub 上的 ActiveMQ、Lucene、Hadoop 等知名 Java 项目）挖掘历史数据，训练机器学习模型，并对外提供在线预测服务与可视化前端。

系统主要功能模块：数据采集与仓库解析（Git 仓库克隆与解析、缺陷提识别、SZZ 算法实现、数据持久化）、特征工程与样本构建模块（实现经典的 Kamei 14 维代码变更度量元，以及代码语义特征提取（可选））、模型训练与评估模块（至少2类（经典机器学习和深度学习）不少于8种预测模型、评估指标（Effort\-unware和effort\-aware两类）、训练集和测试集划分）、预测与解释模块（缺陷概率、缺陷归因/解释）、可视化前端（风险列表、缺陷引入趋势看板等）、工程化（Git 分支规范 \+ 代码评审；CI /CD流水线、插件化等）。

PS：Yasutaka Kamei, Emad Shihab, Bram Adams, Ahmed E\. Hassan, et\.al, A Large\-Scale Empirical Study of Just\-in\-Time Quality Assurance, IEEE Transactions on Software Engineering, 39\(6\): 757–773, 2013\.



✨可选附加功能：

（1）缺陷的可视化定位——按缺陷概率用不同颜色高亮可疑代码行；

（2）针对缺陷给出高质量修复建议；

（3）要保证系统能加载保存现有公开的软件缺陷数据集，但现有即时软件缺陷数据集存在几个突出问题：比如1）标签粒度太粗，往往只包含有无缺陷，并没有缺陷类型信息；2）主要针对Java项目，其他编程语言的开源项目较少；3）数据质量问题（数据不完整、不准确、不一致等，可参照高质量数据集评价与构建方法应对）；（2026/10/12）

（4）早期的即时软件缺陷预测方法是基于专家特征（即经典的 Kamei 14 维代码变更度量元）的，但现在主流方法是利用预训练模型直接从源代码提取深层语义特征，然后构建预测模型；（2026/10/12）



## 基本要求

- 自由组队，每组**3\~4**人（落下的同学无法组队时，会随机分配给人数最少的组）。全体成员对产品质量共同负责，同时须保留可核验的个人贡献记录

- 选题须面向明确用户和真实使用场景，解决一个具体问题，不得简单复刻已有产品或只实现教程式 CRUD

- 产品形态不限（Web、移动端应用等），但须包含可供目标用户使用的界面或交互入口，以及可维护的业务/数据处理层

- 使用**Scrum敏捷开发框架**，每个Sprint都必须交付一个可演示、可运行的产品增量

- 项目须有清晰的MVP（Minimum Viable Product，最小可行产品）和可选附加功能。产品应包含**至少20个彼此关联的核心用户故事**（User Story，即功能模块下的具体功能点），能够形成完整业务闭环（项目范围过大、无法在各Sprint验收，或无实际用户价值的项目会被要求缩减或调整）

- 需求应说明功能需求和非功能需求。非功能需求至少选择并落实**2项**与项目相关的质量需求，例如安全、性能、可靠性、易用性等

## 项目协作规则

- 使用**GitHub/Gitee**协作，提交历史、分支、Issue、看板和OpenSpec文件均为过程考核证据

- 在当前AI Coding环境下，本次实训要求每组开发使用**OpenSpec框架**实践**规范驱动开发（**Specification\-Driven Development，SDD**）**。每组须在项目启动期初始化OpenSpec，并将生成的 openspec/ 及相关AI工作流文件\(proposal\-\>specs\-\>design\-\>tasks\.md等\)一并提交版本控制

- 使用**飞书多维表格/华为云CodeArts/禅道（ZenTao）**进行项目管理，看板中任务应能对应到Sprint和OpenSpec的change/task

- 项目需使用**缺陷管理**工具（项目管理工具通常支持缺陷管理）

- 使用Pull Request协作，合并前应至少有一位非作者成员**审阅**；审阅意见及修改记录保留在Git平台中

- 每组**每周五**课上需进行一次简短进展汇报，并产出工作周报，写明已完成工作、下一步和存在问题

- 每组可在**每周三**前与任课教师约一次课外项目讨论（限时30分钟）

### **Sprint 0（第1\-3周）**

- 至少需要说明Epics/Key Features，即大型用户需求或核心功能，应形成如下层级：

```Plaintext
Epic（业务目标）：在线购物平台
    ├── Feature（功能模块）：用户管理
    │      ├── User Story（用户需求）：用户注册
    │      ├── User Story：用户登录
    ├── Feature：订单管理
           ├── User Story：下单
           ├── User Story：支付
```

- 每个用户故事应确定其优先级、验收标准；每个核心能力至少写出正常场景，以及必要的异常/边界场景。拆分后的用户故事、接口定义、数据约束等可嵌入OpenSpec规格中

- 技术架构应服务于实际产品，建议采用三层架构/微服务架构。应说明主要组件、外部依赖等，并进行数据库设计，确定表结构

### **Sprint 1（第4\-6周）**

- 项目应具备合理的仓库结构

- 需求变更必须通过**同步**新增或修改管理工具及OpenSpec change记录，不得只改代码而不更新规格

- （可选）基于微服务的容器化部署，网页端使用公网链接访问

- （可选）配置自动化流水线CI/CD，在提交或PR时执行构建和自动化测试

### **Sprint 2\-3（第7\-9, 10\-14周）**

> 持续进行项目开发

**开发要求：**

- 更新Backlog（需求待办列表）中上一个Sprint中尚未完成的User Stories、新出现的需求或变更

- 之前已经估算过的Story优先级/工作量，可以根据你们从前面Sprint中获得的经验进行**重新估算**

**测试要求：**

- 对核心业务逻辑进行测试，覆盖正常、边界和异常输入

- 至少覆盖1条核心端到端业务链路的集成或系统测试

- 对每个核心功能给出正向验收和至少一个异常/无效输入验证

- 对已选的每项非功能需求给出适当证据，例如性能测量、安全检查、可用性/无障碍测试、可靠性测试或隐私审查

- 缺陷使用Issue或等价记录管理，至少记录现象、复现条件、优先级、处理状态和关联提交/change

- OpenSpec change中的任务完成**不等于**功能合格，必须有实际运行或验收测试等证据支撑

## 项目展示 Demo Day

> 一点小建议：

- 请用简洁的文字传达有信息量的内容

- 展示中请善用图表、截图等视觉元素

每组**12分钟**展示（10分钟产品展示 \+ 2分钟问答），展示应覆盖以下内容：

1. 用户问题、目标用户、产品价值

2. 关键架构/技术决策设计

3. 完整核心用户场景展示

4. OpenSpec中一个代表性change如何从规格、任务走到实现、测试和归档

5. 测试工作概述与结论

6. 项目总结，包括但不限于：关键数据、已知问题、开发过程中的亮点操作、经验教训等
