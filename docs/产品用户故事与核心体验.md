# 面向真实使用的产品用户故事与核心体验

日期：2026-10-26；首版实现更新：2026-10-27。状态：公开 GitHub、个人使用的双轮审查路径已实现并完成自动化及浏览器验证；尚未开展真实用户访谈。示例人物、PR 编号和时间用于描述场景，不是实际使用记录。

现状以[当前产品](当前产品.md)、[使用指南](PR审查使用指南.md)、[验收记录](审计/2026-10-27-pr-review-journey.md)和代码为准；本稿补充[产品需求文档](产品需求文档.md)中的用户目标与完整流程。下文的故事编号采用独立的 `UX-` 前缀，不替换原需求编号，也不把目标标成已有能力。

## 1. 产品要帮用户完成什么

让评审者完成一次有上下文、有过程记录、有明确交付物、能够继续跟进的代码审查。

用户进入系统，应能回答四个问题：

1. 今天有哪些变更需要我处理？
2. 打开一项工作后，我应该从哪里开始看？
3. 作者更新代码后，哪些地方需要重新核对？
4. 我完成了哪些审查，还需要向作者交代什么？

首版围绕一个真实 PR 形成完整工作过程。提交风险、解释、分析对比和模型能力在这个过程中提供辅助信息。

### 首版用户假设

主要用户是负责 GitHub 仓库代码评审的开发者或维护者。他可能同时处理几个 PR，常因其他工作中断，之后需要重新找回上下文。

第一条完整交付路径支持公开 GitHub 仓库、个人使用：作者仍在 GitHub 提交修改，评审者在本系统组织和完成审查。个人草稿按设备保存，并可备份；身份、存储位置和同步状态清楚可见。

私有仓库、跨设备个人账户、多人共享审查和直接向 GitHub 发送意见属于后续扩展。这些能力需要独立的授权、数据隔离与同步设计，不能由管理员登录或匿名共享接口替代。

### 工作对象

- **PR**：一次准备合并的改动，是用户接手和交付的工作单位。
- **代码版本**：这次 PR 的基准版本和作者最新提交；新增提交后，原审查结论仍属于原版本。
- **审查工作单**：一个人针对一个 PR 的阅读进度、疑问、发现、备注和最终结论。
- **审查问题**：本轮需要回答的具体问题，可以关联多个文件、代码位置与测试。问题的来源、当前证据和人工判断分别可见。
- **分析结果**：模型对某一版本的计算快照，提供辅助线索；人工审查结论单独记录。

### 优先设计的差异化体验

工作单以需要回答的审查问题组织阅读。例如「密码重置 token 过期后会发生什么？」可以同时关联接口处理、token 校验和对应测试，用户沿这条线索核对完整行为。

问题可以来自作者说明、真实改动分析或用户手动建立。系统提出的问题标明依据与尚缺的证据；用户可以修改、忽略或反驳。提交级模型负责提供辅助优先级，额外代码分析的来源单独说明。

作者更新后，工作单继续追踪同一问题：哪些相关代码变了、旧证据是否过期、是否仍缺少验证。最终交付包含每个重要问题的人工判断、证据与剩余事项。

以上价值仍是需要用真实任务验证的产品假设。若用户使用后仍需要重复整理同样的上下文，应调整问题组织方式和阅读路线。

## 2. 当前体验与目标体验

| 用户任务 | 当前实现 | 目标体验 |
| --- | --- | --- |
| 开始一天的工作 | 我的审查按关注、继续、待复核、等待作者及历史组织工作 | 打开我的审查，看到新工作、未完成草稿和需要复核的更新 |
| 接手一项任务 | 从公开仓库选择真实 PR，或直接接入 PR 工作单 | 接手一个真实 PR，形成一张持续使用的审查工作单 |
| 了解改动 | 固定版本的作者说明、文件 Diff、上下文与可编辑问题 | 在工作单里串起作者说明、文件变化、真实代码和审查线索 |
| 记录工作 | 浏览器按 PR 与版本保存进度、问题、证据、人工判断和未完成文本 | 保存读到哪里、有哪些问题、哪些文件已经核对、有哪些待确认项 |
| 作者提交修改 | 进入独立轮次，标记变化文件与过期证据，保留旧判断和阅读出处 | 工作单说明本次新增改动、旧问题所在代码是否变化及待复核范围 |
| 完成审查 | 预览确认后保存本轮意见，可复制或下载 Markdown | 产出能发给作者的审查意见，明确覆盖版本、已检查内容和剩余问题 |
| 模型暂时不可用 | 独立线索区域显示错误，代码阅读和人工记录继续可用 | 代码阅读和人工记录继续可用，模型区域明确显示当前不可用 |

## 3. 一个评审者的一天

以下为虚构流程示例。

**上午打开系统。** 我的审查里出现 PR #42「支持密码重置」的新提交，标明「作者已更新，需要复核」。另一个 PR 保留「审查到一半」的草稿。用户直接选择今天要继续的工作。

**打开 PR #42。** 工作单说明这次改动的目标、涉及文件和上次留下的两个问题。用户上次核对过的文件中，只有一个被作者改动；该文件显示需要复核，其余文件显示沿用上个版本的阅读记录。

工作单把「token 过期后如何处理」列为一个待回答问题，并关联接口分支、校验函数和测试文件。用户从问题进入相关代码，在同一处记录判断与证据。

**核对具体代码。** 用户看到 token 过期分支的修改，打开相应 Diff 和上下文，记录一个疑问，并把另一个问题人工标记为已经解决。每条记录都能回到当时的代码位置。

**中途离开。** 系统保存阅读位置和草稿。下午回来时，用户可以继续，而无需重新回忆哪些地方已经看过。

**结束本轮审查。** 用户选择「建议修改」，生成一份包含两个待处理问题、已审查范围和未覆盖内容的 Markdown 意见。首版可复制到 GitHub；页面说明意见仍未由本系统发送。

**作者再次修改。** 系统将该工作单放回需要复核的队列。旧结论保留，用户能核对作者这次是否处理了问题，再完成新一轮审查。

## 4. 首版用户故事与验收标准

### UX-01 接入项目后，马上找到可以处理的工作

作为仓库评审者，我希望输入仓库或 PR 地址后，能选中一项真实改动开始审查，以便在第一次使用时就完成实际任务。

**触发与完成结果：** 首次进入系统，最终打开一张属于真实 PR 的审查工作单。

**验收：**

- 输入公开仓库地址时，展示真实 PR 的标题、作者、更新时间和外部状态；可选择 PR 开始审查。
- 输入具体 PR 地址时，直接定位该 PR，并清楚显示所属项目。
- 仓库没有打开的 PR 时，说明空态，并允许选择明确的历史 PR 开始复盘；历史复盘清楚标明远端状态，不冒充待合并工作。任意提交范围的工作单属于后续扩展。
- 读取或分析期间展示实际状态；用户无需准备特征文件、理解模型编号或先进入维护工作区。
- 无法访问、来源不支持或请求受限时保留输入并提供重试；准备失败不能伪装成「没有待办」。
- 首次打开显示实际覆盖的代码版本和数据更新时间。

### UX-02 每天打开系统，知道有哪些事还没处理

作为同时处理多个 PR 的评审者，我希望看到关注工作的新变化和未完成事项，以便安排今天的审查。

**触发与完成结果：** 再次进入系统，能够选择一个明确的下一步动作。

**验收：**

- 首页按「新关注的工作」「继续审查」「作者更新待复核」「等待作者处理」组织个人工作。
- 每项显示项目、PR 标题、作者、本人的工作状态、最近变化和一个主操作。
- 用户可以主动关注、暂停或结束一项工作；个人关注不冒充 GitHub 的正式评审人分配。
- 检查更新后仅改变实际发生变化的任务，显示检查时间；检查失败不能显示为所有任务都没有更新。
- 从工作单返回首页时，状态和进度保持一致；重复检查不产生重复任务。
- 远端 PR 被关闭或合并后，展示真实状态，默认移出活跃待办，保留草稿和意见；用户可主动继续历史审查，个人结论不被自动改写。

### UX-03 接手 PR 时，看懂这次要审什么

作为评审者，我希望先了解改动目的、范围和需要核对的线索，以便有顺序地阅读代码。

**触发与完成结果：** 打开工作单后，能够进入一个具体文件或问题位置，而非停留在分数列表。

**验收：**

- 作者原始说明、真实文件变化、涉及提交和基准／目标版本可以对应核对；生成的摘要与作者原话分开标识。
- 支持按文件阅读真实 Diff 和必要上下文，明确新增、删除、重命名、二进制文件及无法展示的内容。
- 工作单提供可编辑的审查问题，每个问题可关联多个相关文件或测试，并标明来自作者说明、改动分析还是人工提出；缺少证据时明确待核对。
- 对过大的改动明确显示已加载和未覆盖的范围，并允许按文件继续读取。
- 模型线索提供依据和来源，不把提交级分数转换成未经验证的 PR 整体缺陷概率。
- 代码行级疑点若来自额外代码分析，应标明来源和待验证性质，不借提交级特征归因冒充行级定位。
- 模型区域失败时，代码阅读与人工审查仍可进行；代码读取失败时，不能把相应文件计为已审查。

### UX-04 阅读时留下能继续处理的疑问和发现

作为评审者，我希望在文件或代码位置记录问题、疑问和建议，以便交给作者或稍后继续核对。

**触发与完成结果：** 阅读过程中形成带出处的审查记录。

**验收：**

- 记录包含类型、内容、所属文件、代码位置及所依据版本；不绑定行号的总体意见也能保存。
- 一项审查问题可以串起多个位置的证据，用户可以记录已核对内容、仍需作者说明之处和自己的判断。
- 区分「待确认的问题」「人工确认的问题」和「一般建议」，模型线索不会自动成为人工确认项。
- 能编辑、撤回和重新打开记录；解决或暂不处理的问题保留理由与原内容。
- 写入失败时保留正在编辑的文本，明确提示尚未保存，用户可重试或导出草稿。
- 从意见列表点击一项，可以回到对应版本的代码；位置过期时提示原因并保留原位置。

### UX-05 被打断后，回来接着审

作为经常被其他任务打断的评审者，我希望离开后恢复自己的阅读位置和判断，以便继续完成这项工作。

**触发与完成结果：** 关闭页面或切换项目后再次打开，能够继续此前任务。

**验收：**

- 恢复上次阅读的文件、已核对文件、未完成文本和未解决记录，并展示这份草稿基于哪个版本。
- 可以标记文件已阅读、需要复查或暂未覆盖，统计口径清楚；已阅读不等于已确认没有缺陷。
- 不同项目、PR、代码版本和个人工作单不会混用记录。
- 首版明确提示草稿保存在当前浏览器，支持备份恢复；旧备份缺少的备注不会导致当前记录被清空。
- 恢复出现冲突时展示差异并让用户选择，不静默覆盖较新的判断。

### UX-06 作者更新后，只处理这轮需要重新核对的内容

作为评审者，我希望知道作者的新提交影响了哪些已审查内容和未解决问题，以便有依据地开展下一轮审查。

**触发与完成结果：** 检查到 PR 新版本，形成新的待复核范围，并保留旧记录。

**验收：**

- 对比明确的旧版本与新版本，展示新增改动和需要复核的文件；检查失败时保留旧版本及时间说明。
- 已改变的文件标为需要复核，未改变的内容可显示沿用上轮阅读记录，并保留其出处。
- 旧意见不会因代码被删除、移动或新增提交而自动变成已解决；用户核对后再改变结论。
- 对每项未解决的审查问题展示相关代码变化及过期证据，保留问题本身和原判断，帮助用户继续核对同一件事。
- 新版本的分析、模型和线索单独保存，旧判断不被新分数重写。
- 作者强制推送、目标分支变化或旧版本不可再取回时，明确说明影响，不把另一版本的代码塞入旧意见。
- 首页的待复核状态与工作单一致；重复检查同一版本不反复重置进度。

### UX-07 结束一轮审查，交付别人看得懂的结论

作为评审者，我希望输出完整审查意见，以便让作者知道需要处理什么，也让自己对本轮工作有明确交代。

**触发与完成结果：** 主动结束当前轮次，得到可复制或下载的审查交付物。

**验收：**

- 支持「建议修改」「本轮审查完成」「暂缓并说明原因」，结论由用户确认。
- 意见包含 PR 与版本、已审查范围、尚未覆盖内容、人工发现、待确认项和建议动作，并可追溯代码位置。
- 系统提示未完成事项，用户选择继续审查或在结论中明确保留；不能把未读取的文件计为已覆盖。
- 确认期间若发现新代码版本，明确结论属于旧版本，并提示先复核或带版本说明交付。
- 首版输出 Markdown／复制文本，并明确尚未发送到 GitHub；用户的个人完成状态不等于远端 PR 已批准或已合并。
- 后续接入发送功能时，须由用户明确操作，并区分正在发送、失败和经远端核对已发送，支持安全重试。

### UX-08 发现系统建议不准时，仍能完成工作

作为评审者，我希望纠正无用的提醒，并保留自己实际发现的问题，以便继续信任自己的审查过程。

**触发与完成结果：** 用户能够给建议作出反馈，人工发现完整保留。

**验收：**

- 可以把线索标为有帮助、无关或需要更多证据，并附原因；保留所针对的代码和建议版本。
- 低分提交也可以记录人工问题，高分提交也可以记录经过核对暂未发现问题，原模型分数保持不变。
- 人工记录与模型输出分开查询，反馈不自动变成训练标签或改变当前默认模型。
- 首版反馈随个人工作单保存在当前浏览器，不自动上传或对管理员公开。用户可主动导出所选案例，预览将包含的字段并选择是否分享；未选择的个人备注不被附带导出。
- 后续直接提交维护案例时，由用户确认发送内容并核对接收状态；管理员审核后才能用于数据或模型维护，普通评审操作不获得维护权限。

## 5. 页面应该围绕工作组织

主入口建议采用三个层级：

| 层级 | 用户第一眼看到什么 | 主要动作 |
| --- | --- | --- |
| 我的审查 | 关注工作、未完成草稿、作者更新待复核 | 开始、继续、复核 |
| 项目 | 真实 PR、项目近期活动、连接状态 | 选择工作、检查更新、管理关注 |
| 审查工作单 | PR 目标与版本、文件、代码、本人记录和剩余事项 | 阅读、记录、复核、交付结论 |

模型管理、数据记录及验证报告继续位于管理员工作区。普通工作单的主操作使用「开始审查」「继续审查」「核对更新」「输出意见」等用户动作，技术身份在来源中可展开核对。

工作单的信息布局示意：

```text
PR 标题、作者、改动目标、当前代码版本、本人状态
本轮还需处理：未阅读文件 / 待复核文件 / 未解决问题
---------------------------------------------------
文件与阅读进度 | 真实 Diff 与上下文 | 意见、疑问与建议
---------------------------------------------------
保存状态                 继续审查 / 输出本轮审查意见
```

| 管理员工作区 | 提供可用模型、数据和验证能力，保持服务端维护权限 |

## 7. 首个可交付版本怎样划分

以「公开 GitHub 仓库中，一个人完成一个真实 PR 的两轮审查」作为第一次产品交付范围，覆盖 UX-01 至 UX-08 的这条纵向路径。

可以分三个 change 实现：

1. **真实工作接入**：公开仓库／PR 读取、关注队列、固定版本、审查工作单与失败恢复，对应 UX-01～03。
2. **审查过程与交付**：文件阅读、意见与草稿、断点续审、备份恢复、结论输出及反馈，对应 UX-04～05、07～08。
3. **更新后的下一轮审查**：检查新提交、待复核范围、旧意见定位和新一轮结论，对应 UX-06，并贯通前两项。

三个 change 属于同一用户交付链路，完成纵向验收后统一为一个 PR，不要求用户自行管理串联 PR。

后续再扩展私有仓库授权、个人账户与跨设备保存、团队分配和共享结论、直接向 GitHub 提交审查。团队扩展的验收必须包括身份、项目隔离、意见所有权和权限恢复，不能仅增加成员列表。

## 8. 用什么证明这次像一个能用的产品

找一位未参与实现的使用者，给他一个实际可访问、带后续更新的 PR，而非模型编号或准备好的特征文件。依次走通：

1. 找到 PR 并开始审查。
2. 理解改动目标，围绕一项具体审查问题打开实现与相关测试，关联证据并记录判断。
3. 中途离开，重新打开后继续工作。
4. 交付一份说明审查范围与未解决问题的意见。
5. 作者新增提交后，继续核对同一问题，识别哪些相关代码和旧证据已经变化，再形成新的判断并完成第二轮。

同时覆盖读取失败、模型不可用、草稿保存失败、旧意见位置过期和重复检查更新。记录实际成功率、卡住位置、理解偏差和用户仍需转去其他工具的步骤；这些数据采集前保持空白，不预设效率提升比例。

## 9. 读者应该能直接回答的问题

- 第一位用户是谁，为什么会每天打开？
- PR、模型分析和个人审查工作单分别是什么？
- 第一次使用需要提供什么，怎样才算完成第一次任务？
- 作者更新以后，哪些东西保留，哪些需要重看？
- 人工判断和模型输出怎样区分？
- 个人意见保存在哪里，别人是否能看见？
- 完成本轮审查究竟输出什么，是否已经发送到 GitHub？
- 哪些能力属于本稿目标，哪些是现有代码已有的？

这些问题用于产品草案的阅读检查，不代表已经开展真实用户验收。
