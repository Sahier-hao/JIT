## 一、测试分层与覆盖目标

| 层 | 现有资产（截至 2026-10-13） | 覆盖目标 | 执行命令（对应目录内） |
|---|---|---|---|
| 单元（后端） | `backend/tests/`：`test_api.py`、`test_artifacts.py`、`test_data.py`、`test_evidence.py`、`test_http_lifecycle.py`、`test_metrics.py`、`test_model.py`、`test_verification_guard.py` | 数据校验、分区、模型、指标、产物/清单、HTTP 生命周期、受保护位置比对的正常/边界/异常输入 | `.venv/Scripts/python.exe -m pytest --basetemp=.cache/verification-tests` |
| 单元（前端） | `frontend/src/`：`App.test.tsx`、`domain.test.ts`、`historical.test.ts`、`shortlist.test.ts`、`useDataset.test.ts` | 域解析与排序、历史契约校验、清单存储边界、加载/错误状态 | `npm test`（Vitest） |
| 集成 | `frontend/scripts/verify.ps1`、`backend/scripts/environment_smoke.py`、API 契约（OpenAPI/前端运行时校验） | 一次复验：后端检查 → 产物核验与复现比较 → 前端干净安装/类型检查/测试/lint/构建/两视口浏览器检查 → OpenSpec 严格校验 | `pwsh -File ./scripts/verify.ps1`（环境前置：PowerShell 7、`chcp.com 65001`、ASCII 路径，见 frontend/README.md「验证环境说明」） |
| 系统 | `frontend/e2e/`：`workbench.spec.ts`（演示链路）、`historical.spec.ts`（真实链路：完整批次→查询→详情→清单→刷新、错误恢复、上下文隔离）、`storage.spec.ts`（清单存储）、`accessibility.spec.ts`（本 change 新增） | 核心端到端链路：界面→业务/数据层，真实 HTTP 不拦截模型响应 | `npm run test:e2e`（Playwright，`desktop-1280`／`desktop-1440` 两 project） |
| 非功能 | 本 change 的易用性/无障碍与性能基线（见第三节） | ≥2 项 NFR 的可测量证据 | 见第三节 |

**核心端到端链路定义**（系统层验收对象）：真实历史批次加载 → 搜索/日期/排序 → 详情 → 加入清单 → 刷新恢复 → 移除；以及服务不可用 → 重试恢复（异常链路）。

**分层原则**：任务完成 ≠ 功能合格，每项功能变更须有对应层的实际运行证据；测试与验证输出只写运行工作区 `docs/evidence/_run/`，归档证据由显式冻结产生，测试不写任何已归档目录。

## 二、缺陷记录规范

缺陷使用 Issue 或等价记录管理，每条至少包含：

- **现象**：实际行为与预期差异；
- **复现条件**：环境、数据/模式、操作步骤；
- **优先级**：阻塞主链路 / 一般 / 低；
- **处理状态**：新建 → 处理中 → 已修复（关联提交/change）或已关闭（附原因）；
- **关联提交/change**：修复该缺陷的提交标识或 OpenSpec change。

测试发现的缺陷先记 Issue 再修，不在测试代码里静默放宽断言。

## 三、非功能需求（NFR）验证

### NFR-1 易用性/无障碍（本 change 落实，Sprint 3 复核）

检查清单由 CRR-12 两个场景与产品文档 NFR-03 逐条推导，每条含判据、方法与证据形式：

| 编号 | 检查项（判据） | 方法 | 证据形式 |
|---|---|---|---|
| A11-1 | 两视口（1280×720、1440×900）无页面级横向溢出 | e2e 断言 `document.documentElement.scrollWidth <= innerWidth`，两 project 各跑 | 断言结果 + 两视口截图 |
| A11-2 | 纯键盘完成「列表→详情→加入→清单→返回」链路，关键操作有可见焦点 | e2e 按 README 已记录链路逐键操作并断言每步 `document.activeElement` 落点 | 断言记录 + 焦点截图 |
| A11-3 | 关闭详情后焦点返回触发位置 | Escape 后断言 `activeElement` 为原提交按钮 | 断言记录 |
| A11-4 | 状态不只靠颜色区分：模式与错误有可读文字 | 断言「真实历史回放/演示模式」徽标文本与错误 `role="alert"` 文案存在 | 断言记录 + 错误态截图 |
| A11-5 | 详情内容可滚动 | 键盘 End 后断言详情区 `scrollTop > 0` | 断言记录 |
| A11-6 | 真实用户走查（非开发者参与者） | 邀请走查并记录人数、耗时、成功率 | Sprint 3 待补，不编造 |

对应关系：A11-1/A11-2 对应 CRR-12「桌面核心链路」场景，A11-2～A11-5 对应 CRR-12「键盘操作与焦点返回」场景，A11-4 同时对应 NFR-03 的「模式和错误有文字说明」。

### NFR-2 性能（本 change 落实基线，Sprint 3 按完整协议重测）

本机链路基线（本 change 实测）：

| 编号 | 测量项 | 方法 | 口径 |
|---|---|---|---|
| PERF-1 | 本机推理服务响应 | `backend/scripts/perf_baseline.py` 用已锁定 httpx 对 `GET /api/review-batch` 发 30 次顺序请求 | 逐次计时 + nearest-rank P95 + 环境版本（Python/CPU/RAM）+ 错误数 |
| PERF-2 | 前端首屏加载 | `frontend/scripts/` 下 Playwright 脚本，两视口各 10 次 | 导航时间戳与 fetch→解析→渲染完成标记 + nearest-rank P95 |

**本机链路基线声明**：以上测量只描述当前本机链路，未做阈值判定；NFR-01 完整协议（每种模型 ≥200 次单条 JSON 预测、4 个 LAN 客户端加载 1,853 条列表、P95≤2s／列表≤3s 阈值判定、冷启动/排队单列）待在线预测接口落地后在 Sprint 3 重测。

### NFR 可选第三项：可靠性（既有证据沉淀）

现有素材：`test_http_lifecycle.py`（服务不可用→恢复重试）、`historical.spec.ts`「网络失败不回退演示，恢复重试实际 HTTP」与「错误真实来源不能展示旧批次」。Sprint 3 将其沉淀为可靠性 NFR 报告；本 change 不重做。

## 四、Sprint 3（11/16–12/20）执行安排

Sprint 3 不写新功能，只测试、修缺陷、补证据：

1. 按第一节分层执行全部测试；每个核心功能给出正向验收与至少一个异常/无效输入验证（已有规格场景为基线）。
2. 执行完整 NFR-01 协议（在线预测接口落地后）与 NFR-02 可靠性沉淀；复测 A11-1～A11-5 并补 A11-6 真实走查。
3. 缺陷按第二节规范记录并处置。
4. 测试报告结构约定：范围与时间、分层执行结果（通过/失败/跳过及原因）、缺陷清单与处置状态、NFR 证据与数字、已知问题与限制。汇总到 `docs/`，与冻结证据互相引用。

## 五、证据与冻结约定

- 测试与验证输出写运行工作区 `docs/evidence/_run/`（可覆盖、不入库）；截图在 `_run/screenshots/`，运行期夹具在 `_run/fixtures/`（冻结时排除）。
- 归档证据只由显式冻结产生：`python -m jit_baseline.cli freeze-evidence docs/evidence/<change>`，随后 `check-evidence` 校验；冻结清单含每个证据文件的相对路径与 SHA256。
- 每个归档 change 附 `verification.json`，把本计划中的检查条目（A11-x、PERF-x）映射到证据文件，逐条可定位。
