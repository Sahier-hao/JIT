# JIT 缺陷预测项目代码导读

适合第一次接手项目、看过界面但还不熟悉代码的人。先读「项目在做什么」和「一次分支分析」，再按自己用过的页面选读。需要查一个具体文件时，在[项目文件索引](项目文件索引.md)里搜索文件名。

本页按 2026-11-20 的仓库代码编写，参考点为 `main` 的 `db115b6`。工作区有正在编辑的文件，本文以已提交版本的核心结构和流程为基准。实际导入的数据、模型启用状态和当前默认模型以本机目录库为准。

## 1. 项目在做什么

这是一套运行在本机的**代码审查辅助工具**。给它一个公开 Git 仓库，它可以对一段提交历史打分，把更值得先看的提交排到前面。评审人可以打开一条 PR，读代码改动、记录自己的疑点，再回来复核作者的新版本。

**JIT** 是 Just-in-Time 的缩写。在这里，它指以代码提交为单位、尽量在审查阶段提供风险提示。主要模型输入是从 Git 历史提取的数字，例如新增行数、删除行数、涉及文件数。一个提交可以包含多个文件和很多行，但项目里的主模型给这个提交一个风险分。分数反映模型对输入的估计，尚未针对当前仓库校准成缺陷概率。是否接受某段代码由评审人判断。

项目有三类用途。

| 你在做什么 | 入口 | 保存或得到什么 |
| --- | --- | --- |
| 登记仓库，分析分支，看近期风险分布 | 项目工作区 | 每次分析使用的分支、提交范围、模型、运行和逐提交分数 |
| 阅读一条 PR，写意见，复核作者更新 | 项目 PR 清单、我的审查 | 服务端的固定 PR 快照，以及本浏览器里按账户隔离的审查工作单 |
| 准备数据、训练和维护模型 | 我的数据、我的训练、我的模型，或管理员工作区 | 数据集版本、训练任务、模型产物、登记信息和评估报告 |

仓库还有用于课程与实验的历史验证、离线 PR 报告、行级研究和 VS Code 扩展。它们的入口和数据范围见[离线与研究](离线与研究.md)。

## 2. 先认识四个位置

```text
浏览器中的 React 页面
   │ 发送 HTTP 请求，例如 POST /api/v1/repository-syncs
   ▼
Python FastAPI 后端
   │ 校验输入，安排后台任务，返回任务 ID 或结果
   ├── Git / GitHub 读入提交、改动和公开 PR 信息
   ├── 机器学习代码把提交转成数字、训练或评分
   └── SQLite 与本机文件保存任务、结果、数据版本和模型
```

| 位置 | 怎么理解 | 从哪个文件进去 |
| --- | --- | --- |
| `frontend/` | 浏览器显示的页面、按钮、表单和图表。React 组件通常是一个可复用的界面块，代码常以 `.tsx` 结尾。 | [main.tsx](../frontend/src/app/main.tsx)、[App.tsx](../frontend/src/app/App.tsx) |
| `backend/` | 接收浏览器请求，排队采集、训练或打分，并读写记录。主体是 Python 包 `jit_baseline`。 | [cli.py](../backend/jit_baseline/cli.py)、[api/app.py](../backend/jit_baseline/api/app.py) |
| `docs/` | 给人看的说明、产品约定、操作手册、验证报告和项目交付材料。 | [当前产品](当前产品.md)、[文档目录索引](README.md) |
| `openspec/` | 按功能记录应该有哪些行为，历史变更保留提案、设计与任务。 | [主规格](../openspec/specs/)、[变更归档](../openspec/changes/archive/) |

**API** 可以理解成前后端约定好的入口。路径告诉后端要处理哪类请求，`GET` 通常读数据，`POST` 通常提交操作。前端页面地址用 `#/` 开头，例如 `#/projects`，由浏览器里的 React Router 解释。以 `/api/` 开头的请求才走 Python 后端。开发时浏览器访问 `127.0.0.1:4173`，Vite 会把 `/api` 请求转给默认监听 `127.0.0.1:8000` 的后端。[路由表](../frontend/src/app/routeTable.ts)、[Vite 配置](../frontend/vite.config.ts)

**服务** 是后端负责一类业务的代码，例如执行仓库分析。**worker** 是实际在后台跑耗时工作的执行入口。**SQLite** 是本机数据库，任务状态和结果等以数据表记录，默认文件是 `backend/storage/catalog.sqlite3`。浏览器收到任务编号后会定期再问状态，所以任务运行时还能操作页面。

## 3. 一次分支分析经过哪些文件

用「我登记了一个 GitHub 仓库，现在想对 `main` 的一段历史用现成模型打分」举例。**登记项目**只是记录要关注的仓库。点「发起分析」后才创建后台分析任务。在代码里，一次分析常叫 `sync`，页面上的 `syncId` 是它的编号。

API 接收请求并返回任务编号，worker 按这个编号执行分析，`predict_risks` 调用模型给每条提交打分。浏览器凭同一个编号查进度和结果。

| 步骤 | 实际发生什么 | 对应文件 |
| --- | --- | --- |
| 1. 打开项目详情 | 路由选中项目页面，组装概览、PR 和分析入口。 | [routeTable.ts](../frontend/src/app/routeTable.ts)、[ProjectPage.tsx](../frontend/src/features/projects/pages/ProjectPage.tsx) |
| 2. 填表并提交 | 弹窗里的表单收集分支、时间、提交数上限和模型策略。模型选择项从后端取得。 | [AnalysisLauncher.tsx](../frontend/src/features/projects/components/AnalysisLauncher.tsx)、[AnalysisForm.tsx](../frontend/src/features/projects/components/AnalysisForm.tsx)、[modelClient.ts](../frontend/src/features/models/modelClient.ts) |
| 3. 发送请求 | `createRepositorySync` 把表单转换成请求体，发到 `POST /api/v1/repository-syncs`。API 读取参数，并检查指定模型的归属。 | [apiClient.ts](../frontend/src/lib/apiClient.ts)、[repositoryContract.ts](../frontend/src/features/projects/repositoryContract.ts)、[api/app.py](../backend/jit_baseline/api/app.py) |
| 4. 建任务 | `SyncService.create` 校验参数、保存所选模型身份，重复的活动请求可以复用。任务写入目录库，排队后由进程入口运行。 | [services/sync.py](../backend/jit_baseline/services/sync.py)、[sync_worker.py](../backend/jit_baseline/sync_worker.py) |
| 5. 采集和准备 | 读取固定范围内的 Git 提交。每条提交转成一行数字特征，例如 `la` 表示新增行数、`ld` 表示删除行数。通常还登记本次采集的数据版本。 | [ml/collect.py](../backend/jit_baseline/ml/collect.py)、[services/repository_datasets.py](../backend/jit_baseline/services/repository_datasets.py)、[core/schemas.py](../backend/jit_baseline/core/schemas.py) |
| 6. 评分并写入 | 按模型策略加载已登记产物，或者满足条件后训练。评分程序按模型期望的 schema 组装字段，通过 `predict_risks` 打分，保存分数、提交和模型运行身份。 | [ml/catalog.py](../backend/jit_baseline/ml/catalog.py)、[ml/model.py](../backend/jit_baseline/ml/model.py)、[services/sync.py](../backend/jit_baseline/services/sync.py) |
| 7. 在页面看到结果 | 分析记录刷新状态。`ReviewWorkbench.tsx` 显示分支分析的提交明细，跟随地址中固定的 `syncId`，因此查看旧记录时能找到当时的分数和来源。点击生成解释后，后端用该结果绑定的模型核对分数并计算特征影响。 | [projectClient.ts](../frontend/src/features/projects/projectClient.ts)、[ReviewWorkbench.tsx](../frontend/src/features/reviews/ReviewWorkbench.tsx)、[CommitDetail.tsx](../frontend/src/features/projects/components/CommitDetail.tsx)、[services/repository_explanation.py](../backend/jit_baseline/services/repository_explanation.py) |

同一个仓库可以有多次分析，每次保存自己的范围与结果。项目有一个便于回到常用结果的「当前分析」，打开一条历史分析仍然看那条记录。`repositoryId` 是项目编号，`syncId` 是单次分析编号，`commitId` 是 Git 提交 SHA。Git SHA 是识别某一提交的字符串。对比分析时先核对两边的模型和范围再解释分数差，图上的高分占比是模型分档统计。[分析对比](../backend/jit_baseline/services/analysis_comparison.py)、[项目趋势](../backend/jit_baseline/services/project_trends.py)

**怎么在编辑器里自己跟一遍**。打开 `AnalysisForm.tsx` 搜索 `createRepositorySync`，跳到它的定义会看到 API 路径。去 Python 代码里搜索同一个路径，就能找到 `create_sync`。再打开 `services/sync.py` 搜索 `class SyncService` 与 `def _run`。跟完这一次，同样的方法也能找到数据导入、训练、PR 刷新对应的后端代码。

## 4. PR 审查和分支分析的关系

PR 是 Pull Request，即作者请求把一组变更合入目标分支。系统会记录比较基准 `base` 和作者提交端 `head` 的 SHA。它们组成固定快照，所见的改动、行号和分析才有可追溯的版本。

1. **从项目看 PR 清单。** `ProjectPullRequests.tsx` 显示清单，`projectActivityClient.ts` 发查询和批量分析请求。后端 `services/pr_updates.py` 处理开放 PR 的跟踪、历史和批次。后台跟踪需要项目显式启用，服务运行时才定期检查。
2. **点开 PR 看只读详情。** `PullRequestJourney.tsx` 协调打开 PR、刷新快照和进入工作单，`PullRequestPreview.tsx` 展示快照摘要与模型线索。`prReviewClient.ts` 调用 `/api/v1/pr-snapshots/…` 等端点，后端 `services/pr_review.py` 负责快照、文件 Diff 和上下文。Diff 是加了哪些行、删了哪些行的对照。
3. **创建个人工作单。** `PullRequestJourney.tsx` 用 `CodeDiff.tsx` 显示代码改动，用 `WorkPanels.tsx` 里的组件编辑问题和结论。`prReview.ts` 把工作单和恢复副本写进当前浏览器的 `localStorage`，`reviewAccount.tsx` 提供当前已确认的账户身份。换浏览器前，在原工作单打开「草稿备份与反馈」，点「导出完整草稿」保存 JSON。新浏览器登录同一账户后，从「我的审查」选择「从完整草稿备份恢复工作」。如果已有该 PR 的工作单，可以在工作单里预览和合并备份。
4. **复核作者更新。** 新推送可以产生新快照，个人工作单保留旧轮次并关联新轮次。模型分数帮助先读风险较高的提交。Python 静态候选由 `services/candidate.py` 单独产生，给出固定侧别、路径、行号和规则证据；候选可由人工确认后放进意见草稿。最终意见由评审人确认和交付。

对应入口见[PR 使用指南](PR审查使用指南.md)、[PR 页面代码](../frontend/src/features/reviews/pages/PullRequestJourney.tsx)、[后台 PR 跟踪](../backend/jit_baseline/services/pr_updates.py)、[本地工作单](../frontend/src/features/reviews/prReview.ts)。

## 5. 数据怎样变成一个可用模型

以「用我的数据训练一个模型，再拿到项目中使用」为例。

| 环节 | 你需要理解的事 | 对应代码 |
| --- | --- | --- |
| 得到数据版本 | 从公开仓库按时间采集，或在「我的数据」导入 CSV。版本描述文件通常叫 manifest，记录来源、字段、时间范围和文件校验值。清洗产生新版本，原版本供复查。 | [MyDataPage.tsx](../frontend/src/features/datasets/pages/MyDataPage.tsx)、[services/user_api.py](../backend/jit_baseline/services/user_api.py)、[services/dataset_builds.py](../backend/jit_baseline/services/dataset_builds.py)、[ml/datasets.py](../backend/jit_baseline/ml/datasets.py) |
| 找到训练用的标签 | 标签是训练用的历史答案。SZZ 从识别出的修复提交出发，用 Git 的逐行历史追溯可能引入问题的旧提交。它是有证据的近似。项目保存观察窗口和成熟状态，观察不足的样本可评分，正式训练和评价有额外准入要求。 | [ml/szz.py](../backend/jit_baseline/ml/szz.py)、[ml/label_maturity.py](../backend/jit_baseline/ml/label_maturity.py)、[ml/admission.py](../backend/jit_baseline/ml/admission.py) |
| 按时间分成三段 | 默认按 `70/15/15` 目标比例切分。最早的训练集用于学习，中间的验证集用于选择配置，最后的测试集用于评估。相同时间的提交留在同一段，实际比例可能和目标略有不同。 | [ml/splits.py](../backend/jit_baseline/ml/splits.py)、[ml/split_preview.py](../backend/jit_baseline/ml/split_preview.py) |
| 训练并保存运行 | 界面给后端发送数据版本、算法和参数，后台安排队列。多方法实验固定数据和分区，让各方法基于同一批成员比较。模型文件、分区清单、指标等保存为一次运行的产物。 | [MyTrainingPage.tsx](../frontend/src/features/training/pages/MyTrainingPage.tsx)、[services/training_tasks.py](../backend/jit_baseline/services/training_tasks.py)、[training_worker.py](../backend/jit_baseline/training_worker.py)、[ml/training.py](../backend/jit_baseline/ml/training.py) |
| 显式登记 | 在个人训练实验里选择「登记本次模型」。登记会校验产物和身份，将可用信息写入模型目录。本人登记的模型可在本人项目请求中选择。管理员另有实验登记和默认模型管理。 | [MyModelsPage.tsx](../frontend/src/features/models/pages/MyModelsPage.tsx)、[ml/catalog.py](../backend/jit_baseline/ml/catalog.py)、[AdminExperimentRunsPage.tsx](../frontend/src/features/admin/AdminExperimentRunsPage.tsx) |

例如，你的 MLP 训练显示成功，项目的模型下拉框还找不到它。先回「我的训练」的实验详情找「登记本次模型」，登记成功后再以原账户打开项目，查看模型是否兼容该分析。管理员设为默认是面向默认选用策略的另外一步。

这里有五个经常一起出现的名词。

| 名词 | 含义 |
| --- | --- |
| **算法** | 用什么方式学习，例如逻辑回归、随机森林、MLP。`ml/algorithms.py` 列出支持的算法和参数。 |
| **特征 schema** | 模型和输入之间的字段合同，包括需要的字段、顺序和含义。同样是 14 个数字，字段含义也可能随 v1、v2 改变。当前采集的 `kamei14-git-v2` 沿第一父链计算历史，默认 SZZ 为 `szz-full-v1`。 |
| **数据集版本** | 这一批样本和它的来源、标签、观察窗口的固定身份。 |
| **运行** | 某一次实际训练的记录，例如用哪个数据、参数和随机种子，切分成员为何。算法相同也可以训练出多个运行。 |
| **已登记模型** | 目录库里可识别、可验证的一条模型记录，通过 `modelId` 关联产物和 `runId`。项目下单时保存选择，历史结果可以追溯到实际使用的模型。 |

模型训练完成、产物登记成功、发布资格检查通过、被管理员批准设为默认，是不同环节。支撑发布的是固定测试数据上的评估。比如 **Recall@20%LOC** 关心给定约五分之一变更行数的审查预算内找回多少有标签的正例，适合解释排序能节省多少阅读工作。**ROC-AUC** 衡量正例排在负例前的能力，**AP** 汇总精确率与召回率的表现，适合关注正例较少的任务。比较这些指标时先看数据版本、测试成员、分数覆盖和预算规则。[数据与训练切分](数据与训练切分.md)、[模型包部署](模型包部署.md)、[模型卡服务](../backend/jit_baseline/services/model_cards.py)

## 6. 哪段代码算数，数据又存在哪里

### 同名文件先看路径

例如 `backend/jit_baseline/sync.py` 顶部写着 `Compatibility proxy`，旧导入会转到 `backend/jit_baseline/services/sync.py`。写着 `canonical module` 的路径是实现位置。读 `catalog.py`、`collect.py`、`training.py` 和 `store.py` 时也有类似情况。[旧 sync 入口](../backend/jit_baseline/sync.py)、[实际 sync 实现](../backend/jit_baseline/services/sync.py)

前端也有层次。页面文件常以 `Page.tsx` 结尾，`components/` 是页面里的局部组件，`*Client.ts` 负责请求，`*Contract.ts` 常负责检查后端返回的数据形状，`use…` 是 React 中可以复用的页面逻辑。共用视觉组件在 `components/ui/`，项目自己的业务逻辑在 `features/`。

### 同一界面可以读多个来源

| 位置 | 里面有什么 | 看代码时怎么区分 |
| --- | --- | --- |
| `backend/storage/catalog.sqlite3` | 项目、分析任务、分数、训练任务、模型目录、账户等持久记录 | 数据文件在本机生成。建库与升级规则在 [catalog_storage.py](../backend/jit_baseline/storage/catalog_storage.py) 和 [migrations](../backend/jit_baseline/storage/migrations/)。编号到 `041`，最新编号对应数据集共享。 |
| `backend/data/datasets/` | 版本描述 JSON，部分版本附带 CSV、标签或其他证据文件 | 一个 JSON 可能只描述一个版本，实际数据还依赖它引用的文件。用 [datasets.py](../backend/jit_baseline/ml/datasets.py) 理解发现、读取与校验过程。 |
| `backend/artifacts/` | 可加载的模型目录、运行清单、分区与指标等实际产物 | 多数由运行生成。本机模型目录与仓库里的发布 ZIP 有各自的生命周期。 |
| `backend/model-packages/` | 随 Git 交付的模型 ZIP 和校验摘要 | `jit-nine-models-v1.zip` 是九种方法的历史六字段兼容交付，`jit-current-v2-models-v1.zip` 是当前 v2 基线交付，`jit-pr-check-model-v1.zip` 供提交分析 CI。安装登记和实际启用状态到目录库核对。 |
| 浏览器存储与 Cookie | 审查草稿和部分界面偏好留在浏览器，登录会话凭证由 HttpOnly Cookie 携带 | 查工作单用 `prReview.ts`，查后端登录和权限用 `backend/jit_baseline/auth/`。清理浏览器站点数据会影响本地草稿和已读状态。 |

普通用户的个人数据集、实验、模型和草稿有账户边界。项目和公开 PR 来源按本机共享设计。管理员的模型维护、数据集管理和验证记录受服务器鉴权保护。看见一个按钮只说明界面提供入口，是否允许执行应追到 API 的授权检查。[入口与端点分层清单](架构/入口与端点分层清单.md)、[权限依赖](../backend/jit_baseline/auth/dependencies.py)、[运行与升级](运维与升级.md)

## 8. 看懂规格、测试和历史记录

- **规格回答应该怎样。** `openspec/specs/<能力>/spec.md` 写要求与场景。一个变更的 `proposal.md` 说明原因与范围，`design.md` 写实现选择，`tasks.md` 是交付清单，`specs/…/spec.md` 是该变更提出的新增或修改。归档目录能解释一个决定的来历。
- **测试回答代码在设定场景下怎样运行。** `backend/tests/test_*.py` 是 pytest 用例，前端的 `*.test.ts(x)` 多是逻辑或组件测试，`frontend/e2e/*.spec.ts` 用 Playwright 在浏览器中走较完整的路径。比如分析后能否打开固定结果，需要看任务结果、页面跳转和真实交互。实际用过哪些运行环境和检查范围应从对应记录确认。
- **证据回答当时验证了什么。** `docs/审计/` 常记录变更内容、已执行的检查和遗留情况。`docs/evidence/` 存固定报告、数据摘要、截图、哈希或可复现脚本；其中有些目录还保存交付时的代码副本。写产品或定位问题时，从 `frontend/src/` 和 `backend/jit_baseline/` 的当前实现追起。
- **持续回归是自动检查入口。** `.github/workflows/regression.yml` 定义何时跑哪些检查，`backend/scripts/regression_scope.py` 列出关键层范围。`commit-analysis.yml` 是另一个工作流，用固定模型生成提交分析报告。依赖、端口和隔离约定见[持续回归](持续回归.md)。

如果日后让 AI 接手某一处，先给它页面地址、做过的操作、实际看到的结果以及期望行为。例如「在项目的分析页用现成模型发起任务，成功后打开历史记录却看到了另一批提交；请核对地址里的 `syncId`、请求参数、响应中的模型与前端读取结果的路径」。这样可以把问题限制在一条用户流程，并按相同操作验证修复。

## 9. 第一次读代码的顺序

从 [AnalysisForm.tsx](../frontend/src/features/projects/components/AnalysisForm.tsx) 开始，沿 [apiClient.ts](../frontend/src/lib/apiClient.ts) 找到 [api/app.py](../backend/jit_baseline/api/app.py) 的创建任务路由，最后去 [services/sync.py](../backend/jit_baseline/services/sync.py) 找任务入队与评分保存。读到能回答下面四个问题，就可以独立追其他页面。

1. 我点的是哪个组件里的按钮？
2. 请求发到了哪个 API，带上了什么参数？
3. 后端把哪一个项目、模型和数据版本绑定到任务？
4. 返回的编号如何让浏览器在刷新后重新找到同一条结果？

遇到没见过的文件名，用[项目文件索引](项目文件索引.md)定位。要在本机启动或升级时，从[项目首页](../README.md)和[运维与升级](运维与升级.md)进入。
