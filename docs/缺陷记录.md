## D-001 本机既有运行的模型 pickle 引用已删除符号，真实模式不可用

**现象**：本机 `backend/artifacts/baseline` 与 `backend/artifacts/reproduction` 的 `model.joblib` 无法加载。`python -m jit_baseline.cli verify` 以 `MODEL_INVALID`（"模型无法加载或类型无效"）退出；本机只读服务的真实模式在启动时判定产物不可用，`GET /api/review-batch` 返回 503，前端显示数据不可用。演示模式不受影响。

**复现条件**：

1. 在 `backend` 下执行 `python -m jit_baseline.cli verify`（默认运行目录 `artifacts/baseline`）。
2. 或在 `backend` 下执行 `python -m jit_baseline.cli serve` 后请求 `GET /api/review-batch`。

两者都报 `MODEL_INVALID`。**该缺陷先于本 change 存在**：把本 change 的源码改动临时收起（`git stash`）后，在 HEAD 状态执行同样命令仍报同一错误。

**根因**：`artifacts/baseline` 与 `artifacts/reproduction` 生成于 2026-10-10（manifest `generatedAt` 为 `2026-10-10T14:50Z`，运行标识 `a31140a9…`）。它们的模型 pickle 引用 `jit_baseline.model.log_counts`。d0370b7（`align-feature-and-model-definitions`）把该函数换成了模块级类 `Log1pColumns`，序列化引用因此失效。`artifacts/` 不进版本控制，而当时没有任何测试读取已提交的运行（所有产物测试都在临时目录现场重训），因此没有被自动发现；该 change 的 D7 又明确"不重写 baseline、运行标识不变"，把"仍然可加载"当作前提而没有验证。

**影响范围**：本机真实模式完全不可用；`frontend/scripts/verify.ps1` 的 `real-artifact-verification` 与 `independent-reproduction-comparison` 两步在 HEAD 状态即失败。

**处理**：按固定命令重建这两个运行（`python -m jit_baseline.cli run --output artifacts/baseline`，`… --output artifacts/reproduction`），重建前把旧目录备份到 `backend/.cache/pre-rebuild-2026-10-10/`。归档证据 `docs/evidence/` **未被修改**；重建运行与归档证据 `docs/evidence/connect-public-data-baseline-review/summary.json` 的 `datasetVersion` 相同、`features` 相同、冻结测试成员数相同，六个指标差为 **0.0**（要求 ≤1e-8）。重建后运行标识由 `a31140a9…` 变为 `07b6102b…`（声明中增加了 schema、方法版本与指标集三项），响应契约对前端保持兼容：`model.id` 仍为 `logistic-regression-six-v1`、六字段顺序不变、契约版本 1、1853 条记录。

**防复发**：本 change 新增"重建的六字段运行仍与归档证据同一数据版本、指标一致"的常驻回归（`backend/tests/test_artifacts.py`，读 Git 内的归档证据，不依赖本机产物），以及"本机既有运行仍可校验与复现比较"的用例。后者对**这一种**已知原因（pickle 引用已删除符号）跳过并给出原因，其它加载失败照常判为失败。

**遗留**：`backend/artifacts/development/model.joblib` 是同一批旧产物、同样引用 `log_counts`；它没有代码引用，README 只把它列为"技术与行为检查、不能作为正式效果"的目录，本次未重建。

## D-002 方法声明的依赖未安装时 `environment()` 抛出未归类异常

**现象**：只要某方法在注册表声明了 `requires` 非空（例如将来的深度方法声明 `torch`），在任何**未安装**该依赖的机器上执行 `python -m jit_baseline.cli run --algorithm <方法>` 都会以未归类的 `PackageNotFoundError` 崩溃，而不是给出可定位的产品错误。`cli.py` 的 `except (BaselineError, OSError)` 接不住它。

**复现条件**：临时把任一注册条目的 `requires` 改成 `("torch",)`（或任一未安装的包名），在 `backend` 下执行 `python -m jit_baseline.cli run --output .cache/d002`；当前 HEAD 会抛出完整 traceback。

**根因**：`artifacts.py` 的 `environment()` 用 `version(name)` 逐个取版本却没有捕获 `PackageNotFoundError`。`requires` 字段在 `generalize-model-registry-and-run-contract` 引入时，两个登记方法的 `requires` 都是空的，这条路径**从未被执行过**；同一 change 在**校验**侧（`check_environment`）写了对该异常的处理，**生成**侧漏了，形成不对称。

**影响范围**：本机 `run` 对任何声明了未安装依赖的方法不可用；GPU 席位登记深度方法时必然撞上。既有运行不受影响（不经过这条路径）。

**处理**：把该异常归一到带稳定错误码的 `BaselineError`（`ARTIFACT_INVALID`，"方法声明的依赖未安装：<包名>"），并登记一个 `requires` 非空的方法（`random-forest-v1`）使这条路径有实际对象。

**防复发**：`backend/tests/test_artifacts.py` 的 `test_missing_declared_dependency_is_a_located_error` 断言错误码与包名；`test_a_method_declaring_a_dependency_produces_a_verifiable_run` 覆盖正常路径；`test_algorithms.py` 断言注册表里确实存在 `requires` 非空的方法。

## D-003 在加速设备上序列化的产物在本机不可加载

**现象**：把在 CUDA 上序列化的模型（保存时张量仍在 GPU 上）交给本机校验或服务时，模型加载失败，服务返回 503 `MODEL_INVALID`。**本 change 之前没有任何地方要求交付的模型必须能在无加速设备的机器上加载**，也没有对应用例。

**复现条件**：本机无 GPU，对交付的产物执行 `python -m jit_baseline.cli verify --run <产物目录>`。错误码本身是对的（`MODEL_INVALID`），但这一点此前既未被要求、也未被测试——与 D-001 同类的失效（产物在另一台机器上不可加载）只是恰好被现有的 `try/except` 兜住。

**根因**：加载路径是 `joblib.load`（pickle 直接反序列化），无法注入设备映射；单机链路下产物与加载它的机器同源，因此问题不可见。训练改到另一台机器后必然出现。

**影响范围**：任何在加速设备上训练并交付的运行。服务所用的运行不受影响。

**处理**：把"交付产物必须能在无加速设备的机器上加载"写成显式契约——[PROTOCOL.md](backend/PROTOCOL.md) 的「环境声明与跨机器语义」与 [artifacts/external/README.md](backend/artifacts/external/README.md) 的交付约定第 4 条；由产方负责设备中立交付，本机**只验证不修补**。

**防复发**：`test_a_model_that_only_loads_on_an_accelerator_is_rejected_with_a_located_code` 与 `test_a_complete_declaration_does_not_redeem_an_unloadable_model` 断言不可加载的产物以 `MODEL_INVALID` 被拒绝；`test_a_device_neutral_stand_in_model_is_actually_loaded_and_run` 覆盖设备中立的正常路径。

**状态说明**：尚无真实 GPU 产物交付，因此**没有实际发生**；本条目是与 D-001 同一失效形态的预防性登记。
