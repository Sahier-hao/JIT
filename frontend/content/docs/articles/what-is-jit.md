JIT 是 just-in-time 的缩写。JIT 缺陷预测在每次提交刚进入仓库时，用这次提交可观察到的变更和历史信息估计风险，帮助审查者决定先看哪一条提交。它不运行测试，也不直接确认缺陷。

## 用一条短提交理解 {#example}

假设一次提交同时做了三件事：

1. 修改支付回调的异常处理。
2. 把两个函数的参数顺序互换。
3. 只更新一个文案。

从提交级特征看，这次改动涉及多个文件和较大的变更块，错误处理路径也发生变化，历史上类似路径更容易出现后续修复。模型可能给出 `0.78` 的分数。

这个分数表示该提交在当前模型排序中相对靠前，不表示有 78% 的概率存在缺陷，也不告诉你是哪一行错了。

## 模型看了什么 {#model-input}

当前仓库分析使用提交级特征，例如：

- 增删行数、修改文件数、修改目录和文件类型。
- 提交涉及的历史变更规模与修复记录。
- 作者近期活动、提交时间和路径相关特征。
- 当前 schema 声明的其他结构性特征。

实际字段和预处理由模型绑定的特征 schema 决定。不同 schema 不能混为一谈；模型身份、运行、数据和 schema 会随分析结果保存。

模型没有阅读完整运行时、测试结果或生产日志。它看到的是固定采集范围内可计算的代理特征，因此只能作为排序线索。

## 为什么会有分数 {#score}

训练时，模型学习历史提交特征与后续缺陷证据之间的统计关系。评分时，模型对当前提交输出一个实数，再按当前产品规则展示。

分数要结合范围理解：

| 范围 | 含义 |
| --- | --- |
| 提交级 | 当前提交的相对风险排序 |
| PR 级 | 已分析提交中的最高分，用于安排审查 |
| 文件级 | 文件涉及提交的最高分，用于阅读顺序 |
| 行级研究 | 只对特定语言新增行的研究排序 |

这些层级都不能直接推出“整个 PR 有某个百分比概率有缺陷”。

## 审查者怎么用 {#next-step}

1. 先看固定的是哪个模型和哪次分析。
2. 从提交级高分开始阅读 Diff。
3. 用作者说明、代码路径、测试和静态规则证据核对。
4. 把有证据的问题记录到个人工作单。
5. 分数低时仍要覆盖关键路径，不把低分当作安全证明。

没有模型时也可以人工审查。模型不可用不应该阻断代码阅读、证据记录和 Markdown 导出。

## 不该从分数推出什么 {#limits}

- 不能说 `0.8` 就是 80% 缺陷概率。
- 不能用不同模型、schema 或分档规则直接比较“风险改善”。
- 不能把文件排序当作文件级概率。
- 不能把行级研究排序当作逐行缺陷概率。
- 不能因为未评分、未覆盖或模型失败就推断低风险。

需要区分各类解释和证据时，阅读[怎么看风险分和代码线索](#/docs/reading-results?section=commit-score)。
