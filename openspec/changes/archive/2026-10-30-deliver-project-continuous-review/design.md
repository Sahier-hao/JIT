# Design

## Context

当前系统为单机部署：单个 FastAPI 后端、单个分析 worker、SQLite 目录库，前端为 React/Vite。已有能力包括项目登记与分支分析、独立仓库更新检查、公开 PR 工作单、个人浏览器草稿和固定分析结果。约束是公开 GitHub 来源、服务端令牌不进入浏览器、单后端实例、不引入 Redis/Celery，并且必须保留既有数据、模型产物与个人草稿。动机与范围见 proposal.md，行为契约见 specs/。

## Goals / Non-Goals

**Goals:**

- 以项目列表为默认入口，把概览、PR 审查、风险趋势、分析记录收进同一项目工作台，同时保留旧深链接与跨项目个人聚合。
- 让项目自身成功分支分析形成固定、可复核的趋势视图，不复制分数、不混入 PR 或用途不明的来源。
- 让项目在后台持续发现 PR 更新并按固定快照与模型自动分析，使用持久意图、队列、租约、重试和幂等事件。
- 保持个人草稿、轮次、证据和人工结论完全留在浏览器；后台事件只提醒，不自动改写。

**Non-Goals:**

- 不新增普通用户账户、团队协作、邮件/桌面推送、Webhook 或 GitHub 写入。
- 不读取简化 SZZ 标签生成项目缺陷率，不重训模型，不改管理员维护界面。
- 不在本变更中升级真实本机数据库；只提供正向迁移与升级前备份。

## Decisions

1. **任务用途与归属放在 `repository_sync` 上。** 增加 `source_kind`（branch/pr/unknown）、`origin`（manual/automatic）、`source_snapshot_id`、`feature_schema_version`、`distribution_rule`；只有分支任务推进项目 `latest/default` 与当前结果。PR 任务的 `repository_id` 属于基项目，`repository_url` 与固定 HEAD 保留实际 fork 来源，不为 fork 另建项目。备选是新建 PR 任务表，但会复制任务生命周期、取消、超时与 worker 回收逻辑，故不采用。

2. **PR 快照与 latest 改为项目作用域。** 迁移 013 正向重建相关表，唯一键包含 `repository_id`；不合并同名重复项目、不改原项目 ID。备选是合并项目或改写 012，都会破坏既有引用与历史证据。

3. **旧 PR 评分在迁移时冻结真实关联。** `pr_legacy_analysis_binding` 只保存迁移时刻 `pr_analysis` 的真实 `snapshot_id/sync_id`，读取时标注两条限制；新任务不写该表，也不因字段缺失自动走旧兼容。备选是按 HEAD 形状推断，会把不同 base 或 fork 的评分错误拼接。

4. **趋势使用固定 manifest，不建物化聚合表。** `project_trend_view` 保存查询、口径、来源 syncId 清单和每个来源的内容指纹；读取时重新加载来源、核对指纹、按 SHA 去重后聚合。相同签名复用视图；新来源只置 `hasNewSources`，显式刷新才生成新视图。备选是物化聚合表，会带来陈旧数据、重复分数和来源追溯困难。

5. **PR 后台使用独立服务与独立检查线程。** `PullRequestUpdates` 拥有自己的单线程检查 executor、600 秒租约、持久游标/分页、意图与尝试表、事件表；不复用 `RepositoryUpdates` 的分支 watch 语义。队列边界为每 PR 一个在途自动分析加一个最新待处理目标，每项目每轮深入 20 个 PR、新增 1 个分析，全局自动排队 2 个；执行仍复用现有单分析 worker。

6. **事件持久化、已读本地化。** 事件写入 `project_event`，以 `uuid5` 生成幂等键；`isCurrent` 同时核对快照与当前自动模型。已读状态只写浏览器 localStorage，不新增账户或服务端已读接口。备选是服务端已读，但当前没有账户体系，会造成“跨设备同步”的虚假承诺。

7. **前端项目子路由显式携带对象身份。** `#/projects/{id}` 三子视图（概览、分析含页内「分析结果 / 风险趋势」切换、PR 审查）、`#/projects/{id}/prs`、兼容的 `/trends/{viewId}`、固定 PR 快照地址都从 URL 恢复；进入未指定 viewId 的风险趋势时按当前口径自动准备固定视图。旧 `#/reviews`、旧 PR 与旧分析地址继续映射。个人工作仍复用现有 `readWorks/saveWork/adoptVersion`，后台事件只提供“查看固定来源”和“明确开始新轮”，不自动写入。

8. **新建项目只登记，概览与分析分开。** 新建项目不 enroll 分支检查，也不产生分析；项目页以「概览（仓库信息）」为默认页，「分析（当前结果与记录）」保留原双栏。仓库概览通过独立服务读取公开 GitHub 元数据、语言、最近 100 条提交和最近 12 周活跃度，写入 `repository_overview` 缓存约 10 分钟。备选是把仓库信息混进当前结果页，但会让基本信息随分析结果变化，且限流/空态无法独立呈现。

9. **分支检查改为只提醒。** `repository_updates` 只 probe 远端 HEAD；发现与当前分析 HEAD 不同时写 `project_event` 的 `branch-updated`，不创建 `repository_sync`，不再要求 watch 绑定模型、窗口或提交上限。分析由用户点「分析这次更新」后通过现有 SyncService 发起，模型和范围在对话框中选。备选是保留自动分析并默认关闭，但用户明确要求“只提醒”；现有已开启 watch 迁移为只提醒，已提交/运行中的任务不取消。

10. **错误契约沿用现有信封。** 新增路径纳入 `api_errors.managed_path`；趋势来源冲突与失效分别返回 409 `TREND_SOURCE_CONFLICT` / `TREND_SOURCE_UNAVAILABLE`；所有响应保留 requestId 与 `Cache-Control: no-store`。备选是新增专用错误码体系，但会扩大客户端分支且无必要。

11. **提交文件映射随分析保存，只用于审查优先级。** `repository_commit` 增加 `file_paths_json`，采集时记录每个提交触及的路径（改名时同时保留旧路径）。PR 读取把快照文件路径与提交映射取交集，返回每个提交的文件、增删行、文件数和按触及提交最高分排序的 `fileRisks`。文件排序只作为阅读辅助，不生成 PR 整体或文件级缺陷概率；旧任务没有映射时不猜测，保持全部文件并说明无法按提交筛选。

## Risks / Trade-offs

- [PR 轮询与发现带来远端请求成本] → 默认间隔 300 秒、每轮深入上限 20、缓存 GET 不联网、分页与游标持久化；限流遵守 Retry-After/reset。
- [自动队列挤占手动分析] → 全局自动排队上限 2、每项目每轮新增 1、自动调度不取消手动或分支任务；执行仍单 worker。
- [旧 PR 关联无法证明新契约] → 迁移时冻结真实关联并明确限制，不自动加入新意图或跨来源趋势。
- [趋势同 SHA 冲突降低可用性] → 整组拒绝并列出冲突来源，提供单次固定来源查看，不静默择一。
- [本地已读无法跨设备] → 产品文案明确仅当前浏览器，不声称账户同步；已读不等于已复核。
- [单后端实例约束] → 部署说明维持单实例；多实例会重复调度并破坏租约语义。
- [重启遗留租约] → 启动时把过期 `checking` 收敛为中断，不自动重跑旧意图，保留主动重试入口。
- [隔离验收的 GitHub 响应受控] → 只证明来源接入与状态迁移，不描述为真实作者配合或模型效果验证。

## Migration Plan

1. 停止旧后端并另行备份 `backend/storage/catalog.sqlite3` 与模型目录。
2. 运行 `backend/.venv/Scripts/python.exe -m jit_baseline.cli catalog-init`；显式初始化旧库时先写一致的 SQLite 副本 `catalog.sqlite3.before-v<旧版本>-<随机>.sqlite3`，备份失败则不升级。
3. 正向应用 013（分析来源与项目作用域快照）、014（固定趋势视图）、015（PR 跟踪与事件）、016（仓库概览缓存）；迁移在事务中执行，失败回滚并保留备份。
4. 启动单个后端与前端。旧项目 PR 自动跟踪保持关闭，分支 watch 保持原设置；旧当前结果若指向 PR 不重置，由工作台说明来源。
5. 回退时停止新后端、备份升级后数据，再恢复升级前数据库及对应代码；旧代码不能直接读取 v16 数据库。个人草稿需在浏览器单独导出。
6. 验证使用一次性临时库、模型副本与端口；本变更按用户要求另行升级真实本机数据库前会先生成一致备份。
