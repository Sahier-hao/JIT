# Design

## Context

动机见[proposal.md](proposal.md)。本change的实现对象是文档：两份产品主文档、模板要求的接口与错误码配套材料，以及根README的导航；本轮propose只生成规划文件。

当前项目已具有React／TypeScript／Vite工作台、FastAPI本机只读接口、固定公开OpenStack数据及六字段逻辑回归。现有两份主规格已完整核对：`commit-risk-review`规定列表、详情、清单及来源边界；`public-data-baseline`规定冻结数据、训练、评价、产物与本机风险服务。它们不能直接作为新输入预测、局域网部署或完整课程范围已经实现的证明。

本项目两个模板刚提供，主文档尚不存在；旧目录只作参考。另有在途`separate-run-evidence-from-archive`正在调整验证输出，不能运行会写入旧证据的产品检查脚本来验证本次文档工作。

### 确认程度

| 类别 | 内容 | 文档处理 |
|---|---|---|
| 用户已确认 | 保留提交评审主线，数据与模型实验为支撑 | 作为产品目标与主流程 |
| 用户已确认 | 首版新输入采用特征文件或JSON；仓库地址＋提交ID以后再补 | 作为在线预测入口边界 |
| 用户已确认 | 团队共用服务，局域网可接受 | 作为完整版本的部署目标；与当前仅本机服务分开 |
| 当前资料已定方向 | 使用公开数据集，不自建Git解析／SZZ管线 | 与团队分工一致，同时记录原始课程要求及替代口径的来源 |
| 已观察事实 | 六字段、单模型、文件产物、历史回放、浏览器个人清单 | 附当前源码／规格／历史报告依据及核对日期 |
| 助手建议，未由用户确认 | 个人清单首版继续本地保存；账户和跨设备恢复后补 | 标为候选默认值或待决项，不写成用户已批准 |
| 后续选型 | 数据库、训练执行器、八模型组合、解释方法、认证和资源上限 | 可提出候选方案与取舍，不宣称已接入、已验证或用户已批准 |

## Goals / Non-Goals

**Goals:**

- 在用户模板中形成可阅读、可交叉核对的产品目标；每项需求能关联模块、界面／API、数据对象和验收方式。
- 把当前实现、未来产品目标、候选技术方案及未取得证据分别说明，避免文档推定系统功能或团队验收完成。
- 给后续功能change足够具体的业务和契约背景，同时保留当前运行边界和实验可复现性。

**Non-Goals:**

- 本change不实现共享服务、认证、数据库、上传、预测或解释接口，不运行模型训练或开启LAN监听。
- 本change不为未实现行为创建增量规格，不改现有主规格、已归档change或实验结果。
- 本change不补造访谈、竞品最新能力、教师批准、个人贡献、性能实测或模型效果；也不将旧项目版本史移植为本项目历史。

## Decisions

### D1. 纯文档change使用skip_specs

`.openspec.yaml`设置`skip_specs: true`。本change没有运行行为变化，因此不增加“文档管理”或“产品基线”运行能力来满足校验，也不将未来新接口写成已生效规格。

替代方案是修改现有两份能力规格或另造文档规格；这会使当前只读、本机、六字段的事实与尚未实现的目标混在一起。后续真正增加共享服务、新输入预测及解释时，单独建立对应功能change，并核对受影响的CRR／PDB条目。

本设计保留的原因：两份文档需协调目标架构、数据模型、接口材料及当前规格兼容性，提前确定编写与复核方式能减少apply时的范围歧义。

### D2. 主文档另存，保留模板结构与原件

apply输出：

| 文件 | 作用 |
|---|---|
| `docs/产品需求文档.md` | 用户、范围、故事、验收、非功能需求及阶段规划 |
| `docs/产品设计文档.md` | 概要与详细设计、模块、流程／时序、接口索引、ER图和字段设计 |
| `docs/api/openapi.yaml` | 现有接口记录及拟议接口契约，逐操作区分实现状态 |
| `docs/全局错误码表.md` | 当前错误含义、HTTP映射及候选新错误码的唯一文档定义处 |
| `README.md` | 仅增加两份主文档的入口，保留当前产品与运行说明 |

主文档章节保持如下；清除CMS、头像、示例Figma地址、空标题和飞书编辑操作提示，不照抄无关样例。

| 需求模板 | 设计模板 |
|---|---|
| 前言；一、版本信息；二、变更日志；三、文档说明；四、需求背景；五、需求范围；六、功能详细说明；七、非功能需求；八、项目规划；附录 | 前言；一、版本信息；二、变更日志；三、文档说明；四、概要设计（系统架构、系统模块划分、API清单、数据库概要设计）；五、详细设计（各模块、API、数据库表） |

模板要求的图示工具、原始任务提示词和资料依据记在主文档附录，并从图示处引用；不为图示记录再增加一批子文档。设计附录属于补充，不改变五章主体。

替代方案是直接填改模板原件或沿用旧目录的长文档。另存主文档保留模板对照，也能避免旧路径、旧版本史和旧技术栈继续成为新项目默认值。

### D3. 用24条候选业务故事组织完整目标

需求文档采用Epic → Feature → User Story，并保留模板功能表的“序号、模块、功能、功能详细说明、交互图”。具体故事暂按下表24条候选展开；apply可以调整表达与拆分，但需保留至少20条有用户价值、相互关联的核心业务故事，不用周报、PR或文档编写任务充数。

| Epic | Feature／候选故事 | 业务关联 |
|---|---|---|
| E1 数据可信且可重复使用 | US-01来源注册、US-02导入与质量、US-03标签语义、US-04特征方案、US-23重开保存版本、US-24输入与模型兼容检查 | 给实验和预测提供可核验输入 |
| E2 建立可追溯模型 | US-05时间分区、US-06两类多模型训练、US-07两类指标、US-08选择模型版本 | 产生带完整来源的可用模型 |
| E3 获得新提交风险依据 | US-09特征文件／JSON在线推理、US-16真实模型解释 | 将外部特征变成可理解预测 |
| E4 完成审查选择 | US-10模式与来源、US-11列表、US-12搜索、US-13日期、US-14稳定排序、US-15详情、US-17加入／移除、US-18清单恢复、US-19失败与重试 | 风险→详情→个人优先审查清单 |
| E5 核对整体结果 | US-20同口径模型比较、US-21历史趋势、US-22报告导出 | 用实验与历史记录核验产品结果 |

每条故事至少包含角色、目标与价值、稳定ID、P0／P1优先级、已有／部分已有／待建状态、正常验收和异常／边界验收，以及对应交互编号。现有CRR／PDB能证明部分行为，不能一概标记整条扩展故事已完成。

最终课程目标包括完整Kamei14、经典与深度两类总计至少八种方法、两类评价、预测解释和至少两项非功能验证；模型配置数量不能冒充方法数量。具体方法尚待数据和预算验证，不能因表格有24行就宣布已满足课程验收。

### D4. 以现状、完整目标和后续扩展三个层次组织流程

现状：固定公开快照 → 六字段逻辑回归 → 冻结测试批次 → 当前工作台／本地清单。依据是当前源码和已有真实报告，注明报告日期及回顾性限制。

完整目标包括两条相关链路：

```text
Public dataset -> source/schema checks -> temporal split
               -> training/evaluation -> verified model/run

Feature file or JSON -> selected model/schema -> validation
                     -> inference/explanation -> review list/detail
                     -> personal shortlist
```

文件输入首版建议CSV；JSON首版建议支持单条提交特征。这是apply编写文档的候选默认值；文件批量上限、部分失败策略和JSON是否支持批量须在目标契约中明确其建议状态，不顺带实现。

输入须由调用方提供符合模型schema的特征，提交标识和时间是上下文，不参与模型拟合；原始Git SHA若未提供，记录使用外部输入ID并声明来源，不能编造真实仓库提交信息。特征类型、名称、顺序、单位、有限值、缺失处理及转换版本需和模型绑定；六字段不能补零升级成14维。服务校验特征文件的结构和数值，不等同于已从源码验证特征的真实性。

公开训练数据中的观测标签独立存放；预测请求不携带评价标签，风险与解释不能从标签生成。模型风险、历史观测标签、解释贡献与用户审查选择在界面和数据设计中分别定义。

后续扩展记录仓库地址＋提交ID自动提特征；它将增加Git读取、diff与历史计算。SZZ属于训练标签构建，不列为每次即时预测的依赖。现有表格未提供源码／diff，不能直接承诺代码序列模型或行级定位。

### D5. 目标设计采用三层结构，技术选型保留确认状态

设计文档分别给出现有架构图与目标架构图。目标图表达职责：多人浏览器入口、React展示层、FastAPI应用与模型服务、集中数据库和版本化文件产物；长训练通过独立执行边界处理。局域网统一入口转发前端与API，数据库和产物由服务端管理；当前只监听127.0.0.1的行为继续作为现状记录。

技术候选的文档表达：

- React／TypeScript／Vite、FastAPI和现有模型产物协议有本项目依据，优先延续；不套用旧Vue页面设计。
- 共享数据库可列PostgreSQL为推荐候选、SQLite为单机受限写入的备选；说明部署／并发／迁移／恢复验证条件，当前项目尚未落库。[SQLite官方适用范围](https://www.sqlite.org/whentouse.html)说明它也可位于应用服务器后端，因此LAN共享本身不足以排除SQLite，选择应核对实际写并发和运维成本。数据库文件不由各客户端通过网络文件共享直接打开。最终选型在对应功能change中冻结。
- 训练执行器与状态管理分开设计：queued／running／succeeded／failed、attempt、重试来源、运行关联及产物校验；不直接继承旧Celery／Redis部署承诺。
- 共享资源为数据集、模型和实验记录；个人清单建议仍按浏览器origin、模式、数据版本与运行隔离。登录、成员角色和跨设备恢复保持待决，不能画出用户／会话表后称已确认。
- LAN访问与写权限单独说明：局域网可访问不自动授予上传、训练或改写公共资源的权限。将最小访问控制列为未来共享服务的设计门槛，认证机制留给功能change；当前API的“本机无鉴权”只描述现状。

模块职责按“系统—模块—功能点”列出。每个模块说明输入／输出、状态、依赖与异常，并对照D3的故事。不能只画架构框图而省略模块间的数据与版本关联。

替代方案是现在锁定旧项目全栈或省略目标架构。前者会引入未确认建设成本，后者无法支撑用户已选择的共享目标；本change提供职责设计及可评审候选，后续按功能增量选型。

### D6. 接口与数据库达到可审查粒度，保留当前兼容性

**接口材料：**

- 现有唯一产品HTTP接口为`GET /api/review-batch`，记录契约版本1、historical模式、数据／运行／模型来源、summary及完整records；保留真实503／500及`error: {code, message}`。当前应用关闭了Swagger／OpenAPI地址，配套YAML是离线文档，不是已上线接口页面。
- 目标API清单覆盖数据集注册／质量查询、schema查询、实验创建／状态、模型查询、JSON预测、CSV上传、解释查询、比较／趋势和报告。每项有编号、模块、方法／路径、入参与出参、返回状态、鉴权建议、调用方和故事引用。
- `docs/api/openapi.yaml`使用OpenAPI3.1，逐operation标记`x-implementation-status: implemented`或`planned`，既有接口保持原响应，目标契约明确为待实现草案。示例与正式模型结果分开。
- 全局错误码文档集中定义码、含义、状态、是否已实现与处理方式；OpenAPI和主设计引用同一名称，不在各接口重复定义冲突码。
- 预测详情必须关联输入批次／记录、modelId、featureSchemaVersion及runId；解释附方法、背景、贡献方向和pending／ready／failed状态。摘要与风险来自不同运行时拒绝拼接。

**数据设计：**

以公开数据集和外部特征记录为起点，候选逻辑实体为dataset、dataset_version、input_record、feature_schema、feature_vector、label_observation、experiment_run、model_version、prediction、explanation、task_attempt及artifact_manifest。可合并有充分理由的实体，但ER关系和字段表必须一致。

数据库概要使用鸦爪ER图；详细表说明字段、类型、空值、主外键、唯一约束、索引、版本关系与必要事务。数据文件、权重和大报告放受控文件产物目录，数据库存引用、hash、状态和元数据。ready状态需对应完整且校验通过的产物，失败重试有独立attempt；个人浏览器清单不强行纳入共享数据库。

没有原始文件改动数据时，不从旧设计复制file_change、issue或SZZ归因表并假称可填充。需要这些对象的后续功能change另行扩展模型。

### D7. 保留实验事实，定义可测量的质量目标

新文档引用`backend/DATA.md`、`backend/PROTOCOL.md`和历史报告，不重定义旧基线的分区、阈值、纳入或评价规则：原始26,855条，纳入12,374条，train／validation／test为8,669／1,852／1,853，当前六字段与固定模型保持原状。

完整Kamei14的规范字段为`ns, nd, nf, entropy, la, ld, lt, fix, ndev, age, nuc, exp, rexp, sexp`，依据[Kamei等原论文的变更度量章节](https://posl.ait.kyushu-u.ac.jp/~kamei/publications/Kamei_TSE2013.pdf)。现有CSV无lt；发布者脚本的rexp是Reviewer experience，arexp是Relative author experience，不能直接当近期作者经验。当前ent的定义未经重建，不静默改名就称等价。目标文档应列每个字段的语义、来源／映射状态和缺口；新的完整方案依赖可核验公开数据，不以填零、猜列名或新增未授权采集管线补救。

旧文档与当前协议还有实际差异：旧成本候选为max(1,LA+LD)，当前用原始LA+LD；旧effort排序候选为风险密度，当前按风险排序；旧Precision退化处理与当前null＋原因规则也不同。保留当前`Recall@20%LOC (risk-ranked)`准确命名，Popt等新指标单独描述候选协议，不覆盖旧结果。时间切分不自动证明历史标签当时可得；预测解释不等于缺陷因果证明。

至少两项非功能需求采用“环境／数据／样本／方法／目标／证据”的结构，建议性能、可靠性为核心，易用性与共享访问控制补充。性能阈值与客户端／模型范围必须标为待验证目标；可靠性包括损坏产物拒绝、失败重试、成功版本保护和多客户端读取同一版本；现有两视口与键盘证据按原日期引用。无数据时不填已达标结论，也不承诺深度方法一定提高效果。

模型组合和解释方法根据可获得输入描述。表格路线不能把任意排列的度量当自然时间序列；语义模型所需源码／diff是独立的数据前提。本文不复制旧训练预算或开启昂贵试验。

### D8. 文档验收采用内容映射与只读检查

| 检查 | 通过条件 |
|---|---|
| A1 结构 | 两份主文档覆盖D2所有模板主体；占位样例清除；模板原件hash不变 |
| A2 范围 | 三项用户确认方向准确；已有、待建、建议、待决可辨；Git自动提取明确后续 |
| A3 故事 | 至少20条唯一核心业务故事；Epic／Feature关联明确；每条有价值、优先级、状态、正常和异常验收，并映射界面／模块 |
| A4 证据 | 当前能力有源码／主规格依据；真实数据与效果引用保存报告；访谈、审批及性能没有伪造；课程原文与项目取舍分开 |
| A5 契约 | API清单、OpenAPI、全局错误码和模块说明相互一致；现有与计划状态可定位；目标schema不会污染现有六字段契约 |
| A6 数据与图 | ER图、字段表、主外键及产物关联一致；流程和时序覆盖成功与失败；LLM图有工具、原始任务提示词及依据记录 |
| A7 质量与计划 | 至少两项非功能需求有可执行验证设计；Sprint按课程阶段组织，日期与责任人没有虚构；计划不勾成完成 |
| A8 导航与兼容 | 主文档及README链接有效；当前规格、模板、旧项目、已归档实验和运行配置保持原状 |

apply时使用一次性只读检查验证Markdown结构、链接、故事ID和验收覆盖、OpenAPI语法／本地引用；具体JSON／YAML工具使用现有可用环境，不为文档安装产品依赖。人工阅读两份文档和图源核对语义。结构检查是文档技术验收，不替代用户／团队内容审核。

本轮propose执行当前change的严格校验、artifact状态和改动范围检查即可。不会调用会写证据的完整产品测试，也不会冻结／归档当前change。

## Risks / Trade-offs

- [完整目标被误认成现有产品] → 现状／目标架构分别表达；接口有实现状态，需求有已有程度；当前运行说明不改成LAN教程。
- [模板修订演变成整套功能实现] → tasks仅为文档编写和验证，后续运行能力另开change。
