# Design

## Context

现有数据集由采集或导入脚本生成，清洗规则固定；管理页只展示质量统计，没有配方、预览、派生版本和导出。版本名必须是 `<数据集>-<起始日>_<结束日>[-8位哈希]`，描述文件会校验版本中的起止日期等于数据实际范围。参见 proposal.md。

## Goals / Non-Goals

**Goals:**

- 清洗配方可预览、可哈希、可复现。
- 派生版本不可变，能追溯到来源版本和逐条去留原因。
- 对比和导出只读取已保存数据。

**Non-Goals:**

- 不实现交互式逐行编辑或在线数据标注。
- 不修改来源版本，也不自动用派生版本替换训练数据。
- 不实现训练分区的类别加权或采样；该能力另立变更。

## Decisions

**配方是规范化 JSON。** 配方包含版本、规则列表（规则标识与参数）和目标 schema。服务端按固定字段顺序序列化并计算 SHA-256；未知规则、参数越界或 schema 不兼容直接拒绝。相同配方得到相同哈希，作为幂等键。

**预览在内存中完成。** 预览读取来源 CSV，按规则顺序计算保留与排除、各规则命中数、缺失变化、正例比例和时间范围，并返回有界数量的排除样例；不写文件、不登记版本。大文件按现有行数上限保护，超限明确失败。

**派生版本沿用现有命名和登记规则。** 版本名使用 `<数据集>-<派生后起始日>_<派生后结束日>-<配方哈希前 8 位>`，其中数据集名沿用来源版本，起止日期使用派生数据实际范围；描述文件增加 `derivedFrom` 与 `curation`（配方、哈希、生成时间）。这样既满足 `VERSION_PATTERN`，也满足 `build_manifest` 对版本时间范围的校验。

**逐条去留原因写旁车。** 派生 CSV 只包含保留记录；逐条去留原因写入 `*.curation.jsonl` 旁车，描述文件记录其哈希和条数。相同来源与配方已存在时直接复用，不重复生成。

**对比与导出只读。** 对比读取两个版本的描述文件、质量统计和旁车汇总，按 schema 与来源关系判断可比性；导出把 CSV、描述文件和去留旁车打包，附哈希清单。两者都不重新执行清洗。

**权限沿用管理会话。** 所有清洗接口要求管理员会话；普通用户和未登录请求不披露数据集内容。

## Risks / Trade-offs

- [大 CSV 预览耗时] → 使用既有行数上限和流式统计，超限明确失败；预览结果不缓存为正式版本。
- [派生版本和旁车占用磁盘] → 版本不可变、不自动清理；管理员可看到谱系后再决定是否导出。
- [派生后时间范围变化导致版本名与来源不同] → 版本名按派生数据实际范围生成，来源关系放在描述文件，不塞进版本名。
- [配方规则与 schema 演进不兼容] → 配方记录 schema 与规则版本，旧配方在新 schema 上明确拒绝。

## Migration Plan

1. 派生版本沿用现有数据集登记表，不新增来源版本表；旁车文件与描述文件一起发布。
2. 既有数据集、训练任务和模型不受影响；不自动生成派生版本。
3. 回滚时停止提供清洗接口并恢复旧代码；已生成的派生版本保留，不删除来源版本。
