# Design

## Context

项目分析已有独立任务、不可变提交结果与模型身份，更新需要复用这些事实，不能通过浏览器轮询冒充持续采集。动机见 proposal.md。

## Goals / Non-Goals

**Goals:** 后端运行期间持续检查；新版本只创建独立分析；失败、重启及模型选择可恢复。

**Non-Goals:** Webhook、毫秒级推送、自动训练及覆盖历史分数。

## Decisions

1. 在迁移011持久化检查开关、分支、模型、时间、观察 HEAD 与任务关联，迁移012增加窗口及上限。相较页面定时器，服务端调度能在关闭页面后继续。旧仓库按需创建关闭状态，避免升级触发未请求的大批分析。
2. 使用有时限、非交互的远端 HEAD 检查及独立进程所有权；新 HEAD 才进入原分析队列。按仓库复用检查，并在入队前再次确认是否已有分析，避免重复执行。
3. 首次绑定实际模型，后续不重新选默认；指定固定 SHA 的 PR 分析不更改项目跟踪分支。窗口和提交上限允许用户调整，保持采集器超限即失败的语义。
4. 保存观察到的 HEAD 和实际分析 HEAD，去重以成功分析的实际 HEAD 为准。失败与取消不推进成功状态；检查租约过期可重试。

## Risks / Trade-offs

- 定时检查存在延迟 → 页面声明频率和后端运行条件，保留立即更新。
- 活跃仓库超过窗口上限 → 显示原因并允许修改范围，不截断或覆盖数据。
- 原模型停用或损坏 → 保留固定选择及旧结果，显式重新选择后才切换。
- 多个部署进程可能重复恢复原分析任务 → 维持现有单后端进程部署约束。

## Migration Plan

停止当前部署后端，使用 SQLite backup 保留数据库及模型产物，再执行 catalog-init 至012。升级保留原记录并新增空表；不自动开启旧仓库。回退前另行备份新数据，恢复原库及对应代码，不让旧代码直接读取新库。验证证据见 `docs/审计/2026-10-27-pr-review-journey.md`。
