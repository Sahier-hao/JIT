# Design

## Context

动机见 [proposal.md](proposal.md)。现有 `commit-analysis.yml` 在 Linux 上导入固定模型并产出分析报告，不执行回归。后端依赖和契约检查依赖分别位于 `backend/requirements.txt` 与 `backend/scripts/requirements-contract.txt`；前端和扩展均有锁文件与测试脚本。浏览器配置使用 Windows Python 路径及 Edge，并已有独立数据库、端口参数和运行证据目录。现状依据见 [计划依据](../../../docs/审计/2026-11-15-next-changes-baseline.md)。

## Goals / Non-Goals

**Goals:**

- PR 获得清晰的关键回归反馈，主分支获得定期完整回归与浏览器验收。
- 干净检出可以准备全部必需夹具，失败仍有可定位日志。
- 原提交风险报告继续独立运行，回归状态只表达工程检查结果。

**Non-Goals:**

- 不配置部署、仓库分支保护、合并策略或 PR 评论。
- 不把风险分数变成质量门禁，不在 CI 重采真实远端仓库或做大型模型训练。
- 不承诺本轮完成 Windows/Linux/macOS 全平台矩阵。

## Decisions

### 1. 新建独立回归工作流

新增 `regression.yml`，PR 与 main 推送运行关键层，`workflow_dispatch` 及每日 UTC 19:00（北京时间次日 03:00）运行完整层。PR 使用候选合并版本检出并记录实际 SHA；不沿用风险分析工作流只检出 base 的方式。不同层使用独立并发组；新 PR 提交可取消同 PR 旧运行，不能相互取消定期完整检查。

首次采用 Windows runner 完成后端及浏览器检查，复用现有路径和 Edge 配置，避免将流水线建设扩成浏览器全平台重构。Python 先沿用现有 CI 的 3.12，Node 使用满足仓库锁定工具链要求的受支持主版本并在工作流明确固定。记录 runner 镜像、Git、Python、Node、浏览器和实际包版本。新环境如存在真实兼容问题需修复并留证，不能当作已验证支持。

### 2. 将检查范围列为显式清单

关键后端覆盖模型包、冻结分析身份、切分、训练任务、用户与管理权限、项目分析和 PR 更新的现有测试；实施时在统一清单中列出具体文件与必要用例，日志输出选择列表与实际收集数量，空清单失败。前端执行 `npm ci`、类型检查、完整单元测试和构建；扩展执行 `npm ci` 与 `npm test`。各独立检查拥有各自失败状态，不能用管道最后一个命令掩盖前一步退出码。

完整层执行后端全部测试及上述前端、扩展检查，并显式运行模型包恢复与项目分析到 PR 续审的浏览器旅程。使用现有专用 Playwright 配置，串行执行共享全局状态的用例；列出每个配置及测试文件，不能仅运行默认配置后称所有专用旅程都已验收。与新 change 相关的成熟准入和账户切换旅程在合入后加入清单。

关键检查以可维护的风险边界为依据，不以固定通过数量为目标；新增测试正常增加数量。完整套件暂定 90 分钟超时，关键与浏览器步骤分别有明确时限，根据实际首轮耗时修订并记录，不能通过放宽断言或重复跑到通过掩盖失败。

### 3. 干净环境准备与夹具可移植

Python 安装声明版本的 CPU PyTorch，再安装后端和契约依赖；前端及扩展通过各自锁文件安装。依赖缓存可加速下载，但一次性数据库、模型状态和测试结果不可跨运行缓存复用。

先在独立检出中运行，识别测试对未跟踪数据或开发产物的依赖。用仓库已有固定模型包、受哈希保护的公开数据与确定性 Git 夹具在运行目录中准备副本；不能上传个人 SQLite、依赖本机 `artifacts`，也不能把缺夹具直接改为 skip。需要少量测试模型时使用已有小型构造及固定参数，不能将 CI 变成正式实验训练。

浏览器服务继续使用 `reuseExistingServer: false`、显式端口与独立数据根目录。输出进入每次运行独立的临时根，清理只针对本次拥有且核验位于运行根内的路径和进程。不停止占用默认端口的其他会话。

### 4. 保留终态和失败产物

统一运行摘要包含提交、触发、层级、各命令、测试数量、退出码、跳过与失败原因。pytest 输出 JUnit，前端与扩展保留结构化结果或原始日志，Playwright 保留失败截图、trace 和服务日志。收集/上传步骤使用失败后仍执行的条件，但测试命令本身不得 `continue-on-error`。

超时和取消不生成通过摘要；能收集到的部分日志标明不完整。工作流摘要与实际各 job 状态一致，上传失败另行说明，不能覆盖先前测试失败。运行输出遵循 `verification-evidence` 保护，显式冻结才写本次 `docs/evidence/`。

### 5. 最小权限与实际验证

使用普通 `pull_request` 与只读仓库权限，无部署密钥或私有服务依赖；不使用特权事件运行 fork 代码。回归与风险报告使用不同状态名称和并发组。

先验证 YAML、脚本、干净检出和故障注入，在具备仓库权限时观察一次真实 PR 关键检查。新工作流的定期和手动入口依赖其先进入默认分支，因此首次远端完整运行列为合入后跟进；合入前执行完整层的本地等价链，不冒充远端验收。远端无法执行时记录具体权限或环境阻塞；实际 fork 触发未验证时明确保留该边界。

## Risks / Trade-offs

- [完整套件耗时及共享 runner 波动] → 分层反馈、独立时限与日志，保留性能预算原断言。
- [测试隐含依赖开发机文件] → 干净检出先暴露依赖，受校验夹具取代，缺少必需输入即失败。
- [Windows runner 与本机版本不同] → 记录环境并实际验证；不宣称未运行平台支持。
- [新 change 增加专用测试] → 合入后更新检查清单并运行集成回归，避免长期只跑旧文件。

## Migration Plan

1. 增量添加回归工作流及准备脚本，先保持现有风险报告工作流及仓库设置不变。
2. 在干净检出准备隔离运行根，验证首次执行和再次执行，不污染正式数据。
3. 推送后核对可触发的关键运行及失败日志，默认分支首次合入后跟进完整远端运行；实际执行记录置于 `docs/审计/`，远端阻塞单列。
4. 若需回退，只停用新增回归工作流或撤回其代码；保留已产生的诊断与所有正式数据，不更改分支保护。
