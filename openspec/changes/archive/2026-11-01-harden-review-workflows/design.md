## Context

仓库同步已经按 `HOLDOUT_DAYS = 90` 计算训练截止时间，`choose_model` 也用它统计可训练样本，但实际训练调用没有把截止时间传给 `build_run`，因此时间切分会把近期提交一起纳入训练。`build_run` 已支持 `holdout` 并记录 `holdout.epoch` 与 `trainableRecords`，缺的是共享执行器和同步调用链的透传。

「分析全部 PR」当前只读取 `pr_cache` 中已发现的开放 PR，在单个后台循环里逐条刷新，任何异常都被 `continue` 吞掉，返回的 `queued` 是候选缓存数量。它无法覆盖未缓存的 PR、无法区分复用与失败，也没有批次身份可供前端读取，服务重启后状态消失。

单 PR/批量 PR 路由不在 `managed_path` 覆盖范围内，`BaselineError` 会落到普通异常分支或 FastAPI 默认响应，用户只看到「服务器内部错误」。管理训练页固定读取前 20 条，返回列表时旧详情仍留在 state，失败后没有真正重新请求。PR 工作单的证据跳转复用了普通版本切换，版本变化副作用会把视图重置为提交列表。

## Goals / Non-Goals

**Goals**

- 训练截止时间贯穿同步编排到产物，实际训练、验证与测试成员与页面统计一致。
- 批量 PR 分析有持久批次、远端完整范围、固定模型、逐条结果、失败重试与重启恢复。
- PR 分析接口错误统一、可定位，并防止后续新增接口漏接。
- 管理训练页和 PR 证据跳转在真实操作序列中可用。

**Non-Goals**

- 不新增模型算法、不自动选择或替换默认模型、不自动向 GitHub 发布评论。
- 不改造个人草稿的存储、备份、恢复和云同步。
- 不实现在线多项目训练编排或管理区报告展示（后续阶段）。
- 不重做已有管理工作区外壳和图表。

## Decisions

### D1 截止时间作为显式训练参数

`TrainingExecutor.run` 增加可选 `holdout`，直接传给 `artifacts.build_run`。仓库同步在采集后按原始记录计算 `max(epoch) - 90 天`，同时用于 `choose_model` 和训练调用。管理员训练不传该参数，保持既有全量切分行为。

产物继续使用 `summary.json` 的 `holdout`（截止 epoch、`trainableRecords`）和 `split.partitions`（各分区数量与时间范围）。不再新增平行的统计口径。近期记录仍进入本次评分输入，但不进入训练、验证或测试分区。

### D2 批次是持久资源，不是一次函数调用

新增 `pr_batch` 与 `pr_batch_item`。批次在创建时解析并写入固定模型；后台工作先从远端分页读取全部开放 PR（直到 `hasMore` 为假），再逐条刷新快照并提交分析。发现失败时保留已发现范围，批次以 `partial` 或 `failed` 结束并记录 `discoveryComplete=false`，不宣称全部完成。

逐条判定顺序：

1. 刷新该 PR 当前快照并读取同快照、同模型的既有分析。
2. 在途任务（排队/运行）→ 复用任务。
3. 已成功任务 → 复用结果。
4. 同快照、同模型的失败、取消或中断任务 → 用户本次显式发起，允许创建重试。
5. 无匹配分析或快照变化 → 创建新分析。

批次和逐条记录只保存来源、模型、快照与任务引用，不复制分数。进度接口同时读取 `repository_sync` 当前状态，保证排队、运行、完成、失败、取消和中断如实显示。

同一项目存在进行中的批次时：相同模型返回该批次，不同模型返回 409，避免重复活动任务。仅重试失败项会以原模型创建新批次，并记录 `retry_of`。

服务启动时把未完成批次标记为 `interrupted`；已提交的分析任务由既有同步恢复逻辑处理，批次不冒充成功。

### D3 错误信封按路由覆盖，而不是按异常类型

把 PR 分析、批次进度和重试路由加入 `managed_path`。新增测试遍历 `create_app` 注册的 `/api/v1` 路由，要求全部由 `managed_path` 覆盖（显式允许列表除外），新增路由遗漏时测试失败。错误响应继续使用 `{error: {code, message, requestId, details?}}`，不返回堆栈、令牌或内部路径。

### D4 页面状态随对象身份重置

管理训练页以 `taskId`、分页参数和重试计数驱动请求；`taskId` 变化时先清空旧详情再加载。失败和轮询失败保留明确的重试动作，重试通过递增重试计数实际发起请求。分页使用服务端 `limit/offset` 与 `total`。

PR 工作单用单独的「证据跳转」标记区分版本切换：跳转后把视图设为文件页并定位到证据文件与行号；版本不存在或文件不可读时保留原版本和位置，显示原因，不切换到其他版本。

## Risks / Trade-offs

- 批量分析逐条刷新快照会按 PR 数量产生远端请求和文件下载；沿用现有单 worker 顺序执行，避免放大并发与限流风险，但大批量会耗时较长。进度以逐条状态暴露。
- 批次表只保存提交结果，不保存分析分数；前端需要同时读取批次进度和现有 PR 列表。这样避免重复数据源，但进度接口要多读一次任务状态。
- 远端发现中途失败时仍处理已发现的 PR，可能低估范围；批次明确标记 `partial` 且前端不得显示「全部完成」。
- 训练截止时间依赖窗口内最新提交；若采集上限截断最新提交，截止时间随实际采到的最新提交变化。这是现有窗口语义，产物会记录实际 epoch 供核对。

## Migration Plan

- 新增迁移 `019_pr_batches.sql`，只新增 `pr_batch`、`pr_batch_item` 及索引，不改既有表。
- 升级前按现有流程备份 `backend/storage/catalog.sqlite3`；`catalog-init` 前向应用迁移。
- 旧项目没有批次记录，前端显示「尚无批量分析」，不影响既有 PR 列表和单条分析。
- 回退需停止新后端并恢复升级前数据库与代码。
