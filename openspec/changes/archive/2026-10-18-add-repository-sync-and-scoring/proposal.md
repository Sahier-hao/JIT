# Proposal

## Why

系统当前只能用发布者预先算好的 OpenStack 历史快照做回放：`backend/jit_baseline/collect.py` 已经能从真实 Git 仓库采集提交、计算 Kamei 14 维特征并生成简化 SZZ 标签，但这条能力只存在于命令行，采集产物从不落库，界面也没有任何"接一个仓库"的入口。结果是系统外观像评审工具，实际面对任何真实工作仓库都不可用，评审员与课程验收无法在系统内证明它能处理自己的提交。

本 change 把已有采集器接成一条从界面可完成的最小通路：填仓库地址 → 同步 → 得到可打分的提交列表，并在工作台如实标明数据来自哪个仓库。

## What Changes

- 侧栏新增「数据来源」入口：表单填写仓库地址、分支、起始日期、提交上限，提交后创建一次同步作业。
- 服务端新增同步作业：克隆仓库 → 采集提交与标签 → 登记为新数据集版本 → 决定用哪个模型打分 → 对窗口内提交打分；作业有明确状态与失败原因，客户端可查询进度。
- 打分模型由用户选择，默认「自动」：训练窗口的提交数与正例数达标时用该数据集训练一个模型；不达标时降级使用特征口径兼容的既有模型，并在结果上注明降级原因与该模型未在此仓库验证。用户也可以强制选择只用现成模型或强制训练，强制训练时结果页必须如实给出训练区样本数与波动风险。
- 工作台新增数据源切换与来源标识，新增「仓库同步」这一来源类型，与公开数据集回放、人工演示并列展示且不可混用。
- 同步产出的模型进入模型目录，标注其来源数据集版本、同步作业与可预测范围，不覆盖既有模型身份。
- 首版只做**手动触发、整仓全量、单进程执行**：不做定时同步、不做增量、不做 webhook、不做多仓库混排。
- 复用既有采集规则与登记入口，不新增特征算法、标签算法或模型方法。

## Capabilities

### New Capabilities

无。本 change 不引入新的系统行为类别，而是在既有采集、目录与评审能力上补齐「服务端同步作业」与「来源可切换」。

### Modified Capabilities

- `repository-collection`: 新增服务端同步入口（RCL-07）、同步作业生命周期与可操作失败（RCL-08）、同步产物串联打分并按数据量决定是否训练（RCL-09）；既有 RCL-01~06 的采集规则不变。
- `model-catalog`: 新增同步训练所产出模型的登记与来源要求（MC-07），明确自动训练不改变 MC-01~06 的准入、身份与可用性规则。
- `commit-risk-review`: `CRR-01` 增加「仓库同步」来源类型与数据源切换；`CRR-09` 清单隔离上下文扩展到仓库数据集版本。

## Impact

- **后端**：`backend/jit_baseline/api.py` 新增同步作业与数据源查询接口；新增作业编排模块，包装既有 `collect.py`、`store.py`、`catalog_storage.py`、`model.py`；`storage/catalog.sqlite3` 需要迁移新增同步作业表。
- **前端**：新增数据来源页面与同步状态组件；`App.tsx` 工作台增加来源徽章与数据源切换；`AppShell.tsx` 导航新增一项；`useDataset.ts` 增加仓库数据加载器。
- **契约**：`docs/api/openapi.yaml` 新增同步作业创建、查询与数据源列表路径，并修正 `/api/v1/datasets` 已实现却标为 planned 的状态。
- **数据**：首次真正产出 `kamei14-git-v1` 数据集与对应运行，`backend/data/datasets` 与 `backend/artifacts` 增加该来源的目录；OpenStack 既有版本保持不变。
- **测试**：新增同步作业正常/失败/幂等/并发用例，工作台来源切换与清单隔离用例；既有 25 个后端测试与 19 个前端单测不得回归。
- **限制披露**：仓库同步数据必须沿用 `RCL-06` 的两项限制（提交级聚合、简化 SZZ），且新提交无标签的事实必须在界面标注。
