## Goals / Non-Goals

**Goals:**
- 用一个客户端应用承载规格中的完整交互，让数据处理、清单状态和页面展示可以分别验证。
- 演示来源与示例风险贯穿界面，后续接入真实来源时通过明确的规格变更调整，不能仅替换几个常量就声称已完成真实预测。
- 让每项规格场景可关联到自动化结果或实际浏览器验证证据。

**Non-Goals:**
- 业务范围之外的内容见 proposal；本设计不为未来后端选择框架、数据库、任务队列或部署架构。
- 不提前定义整个项目的表结构、业务 API 或20个故事。此原型的行为契约仅覆盖当前能力，不能作为课程完整需求基线。

## Decisions

### D1. 单个 React + TypeScript + Vite 客户端

进入 apply 后在 `frontend/` 创建独立客户端，使用 npm 和单一 lockfile。首轮只有工作台及清单视图，详情为侧面板，视图切换由应用状态管理，不引入路由、全局状态库、图表库或整套管理后台组件。

选择理由：当前的状态主要是搜索、日期、排序、选中提交与清单；组件化有利于共享加入状态，TypeScript 有利于区分缺失分数、无效分数和有效分数，Vite 提供本地运行及静态构建。官方 React 文档提供 Vite + TypeScript 的起步路径，同时提示从头构建的路由和数据读取责任；本次范围有限，可以承担这些责任。

| 替代方案 | 实现成本与取舍 |
| --- | --- |
| 原生 HTML/TypeScript | 初始依赖更少，但列表、详情与清单之间的状态同步和后续演进需要更多手工组织。 |
| Vue + TypeScript + Vite | 同样可满足范围；本次没有已确认的 Vue 技能优势，因此选用 React 作为提案默认值，可在 apply 前整体评审调整。 |
| Next.js 或服务端全栈框架 | 当前没有服务端渲染、公开内容检索或服务端业务需求；会引入本 change 用不到的运行和组织成本。 |

apply 时选取与本机运行时兼容的稳定依赖版本并锁定，记录实际版本，不在本轮安装或猜测精确版本。浏览器启动、依赖下载或测试运行时缺失应作为环境问题单独报告。

参考：[React 从头构建应用](https://react.dev/learn/build-a-react-app-from-scratch)、[Vite 起步与运行时要求](https://vite.dev/guide/)。

### D2. 桌面布局采用“提交表格 + 右侧详情 + 清单视图”

工作台顶部展示项目、数据版本和演示模式；列表工具区承载搜索、日期与排序；主要空间用于提交记录。详情显示完整标识、风险、变更信息、示例因素和清单操作。清单通过独立入口进入，并保留返回工作台前的查询状态。

首次视觉评审后，用户选择浅色开发工具风格：深色导航、浅灰工作区和白色内容面板，蓝色用于操作与选中态，暖色用于示例风险与提醒。正文、记录和关键控件以13至14px字号为基准，标题采用简明的业务名称与无衬线字形；提交标识保留等宽字体。导航、图标、输入框、按钮与详情面板使用一致的间距及轮廓，控制顶部高度，让提交记录成为页面主体。分数附文字，不能仅用颜色表达风险；不增加无关趋势图、模型准确率卡片或虚构统计。使用本机字体回退和自行绘制的SVG界面图标，不引入外部字体或图标依赖。

2026-10-10 首次用户评审明确认为界面不好看。原有功能验证只证明交互行为，不能代替视觉满意度；本次重新打开布局、证据及综合验证任务，保留首次结果，完成视觉返工后重新生成对应源码的测试与截图证据。

替代方案是独立详情页面。侧面板能让评审员同时参考列表排序和单条信息，并减少首轮导航复杂度；代价是小屏空间更紧，本次以桌面视口验收。侧面板需要可关闭、可见焦点和可靠焦点返回，不能让遮罩挡住清单操作。

详情采用独立的可滚动内容区，关闭和加入操作位于内容区外。内容区有明确的区域名称、键盘停靠点和可见焦点；键盘用户可滚动阅读，再继续到加入按钮，并用Escape返回原触发位置。浏览器验收同时验证滚动阅读和加入操作。

### D3. 演示记录与页面解耦

演示数据通过一个可替换的读取边界异步提供；本次实现可以读取应用自带的静态数据，并为测试替换读取结果。该边界不定义未来服务端 API，也不下载公开数据集。

客户端记录只包含目前界面需要的信息：项目与演示版本、唯一提交标识、带时区的提交时间、可选变更行数与文件数、可选度量、风险可用状态以及示例解释。项目与版本、唯一非空标识和可解析的带时区时间为必需信息；重复标识或必需信息错误进入加载失败状态。风险字段按 CRR-03 区分有效、缺失和无效，可选信息缺失不会使整条提交不可用。

原型默认提供12条固定示例记录，使用 `demo-0001` 一类可识别的演示标识和虚构的“演示项目”，不伪造真实仓库提交链接。记录包含同分、0和1边界、暂无预测、缺失度量与解释等情况；额外的无效数据仅用于自动化故障注入。示例内容来源说明随数据提交，不带真实缺陷标签，不随机生成分数，不运行假训练逻辑。

替代方案是在各页面直接写死显示内容。这会使详情、列表和清单容易出现不一致，也难以注入失败场景；统一记录能用完整标识关联各视图，而不是依赖行位置。未来真实数据接入还需核对提交信息、标签来源与时间划分，不能把演示字段当作公开数据集已具备的字段。

### D4. 查询、选择与数据独立维护

搜索、起止日期、排序、当前视图、详情提交标识、清单标识集合分别维护；原始记录不因排序或清单操作改写。列表通过已应用查询条件派生，清单按加入顺序从全量有效记录解析，详情始终按完整标识定位。

日期按 Asia/Shanghai 的日界线解释，起止均包含当日；出现无效范围时显示修正提示并保留最近一次有效查询结果，清除筛选恢复有效状态。风险排序将有效分数排在前面，同分使用时间与标识稳定打破并列；没有有效分数的记录之间也按时间与标识排列。时间排序同时间按标识升序。保留原始数值供排序，仅在展示时格式化，避免舍入造成错误顺序。

替代方案是各组件单独保存状态。它更容易出现“详情已加入，但列表仍可加入”以及排序后打开错误提交的问题；集中管理当前交互状态，组件通过操作入口更新即可，无需额外状态库。

### D5. 清单存入同一浏览器的 localStorage

这是本提案新增的建议默认值；采用版本化且包含项目和演示数据版本的存储键，只保存提交标识及加入顺序。加载时验证数据格式，去重并排除当前数据中不存在的标识；损坏或不支持的内容显示恢复失败提示。不同版本自然使用不同键，不迁移或覆盖其他版本的清单。

读写失败时保留本次内存清单，显示刷新后可能丢失的提示；不删除其他应用记录，不把存储成功当作跨设备持久化保证。清单不作为真实缺陷标签、评审通过结论或训练样本来源。

替代方案：仅内存状态最省实现，但刷新会丢失审查选择；服务端账户同步能跨设备，但需要身份与服务端数据层，超出当前目标。localStorage 满足同浏览器个人使用，代价是浏览器清理、隐私模式或不同应用地址会影响恢复。本 change 不承诺多标签页实时同步。

### D6. 以行为测试和桌面运行证据验收

建议使用 Vitest 验证查询、数值边界、清单唯一性和存储恢复行为；使用 Playwright Chromium 验证完整用户链路及键盘交互，不以组件快照或 CSS 类名测试代替用户行为。端到端测试覆盖固定的两个桌面视口，不扩展成全浏览器或移动端矩阵。

自动化故障通过测试替换数据读取和存储边界，不增加面向评审员的“故障模拟”产品菜单。还需查看实际截图，确认表格、详情、清单和错误提示可读可用。参考：[Vitest](https://vitest.dev/guide/)、[Playwright](https://playwright.dev/docs/intro)。

| 规格 | 验证方式及证据重点 |
| --- | --- |
| CRR-01、CRR-02 | 演示标识与字段呈现检查；缺失来源失败、可选信息缺失；工作台、详情与清单截图。 |
| CRR-03 | 有效边界、缺失、非有限及越界数值的行为测试；UI 文字和百分比一致性。 |
| CRR-04、CRR-05、CRR-06 | 空白及大小写搜索、无结果、清除筛选、日期边界与无效范围、风险同分和缺失排序。 |
| CRR-07、CRR-08 | 列表打开详情、保持查询、加入清单、重复加入、移除、空清单和返回正确详情的完整链路；不存在标识的异常反馈。 |
| CRR-09、CRR-10 | 刷新恢复、版本隔离、坏记录、未知标识及存储拒绝后的本次操作与警告。 |
| CRR-11 | 加载中、空数据、读取失败、重复标识、无效必需字段与成功重试。 |
| CRR-12 | 两个桌面视口的完整操作与截图；键盘打开、加入、关闭及焦点返回；文字状态提示。 |

apply 后将运行证据索引放在 `docs/evidence/build-desktop-review-workbench-prototype/acceptance.md`，记录日期、提交或工作区状态、Node与依赖版本、演示数据版本、实际命令与退出状态、测试结果、截图路径、规格场景映射和未解决问题。当前不创建该报告，不填写已通过状态。

本原型选择易用性与恢复可靠性作为质量验证方向，证据分别对应 CRR-12 与 CRR-09至CRR-11。这里只能证明原型范围内的结果，不代表整个最终系统的非功能验收。

## Risks / Trade-offs

- [示例分数被当成真实预测] → 所有视图保留演示标识，示例记录有来源说明；验收检查措辞，不输出真实模型效果结论。
- [未来数据集字段或标签信息不足] → 首轮只使用有明确定义的演示记录，后续独立核验提交标识、时间、14维特征、标签可用时间和复现条件，再修改相关增量规格。
- [清单本地保存被误当成账号同步] → 明确同浏览器、同地址与同版本边界，并验证失败降级，不加入登录模块。
- [窄桌面布局与侧面板互相遮挡] → 用两个目标视口实际运行和截图检查，必要时缩减装饰与列宽，优先保证操作完整。
- [结构校验或构建成功被当成验收] → 执行完整链路、异常场景和桌面检查，并保留证据映射；失败项目不打勾、不归档为完成。
- [原型完成被当成课程完整 MVP] → 报告明确交付级别；真实数据、训练、评价与推理需要后续独立验收。

## Migration Plan

本项目没有既有应用或数据迁移。apply 获得明确指示后创建客户端与测试，锁定依赖，在本机运行及构建，并整理验收证据；本 change 不发布外部站点。实现有问题时可恢复本 change 的应用文件和演示数据，但不能清理其他应用的浏览器记录。

功能验收与规格校验通过后，整理待归档依据并报告给用户；获得归档指示时使用相应 OpenSpec 工作流，同步增量规格到主规格再归档。首轮 proposal 不写主规格、勾选实施任务或自动进入 apply。

## Open Questions

- 演示项目文案、字体资产和图标细节可在 apply 时细化，不改变规格行为及任务范围。
- 真实数据集、模型和正式解释方法是后续 change 的独立规划事项；本 change 不暗示其已经选定。
