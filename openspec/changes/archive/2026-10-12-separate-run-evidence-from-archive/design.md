# Design

## Context

动机见 [proposal](proposal.md)。影响方案实现的现状：

- 证据路径 `docs/evidence/connect-public-data-baseline-review/` 硬编码在 9 处，跨 Python、TypeScript 与 PowerShell。
- 该目录同时是**跨测试通信通道**：`backend/tests/test_http_lifecycle.py` 写出 `runtime-context-fixture-batch.json`（629 KB），`frontend/e2e/historical.spec.ts` 读取它。这条通道是有意设计的，`historical.spec.ts` 中有注释说明该载荷由真实 TCP 模型服务产生。
- `frontend/scripts/verify.ps1` 是唯一的全链路编排入口，已经在采集时间戳、git 状态、源码哈希、依赖版本与每项检查退出码，并且已经读一份手工维护的 `protected-files.json`（38 项）做哈希比对。
- 该保护清单覆盖的是**更早一代**的归档证据与规格文件，没有覆盖它自身所在 change 的证据。
- 证据目录进入版本控制；`frontend/test-results/`、`frontend/playwright-report/` 已在 `.gitignore` 中。

## Goals / Non-Goals

**Goals:**

- 让测试与验证运行**在物理上**无法写入任何归档证据目录。
- 让归档证据只由一次显式冻结产生，并自带可重新校验的完整性清单。
- 让冻结产生的清单**不依赖手工维护**，消除"落后一代"。
- 保持跨测试夹具通道继续工作，不改变任何测试的断言语义。

**Non-Goals:**

- 不重写、不搬迁、不重新冻结两个已归档 change 的证据内容。
- 不保留多次运行的历史；运行工作区只保留最近一次运行。
- 不把证据索引从 change 改为 capability，也不做证据条目与规格场景的自动映射。
- 不自动触发冻结。
- 不引入新的运行时依赖或工具链。

## Decisions

### D1. 运行工作区固定在 `docs/evidence/_run/`，证据与夹具用子目录区分

`_run` 与归档目录同级，便于冻结时做一次目录拷贝；`_` 前缀让它稳定排在归档目录之前，且不会与任何 kebab-case 的 change 名混淆，读到时不会误认为是某个 change。运行工作区加入 `.gitignore`。

工作区内部按用途分层，避免冻结时靠人工维护纳入清单：

```
docs/evidence/
  _run/                      <- 运行期，可覆盖，不提交
    <证据文件>                <- 默认全部纳入冻结
    fixtures/                <- 运行期夹具，冻结时排除
  <change-name>/             <- 冻结后，提交
    <证据文件>
    冻结清单.json
```

**替代方案**：用 `.freezeignore` 或显式纳入清单——都要人工维护，且漏项时不会有任何提示；目录约定的纳入规则是自解释的。用仓库根的 `.run-evidence/`——与归档目录相隔较远，冻结拷贝跨目录树，且不易被发现。

### D2. 路径在每一侧各定义一次，不以环境变量作为默认

后端在测试包内定义一个证据根常量，前端新增一个共享模块导出运行工作区与夹具目录常量，三个 e2e 规格从该模块导入；`verify.ps1` 已在第 5 行集中定义一次，只需改这一行。

**替代方案**：用 `EVIDENCE_DIR` 环境变量、默认指向运行工作区——看似灵活，但它把"指错就写坏归档"的可能性重新引入，正是本 change 要消除的东西。若将来确需覆盖（例如 CI 指定输出），再以显式参数加入，且不接受指向归档目录的值。

### D3. 冻结做成后端子命令，复用现有哈希与 JSON 工具

在 `backend/jit_baseline/cli.py` 增加子命令，与已有 `verify`、`compare` 并列。理由：`artifacts.py` 已有 SHA256 计算与 JSON 原子写入的实现，`cli.py` 已经是本项目的验证工具入口，复用成本最低，且不需要新增顶层目录结构。

**替代方案**：新增顶层 `scripts/freeze-evidence.py`——角色更清楚，但为一个子命令引入新的顶层结构，收益不足。放进 `verify.ps1` 作为开关——会把"全链路跑一遍"和"冻结一次运行"两件不同的事混在一个入口里。

### D4. 受保护位置用运行前后自动比对，取代手工快照

`verify.ps1` 在开始与结束时各计算一次受保护位置的哈希集合——已归档 change 的证据目录、`openspec/specs`、`openspec/changes/archive`、`openspec/config.yaml` 与 `frontend/public`——不一致即失败并逐项列出差异。

这取代了原先的 `protected-files.json`。那份清单是 2026-10-10 手工拍的快照，覆盖范围与本轮选定的受保护位置一致（28 项证据、2 项主规格、6 项已归档 change、`config.yaml` 与 `demo-dataset.json`）。但 10-11 归档时主规格被合法同步，快照没有跟着更新，于是此后每次验证都会在这一步失败——只是因为脚本更早的一步先抛了异常，这个失败一直没露出来。手工快照与它要保护的内容之间必然存在这个时差，换成本次运行的实际状态作为基准后时差就不存在了。

**替代方案**：重拍一次快照——改动最小，但下一次合法同步主规格时会以同样的方式再次过期，而且同样可能被别的失败长期掩盖。改用 git 状态交叉检查——git 已经是这些文件的变更检测机制，但脚本要回答的是"运行期间有没有东西写进来"，而不是"工作区相对 HEAD 有没有改动"，两者不等价。

### D5. 移除对已归档 change 的规格校验

`verify.ps1` 第 52 行校验的是 `connect-public-data-baseline-review` 这个已归档 change。同一脚本第 51 行已按 `--specs --strict` 校验全部主规格，覆盖了真正持久的东西。保留该行会为归档的、不再变化的 change 反复出报告，其结论随时间只增不减地失去意义。

### D6. 一次改完，不保留新旧双轨

9 处路径在同一轮内全部改到运行工作区，旧路径不再被任何代码写入，文档同步更新。

**替代方案**：新旧并存一段时间——会让"证据到底在哪"产生歧义，且归档目录一旦仍被写入，本 change 的目的就没有达成。

### D7. 就绪检查容忍启动竞态

有两处把"还没就绪"误判成了失败。

一是 `wait_ready` 只用 `(OSError, TimeoutError)` 判定"尚未就绪"。被等待的 uvicorn **先绑定端口、再完成应用启动**：这个窗口里连接可以建立而响应正文为空，`json.load` 抛 `JSONDecodeError` 不在捕获范围内，直接冒泡成检查失败而不是继续重试。实测在完整测试套件下约 1/8～1/3 概率复现。

二是浏览器回归里 reload 之后直接拿"某一行按钮的状态"当就绪判据。1853 行表格在并发下不总能在默认 5 秒内渲染完，断言于是报 `element(s) not found`。同一个测试另外两处 reload 后的断言都写了 10 秒，只有这一处漏了。实测约 1/4 概率复现。

两处按同一原则修：把"等待就绪"与"断言行为"分开，等待留出与已完成工作量相称的时限；真正超时仍按原样失败并指出目标。理由：运行记录里的失败必须表示真实缺陷，否则整份证据不可信；而且这两项检查即将进入 CI，随机变红会让流水线失去意义。

**替代方案**：固定等待一段时间——掩盖竞态而非容忍它，还拖慢每次运行。要求服务侧在就绪后才绑定端口——属于被检查服务的改动，超出本 change 范围，且覆盖不了另一处界面渲染的竞态。

## Risks / Trade-offs

- [有人忘记冻结，归档目录没有本次证据] → 冻结是归档前的显式步骤，写入 tasks；完整性比对会指出归档快照与运行结果不一致，而不是静默通过。
- [运行工作区被误提交] → `.gitignore` 规则；同时运行工作区内的文件不进入任何归档清单。
- [前端三处 e2e 各自定义路径导致不一致] → D2 收敛到一个共享模块导入。
- [夹具迁移后前端读不到] → 夹具与证据的目录分层在 D1 固定，两侧按同一约定写读；完整验证会实际执行该链路。
- [冻结是拷贝，可能覆盖归档目录里的既有内容] → 冻结只写入本次纳入的条目，并在报告中列出被写入的路径；不删除目标目录中未纳入的文件。
- [本轮改动集中在路径与工具，若有遗漏不回滚归档证据] → 本 change 不修改任何已归档证据；验证会比对归档目录哈希，若变动即失败。

## Migration Plan

1. 增加 `.gitignore` 规则与运行工作区约定。
2. 9 处路径改为运行工作区；夹具迁入 `_run/fixtures/`，前后端两侧同步。
3. 增加冻结子命令与冻结清单格式。
4. `verify.ps1` 增加归档目录前后比对；移除第 52 行。
5. 更新引用证据路径的文档。
6. 运行一次完整验证，确认两个已归档 change 的证据目录哈希不变。
7. **回滚**：改动只涉及路径常量、新增冻结工具与校验逻辑；还原这些文件即可。已归档证据在本 change 中从未被写入。

## Open Questions

- 证据索引是否从 change 改为 capability——取决于后续是否要长期回答"这条规格要求现在还被证明着吗"，与本轮的信息隔离目标正交。
- 两个已归档 change 的证据目录没有冻结清单（早于本机制），它们的完整性目前依靠 git。是否为存量归档补一次冻结，另行判断；不做也不影响本轮的隔离与新增冻结。
