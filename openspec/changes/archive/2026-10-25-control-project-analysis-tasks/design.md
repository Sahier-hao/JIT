# Design

## Context

现有分析记录保存请求、实际模型与成功结果，单 worker 顺序执行。Git 命令、训练和推理都可能阻塞；Python 线程不能安全强制终止。动机与行为范围见 proposal.md。

## Goals / Non-Goals

**Goals:** 将执行寿命与 HTTP 服务分离，以持久取消请求和事务检查保护终态及成功视图；使队列、取消和原参数重试在项目页连续可用。

**Non-Goals:** 不扩展为分布式队列或多后端实例，不增加训练管理平台，不改变模型策略、采集标签或预测算法。

## Decisions

1. HTTP 服务保留单 worker 调度，但每次标准分析由私有 Python 进程执行，使用同一独立目录库和绑定模型记录。相比仅设置线程取消标志，这能在 Git、训练或推理阻塞时停止任务。测试注入的自定义采集函数保留阶段检查路径，不作为 HTTP 服务运行入口。
2. Windows 使用设置 KILL_ON_JOB_CLOSE 的 Job Object 管理工作进程及后代；POSIX 使用独立进程组。先建立所有权，再通过 stdin 交付配置；服务退出时关闭其拥有的进程树。配置只含路径、任务 ID 和执行选项，不传管理员会话。临时 Git 目录位于本次专属工作目录，结束后清理。
3. 迁移 009 保留旧列顺序，重建带 cancelled 约束的任务表及提交外键表，并恢复数据和索引。增加 started_at、deadline_at 和 cancel_requested_at。相比把取消伪装成普通失败，独立终态可供查询、重试与页面准确显示。
4. 取消与成功发布都在即时写事务中读取当前状态。排队取消立即结束；运行取消先持久化意图，再由监督者停止执行。阶段推进和成功发布同时检查终态、取消请求及截止时间，阻止迟到结果覆盖。相比乐观更新 UI，响应和后续查询决定实际状态。
5. 执行截止从领取任务时计算，包含进程启动与实际工作，排队时间排除。监督者检查退出、取消、截止与服务退出，异常终止保存明确错误码；正常退出停止自有任务，重启恢复不自动重跑。
6. 队列位置按任务入库顺序计算，提交调度在同一服务锁内完成；详情和记录列表共享字段。位置不估计等待时长，开始执行后为空。
7. 项目页使用既有确认样式与轮询展示取消；取消中不开放删除。重试将 UTC 起点转换为日期，将保存的开区间终点减一天恢复为包含式结束日期，保留指定模型与原记录。相比直接填 ISO 字符串，这符合原生日期控件并避免范围逐次扩大。

## Risks / Trade-offs

- 每个任务启动独立进程增加加载开销 → 保持现有单 worker 和真实模型校验；本轮不承诺吞吐提升。
- 取消发生在数据或产物登记之后 → 保留已完整登记的数据及模型，不删除共享资产；未完成产物不被当作成功结果。
- 系统强制结束服务 → Windows Job 关闭释放子树；重启时恢复持久作业状态。POSIX 非正常父进程退出的全局清理不作为本机 Windows 验收结论。
- 多个服务共享同一数据库会破坏单所有者假设 → 维持单实例部署，分布式领取与租约另行设计。
- 历史时间窗口语义不同 → 日期型旧值原样保留，当前标准 UTC 窗口转换为包含式日期并以实际重试响应核对。

## Migration Plan

1. 停止当前部署的自有后端；使用 SQLite backup 保存目录库，保留对应模型与数据目录。
2. 运行 `catalog-init` 应用迁移 009，核对旧任务、提交、模型身份与外键；重复初始化应保持幂等。
3. 部署对应前后端，确认队列、取消、重试和既有结果读取。新字段允许旧记录为空。
4. 回退前停止新后端并另存升级后数据，再恢复升级前数据库与匹配代码；不以旧代码直接读取迁移 009 数据库。

验证范围与实际结果见 `docs/审计/2026-10-25-analysis-task-control.md`。
