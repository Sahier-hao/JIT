# Design

## Context

PR 来源与个人轮次均已按固定版本保存。更新处理需要连接新代码和原工作，而不能改写原轮的判断及交付物。动机见 proposal.md。

## Goals / Non-Goals

**Goals:** 让待复核范围和旧证据可解释；重复检查不重置；交付范围不随远端变化漂移。

**Non-Goals:** 自动解决意见、自动迁移行号、推断作者已修复缺陷及基于分数变化评价修复效果。

## Decisions

1. 更新先读取真实远端版本，相同版本复用来源；新版本为个人工作新增轮次。当前阅读指向保持原轮，用户明确进入新轮。首页状态由个人关注、远端状态、版本和未完成项共同计算。
2. 按文件路径、重命名来源与内容身份比较阅读范围。未变内容保留原阅读出处，变化和基准变化使已读内容待复核；整体或关联变化的问题保留人工状态并单独标记复核。
3. 使用 GitHub 比较结果记录已核对的提交继承关系，读取不到则保留 unknown；不把未知当作连续追加。原位置始终引用原快照，避免不可靠的自动行号迁移。
4. 预览和确认交付时再次检查版本，更新或检查失败时要求明确按旧版本交付。新轮沿用已选模型，但分析、分数和结论分别保存，不能重写原轮。

## Risks / Trade-offs

- 个人工作间隔跨过多个版本 → 相邻服务端快照关系不代表个人两轮关系，无法对应时显示未知。
- 基准更新导致较多内容待复核 → 采用保守提示，不推断此前判断自动有效。
- 远端关闭或合并 → 从活跃队列移入历史，但不修改个人完成状态及草稿。

## Migration Plan

新轮只追加，不覆盖旧轮。旧工作单缺少继承关系或位置元数据时显示未知并继续提供原来源；完整备份恢复仍按当前冲突规则执行。验证见 `docs/审计/2026-10-27-pr-review-journey.md`。
