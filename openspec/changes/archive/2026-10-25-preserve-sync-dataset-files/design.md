# Design

## Context

采集登记已有内容哈希后缀、描述文件原子写入与数据库导入幂等，原始 CSV 的写入发生在冲突判断之前。相关行为契约见 repository-collection 的 RCL-05，动机见 proposal.md。

## Goals / Non-Goals

**Goals:** 不改动已存在的 CSV 字节；新文件的完整发布先于描述登记；保留现有元数据和导入冲突恢复。

**Non-Goals:** 不迁移数据库、不重命名已登记版本、不删除既有产物、不新增管理员操作。

## Decisions

1. 先比较已有 CSV 与本次字节。相同则复用，不同则把当前候选作为版本冲突并尝试既有内容哈希后缀；相比先覆盖再验证，这能在失败时保留旧版本。
2. 新 CSV 写入同目录 UUID 临时文件后，通过硬链接原子创建正式名称。目标已存在时重新比较字节，最后移除本次临时文件。相比 `replace`，该操作不覆盖并发创建的目标；相比直接独占写正式文件，读者不会看到写到一半的正式文件。
3. CSV 发布后继续调用既有描述登记及数据库导入，两者的 DATASET_EXISTS 仍进入版本冲突分支。不把元数据变化仅按原始 CSV 哈希认作同一登记事实。

## Risks / Trade-offs

- 文件系统不支持硬链接 → 明确返回数据集不可用，不退回可能覆盖旧文件的写法；当前 Windows NTFS 路径已通过实际采集验证。
- 写临时文件期间强制结束进程 → 可能留下未引用的 `.tmp` 文件；正式 CSV 保持完整，登记扫描不把临时文件作为数据集。
- 内容哈希候选也冲突 → 明确拒绝并保留原版本，不覆盖或无限尝试。

## Migration Plan

随后端代码部署，无数据迁移。回退代码不改动既有 CSV 或描述文件；回退后不应使用旧发布路径写入冲突版本。

验证范围与实际结果见 `docs/审计/2026-10-25-analysis-task-control.md`。
