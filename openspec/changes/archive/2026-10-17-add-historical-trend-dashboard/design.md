# Design

## Context

现状与约束（细节见 proposal.md 的 Why，规格见 `specs/`）：

- `run` 生成 9 个产物文件：`source.json`、`split.json`、`test-input.json`、`test-labels.json`、`model.joblib`、`reference-predictions.json`、`metrics.json`、`summary.json`、`manifest.json`。
- 服务只读其中 6 个（`SERVICE_FILES`），并明确**不读** `test-labels.json` 与 `reference-predictions.json`（`backend/README.md`「本机 HTTP」一节）。
- `runId = identity(config)`，`config` 含训练代码 8 个文件的哈希、核心文件哈希、schema、方法超参与环境声明；`summary.json` 不在核心文件集合内，其哈希单独记在 manifest。
- `Snapshot.load()` 是服务与校验**共用的准入**，负责字段顺序、身份、数量与模型可加载性检查。
- 产物必须**自足**：跨机器校验（PDB-15/PDB-17）不能依赖本机存在源数据目录，因此校验只能读运行目录内的文件。
- 前端 `frontend/src/historicalContract.ts` 对每条记录断言不得出现 `label`／`title`／`explanation`；`summary.split[*].positiveCount` 已提供按分区的观测标签聚合。
- 前端运行时依赖只有 `react` 与 `react-dom`，图表与图标均为手绘 SVG（不打包外部资产）。

## Goals / Non-Goals

**Goals:**

- 提供可核验的历史观测与模型风险趋势：聚合在离线产生、随运行记录供给、可被校验约束。
- 服务继续保持"不读测试标签"，逐条标签不出现在任何响应中。
- 既有运行零破坏：不重跑也不改写的旧运行仍按自身声明通过校验并被正常供给。
- 前端不为趋势引入新的运行时依赖，且不改变既有视图与契约行为。

**Non-Goals:**

- 不做预测解释（归因）、不做多方法比较与报告导出、不新增 HTTP 端点。
- 趋势是**回顾性观测**，不构成在线缺陷率或未确认缺陷的结论。
- 不修改 `records` 的字段集合与语义，不把标签带进记录。

## Decisions

### D1 聚合在离线 `run` 阶段产生

**选择**：`run` 在完成解析、分区与评价后，用手中的全量标签计算时间桶聚合并写入产物；服务只读这份无标签的聚合。

**替代方案**：服务在请求时读 `test-labels.json` 现算。它能让既有运行立刻可用，但会让服务首次读取标签文件，破坏 `backend/README.md` 明写的性质，并使"聚合"与"逐条泄漏"之间只剩代码自觉；`verify` 也覆盖不到它。

### D2 聚合承载在 `summary` 的可选键

**选择**：聚合放在 `summary` 的固定可选键 `summary.trendBuckets` 中（结构见 D10），随既有的免凭据 `/api/review-batch` 一起返回。

**已知后果（决定 DTD-01 的措辞）**：趋势与工作台取自**同一次响应**，因此不存在"摘要可读而批次不可用"的状态——服务端的失败是整请求 503，前端的解析失败同样是一次性的。趋势视图因此只承诺"不要求先打开工作台、不要求团队凭据"这一层可达性，不承诺数据层面的独立可用。

**替代方案**：独立产物文件 + 独立端点。职责更清晰，但要么把趋势挂到 `/api/v1`（需要团队 Bearer 凭据，与"历史回放免凭据"的既有体验割裂），要么另开一个 `review-*` 端点（多一套错误码与测试面），还要引入"可选产物集合"机制。当前需求只有一种聚合，`summary.split[*].positiveCount` 已是同类先例，因此选择零新增面的方案；将来聚合种类变多时再抽独立文件。

### D3 桶粒度按月，边界取界面时区

**选择**：按固定 UTC+08:00 的月边界分桶，桶数约 27，覆盖全部纳入记录（2011-11 ~ 2014-02）；产物记录粒度标识与时区，界面按同一时区展示桶起止。

**替代方案**：周桶（2011—2012 早期月份样本稀疏，比例噪声大）；UTC 月边界（与界面既有"同一时区呈现"的约定不一致，用户看到的"12 月"会错位）。

### D4 最小样本阈值与空值形态

**选择**：桶内提交数低于运行声明的阈值（默认 20）时，该桶比例记为 `null` 并附原因，形态与既有 `{value, reason}` 指标一致；校验按该形态比对，不把空值当 0。

**替代方案**：直接展示比例（稀疏桶会出现 0% 或 100%，把图读成"缺陷率极低"）；省略稀疏桶（图上出现时间缺口而不说明原因）。

**执行位置**：这条联动由**产出端与校验端**保证——`build_trend_buckets` 直接产出空值，`validate_structure` 拒绝"样本不足却给出比例"以及"含测试记录却没有风险分布"的聚合。前端只校验 `{value, reason}` 互斥，不重复施加跨字段约束，避免比产出端更严而误拒合法产物。

### D5 序列分层：观测覆盖全量，风险只覆盖测试区间

**选择**：样本数与观测正标签比例覆盖全部纳入记录；风险分布（中位数与高分位）只出现在冻结测试区间。

**理由**：模型只对测试分区做过推理；对训练分区推理属于拟合内表现，项目明确不拿它充当效果（PDB-04）。

### D6 校验范围：测试区间逐条重算 + 全量守恒核对

**选择**：校验对**测试区间**的时间桶用 `test-labels.json` 与重算风险逐条重建并比对；对全量与各分区做**守恒核对**——各桶样本数之和等于纳入行数、正标签数之和等于观测正例数、按分区归并后与 `split` 的分区统计一致。

**替代方案 A**：要求全量逐桶逐条重算。**不可行**：产物只保存测试分区的逐条标签（`test-labels.json`），训练与验证分区只有聚合统计。
**替代方案 B**：新增全量标签产物文件以便逐条重算。**被否**：产物为 12,374 条标签会显著增大，且与"只有测试批次需要答案文件"的既有最小自足设计相悖；源 CSV 虽被哈希锁定，但校验按 PDB-15/PDB-17 必须能在没有源数据的机器上完成。
**代价**：训练与验证桶的正确性由"运行身份 + 守恒关系"约束，而不是逐条重算。这一点在规格与设计里如实记录。

### D7 供给哪个运行由启动配置选择

**选择**：新增环境变量（如 `JIT_RUN_DIR`），默认仍为既有固定运行目录；指定的目录 MUST 走同一个 `check_files` + `Snapshot.load` 准入。

**替代方案**：目录交换（把新运行改名为固定目录，旧运行移走备份）——零代码，但破坏"目录即该运行"的直觉且容易留下半成品；给 `run` 加 `--force` 覆盖——与"拒绝覆盖已存在运行目录"的既有原则冲突。

### D8 前端接入方式与校验边界

**选择**：新键按**存在性驱动**解析（与既有 `featureSchema` 形态判定同一模式）：缺少该键即视为"该运行未提供趋势聚合"；结构或取值不合法则判趋势视图不可用。图表手绘 SVG，并同时渲染承载同一数据的文本视图。

**校验边界（必须遵守）**：该键的解析与校验 MUST 与工作台的批次解析**分离**——`parseHistorical`／`parseEnvelope` 不校验该键，也不因它失败；趋势视图走独立解析路径（如 `trendContract.ts`）校验它。否则一个坏聚合键会让整个工作台变成"数据不可用"，与 CRR-11／CRR-14 的立场冲突，也与 DTD-02 的"不扩大失败范围"场景矛盾。

**替代方案**：把趋势塞进 `records`（被 `historicalContract.ts` 的断言直接拒绝）；引入图表库（违反项目"不打包外部资产"的既有惯例，且增加依赖面）；把校验并入 `parseEnvelope`（省一个文件，但会扩大失败范围）。

### D9 运行身份与新旧并存

**选择**：接受"改训练代码即产生新 `runId`"这一既有语义。新运行带聚合键，旧运行不带；两者都能通过各自声明的校验，可并存供给（由 D7 切换）。归档证据不改写；报告里引用的旧 `runId` 不再能逐字节重现，但数值应一致——`backend/tests/test_artifacts.py` 的 `test_rebuilt_six_field_run_still_matches_the_archived_evidence` 只比对 `datasetVersion`、`features`、`split.test.count` 与指标数值，不比对键集合，因此既有的这条回归在加键后仍成立（同时它也是"旧运行不受影响"的现成证据）。

### D10 聚合键的线上结构（冻结）

**选择**：`summary.trendBuckets` 固定为以下形状，供后端产出、前端解析与 e2e 契约用例共同引用：

```json
{
  "grain": "month",
  "timezone": "UTC+08:00",
  "minSample": 20,
  "buckets": [
    {
      "start": "2011-11-01T00:00:00+08:00",
      "end": "2011-12-01T00:00:00+08:00",
      "commits": 143,
      "positives": 21,
      "observedRate": { "value": 0.1469, "reason": null },
      "byPartition": {
        "train": { "commits": 143, "positives": 21 },
        "validation": { "commits": 0, "positives": 0 },
        "test": { "commits": 0, "positives": 0 }
      },
      "risk": null
    }
  ]
}
```

**理由**：一个自然月可能同时包含验证分区与测试分区的记录（分区边界是具体时刻，不是月初），所以"每桶一个分区标签"并不成立。改为**按分区分别记录**样本数与正例数，既让 D6 的守恒核对精确，也让"风险只覆盖测试记录"有明确落点。`observedRate` 沿用既有 `{value, reason}` 形态；`risk` 只在该桶含测试记录时存在，为 `{count, median, p90}`，否则为 `null` 并附原因（`minSample` 阈值同样作用于风险分布）。

**替代方案**：每桶只记一个总数（无法做分区守恒核对，也无法说明风险序列到底覆盖了桶内哪些记录）；把桶边界切在分区边界上（破坏"自然月"这一用户可读粒度）。

**连续性的归属**：桶的首尾相接（含零提交的月份）由**产出端**保证——`build_trend_buckets` 在首尾之间逐月补齐空桶——并由 `validate_structure` 校验。前端只要求"升序且不重叠"，不强制严格相接：规格没有固定"缺口语义"，若前端更严，一旦上游按别的口径产出就会把整份聚合判为不可用（DTD-02 的"不扩大失败范围"）。

### D11 趋势视图的取数方式

**选择**：趋势视图复用 `useDataset` + `historicalLoader`，独立请求同一个 `/api/review-batch`，与工作台之间**不共享缓存**——与既有"路由切换即重新取数"的行为一致。已知代价：该响应含 1,853 条记录（约 368 KB），而趋势视图只需要 `summary`，因此会重复下载一次。加载中、失败与重试沿用同一套状态与文案，不新增取数语义。

**替代方案**：新增 summary-only 的查询参数或端点（被 proposal 的"不新增端点"约束排除）；把工作台已取到的数据提升为跨路由共享状态（会改变既有路由与加载语义，收益只是省一次本机请求）。

## Risks / Trade-offs

- [改动管线代码改变 `runId`，前端清单上下文随之切换] → 这是文档化的既有行为；提供 D7 切换以新旧并存，并在交付说明中写明重跑命令。
- [全量观测聚合无法逐条重算] → 明确记录其约束方式（运行身份 + 守恒核对 + 测试区间逐条重算），不把它说成"完全可重算"。
- [`summary` 体积增长] → 约 27 个月桶、每桶数十字节，量级可忽略。
- [风险序列只覆盖测试区间，可能被误读为其它区间无风险] → 图例与文字明确标注分区范围，并在限制说明中保留"回顾性评价"表述。
- [前端解析新键导致旧运行报错] → 存在性驱动 + 缺少即"未提供"；新增针对"无聚合键运行"的回归测试。
- [新环境变量被指向未校验目录] → 复用同一准入校验，失败时明确拒绝并给出可定位原因，不退回原运行冒充成功。
- [按月桶在极端稀疏月份仍不可读] → 阈值化空值 + 原因文字 + 文本视图中逐桶可读。
- [训练与验证分区的桶无法逐条重算，理论上可在保持合计不变的前提下被改动而不被发现] → 如实记录该残余：它们只由运行身份与守恒关系约束，不宣称"完全可重算"；测试分区的桶逐条重算，且任何改动 `summary` 的行为都必须同时改写 manifest 中记录的哈希。
- [趋势键的解析若与工作台耦合，会扩大失败范围] → D8 的校验边界 + DTD-02 的"不扩大失败范围"场景 + 专门用例（"坏聚合键时工作台仍可用"）。
- [趋势视图重复下载整批记录] → 记录为已知代价（本机约 368 KB，复用既有加载态）；不为此新增端点或跨路由缓存。

## Migration Plan

1. 后端实现分桶与摘要写入、校验重算与守恒核对、运行目录选择；补单元测试。
2. 用本机已就绪的数据重跑 `run` 到**新目录**（无需网络），再对新旧运行分别执行 `verify`。
3. 通过 D7 的配置把新运行供给服务（默认行为不变），重启服务验证响应中包含聚合。
4. 前端实现趋势视图与契约解析，跑 `typecheck`、`test` 与既有 e2e（两视口、仅键盘、无障碍）。
5. 证据与文档：两视口截图、无障碍与性能记录、运行产物摘要写入 `docs/evidence/_run/`，再按既有冻结流程归档；同时同步产品文档里趋势视图的状态与界面说明（见 tasks 第 5 组）。

**回滚**：不设置 D7 的配置即回到原固定运行（既有行为）；前端改动可独立回退，此时趋势视图对无聚合键的运行显示"未提供"，其余视图不受影响。

## Open Questions

- 空值桶在图形上的表达方式（断开线段还是留空槽位）——不改变规格与任务拆分，实现时确定。
- 最小样本阈值是否需要按运行可配置（当前设计为随运行声明、默认 20）——实现时按声明读取即可，后续可按需扩展。
