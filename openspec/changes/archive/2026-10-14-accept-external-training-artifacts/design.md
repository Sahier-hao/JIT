# Design

## Context

动机与规格见 [proposal](proposal.md) 与 [public-data-baseline](specs/public-data-baseline/spec.md) 增量。当前实现里，跨机器的阻塞集中在四处：

| 位置 | 现状 | 跨机器时的后果 |
| --- | --- | --- |
| `artifacts.py:46` `environment()` | 记录**本机** python／platform／包版本 | 记录的是校验机的环境，不是训练机的 |
| `artifacts.py:61-64` `check_environment` | 要求 `python`、`platform` **全等** | 产方平台不同即硬失败 |
| `artifacts.py:68-77` | 声明的包必须在**本机**安装且版本相同 | 校验声明了 `torch` 的运行要求本机也装 torch |
| `artifacts.py:250` `joblib.load` | pickle 直接反序列化 | 加速设备上序列化的产物在本机不可加载（D-001 同类） |

另有两条结构性事实：

- `compare_runs`（`artifacts.py:309-312`）对非 `tolerance` 口径**直接拒绝**，使声明了独立协议的深度方法无法参与任何数值比较。
- 仓库层面的既有约定是**产物不入 Git**：`.gitignore` 忽略 `backend/artifacts/` 与 `backend/data/`，README 写明"正式模型和源文件不入 Git，使用命令重新取得"。这条约定的**前提是产物可由命令在本机重现**。
- `config["sourceCode"]` 已按上一 change 的 D6 降级为**溯源记录**（`check_files` 不再要求与当前文件逐字节相同）。因此产方在其检出上产生的训练代码指纹**不会使本机校验失败**，跨机器这一点无需再改。

约束：既有运行的产物、复现与归档证据不得被重写；`GET /api/review-batch` 的响应契约与前端行为不变；`Snapshot.load` 的 `isinstance(model, Pipeline)` 与 `n_features_in_`／`classes_` 检查面（`artifacts.py:251`）继续是加载校验的依据；团队协作走 `feature/` 分支 + PR + 非作者审阅（`docs/团队分工.md:251-252`）。

## Goals / Non-Goals

**Goals:**

- 让"训练机器"与"校验机器"可以不同：产方环境成为溯源记录，准入改为行为化校验。
- 让一份外部产物能在**无加速设备**的机器上被校验、加载、重算并如实记录来源。
- 使外部产物**经仓库既有流程**进入本链路，不另造投递协议。
- 使校验**可由任一席位在任一台机器**上执行。
- 整个过程可在**无 GPU** 的机器上设计与验证。

**Non-Goals:**

- 不引入深度学习框架、不训练、不登记真实深度方法（本 change 只把契约与路径打通）。
- 不做设备映射适配层（不替产方把加速设备上的产物"救"回 CPU）。
- 不新增打包、传输、签名或投递协议。
- 不改服务所用的运行，不改 `api.py` 与前端契约。

## Decisions

### D1. 环境声明拆成"产方训练环境"与"本机验证环境"

`config["environment"]` 一词两义（"谁训练了它"与"凭什么能在这校验它"）是本次的核心病灶。拆为：

- **产方训练环境**：产方如实声明（平台、Python、框架与版本，若有加速设备则声明）。**仅作溯源**，本机不做等值判定。
- **本机验证环境**：校验时由本机记录，用于审计。

**备选与否决理由**：(a) 沿用单一 `environment`，把全等改成"包含"——仍要求产方声明的包在本机存在，等于要求校验机装齐训练机的框架，正是要避免的；(b) 只删平台与 Python 检查、保留包检查——留下"本机必须装 torch"这一条同样致命；(c) 拆成两个语义并分别记录——采纳。

### D2. 准入改为行为化：能否加载 + 重算是否落回参考

外部运行的准入从"环境相等"改为两件事：**模型在本机实际加载成功**，且**用交付的无标签输入重算的风险落回交付参考的声明口径之内**。

**理由**：能加载在语义上**蕴含**"运行所需的依赖被满足"——装的包不够，模型就加载不了。因此对**外部**运行，PDB-11 的包含关系是冗余的，可以退成纯溯源；对**本机**运行，PDB-11 原样保留（保护既有运行）。这也让"环境声明"回归它真正的性质——是描述，不是判据。

**备选与否决理由**：保留包级包含检查作为额外闸门——挡不住真正的不兼容（包版本都对但 ABI 不同的模型照样崩），却会挡住合法产物，收益为负。

### D3. 交付产物必须设备中立，由产方负责

契约要求交付的模型能在**无加速设备**的机器上加载；产方负责以设备中立形态交付（保存前映射到 CPU，或交付可在 CPU 重建的形态）。本机**不**做设备映射适配。

**理由**：其一，D-001 的教训是"产物**在加载它的那台机器**上能否加载必须被独立校验"，本 change 把这条做成显式契约；其二，当前加载路径是 `joblib.load`，pickle 无法注入设备映射参数，"本机适配"要先另立一条非 Pipeline 的加载与校验分支，成本高且绕不开。设备中立由产方保证，本机**只验证不修补**，与本项目"校验不匹配必须失败、不静默修补"的既有立场一致。

**备选与否决理由**：(a) 本机识别框架并 `map_location="cpu"`——见上，加载路径不支持且引入永久适配负担；(b) 强制把一切包装成 sklearn `Pipeline`——不解决问题，pickle 里的加速设备张量照旧失败。

### D4. 交付走仓库既有流程，不新增投递／接收协议

外部产物以 `feature/` 分支 + PR 进入仓库，与其它工作一致：产方在 PR 中说明方法与产方环境，由非作者席位审阅。校验**复用既有的 `verify`／`compare` 入口**，按运行自身声明的**来源**（本机产生／外部产生）分派行为，**不新增独立的"收包"命令**。

**理由**：团队已经用分支 + PR + 评审协作，产物经仓库流动天然可评审、可追溯、可回退；再造一套打包与收包协议会把同一件事做两遍，并**绕开 PR 评审**——而评审正是本项目的过程证据（`docs/团队分工.md:18`：过程实践 40 + 测试实践 40 = 80 分考的是证据，不是代码）。

**备选与否决理由**：新增专门的接收命令与投递格式（如 tarball + 校验清单）——在 git 已经提供传输、版本与评审的前提下，它只增加一条旁路；且"接收"这个动作在仓库工作流里就是 `verify` 已有的语义。

### D5. 外部产物在仓库中的位置与版本控制：给"不入 Git"的约定开一个受控例外

既有约定"产物不入 Git"的前提是**产物可由命令在本机重现**。GPU 产物在本机无法重现，前提不成立，因此需要**显式例外**：外部产物放在仓库中一个**受控的、纳入版本控制**的路径（与既有被忽略的本机运行目录分开），`.gitignore` 只放开该路径。

**本项已确认为仓库策略**：外部产物纳入版本控制；`backend/artifacts/` 与 `backend/data/` 的既有忽略规则**保持不变**（它们仍是"可由命令重现"的本机状态）。

**理由**：若不入库，产物在本机既取不回、也无法在 PR 中被审阅，本 change 的核心价值（可评审、可追溯、任一席位可校验）就落空了；而当前模型很小（sklearn joblib，KB 级），纳入版本控制没有实际代价。

**备选与否决理由**：(a) 只提交"配方 + 校验值 + 存放位置"，产物从外部存储取回——本机无法重算意味着该存储必须先存在，且产物不可评审，等于把问题推迟并新增一个跨机器分发机制；(b) Git LFS——当前体积不需要，留作将来深度模型变大时的评估项（见 Open Questions）。

**风险与缓解**：深度模型可能显著大于当前模型。→ 缓解：本 change 的路径与体积无关；若将来超过约定阈值，改用 LFS 或外部存储只影响该路径，不影响校验行为。

### D6. 运行标识沿用产方声明，不重算

外部运行的 `runId` 沿用产方声明，本机只校验其**自洽**（`identity(config) == runId`），不重算。

**理由**：`runId = identity(config)`（`artifacts.py:143`）而 config 含环境；若本机重算，会用**本机验证环境**算出一个**不同的** runId，产方与校验方再也对不上同一次运行，溯源断裂。沿用它并与 PDB-19 的来源标记配合，才是可追溯的。

**风险与缓解**：沿用产方声明意味着运行标识不可信为"未篡改"。→ 缓解：校验 `identity(config) == runId` 的内部自洽，并另记**本机验证环境**与校验来源；不宣称该标识具有抗篡改性质（签名不在本 change 范围）。

### D7. 数值口径接到校验上，且不挡深度方法

校验的比较**读取该运行声明的方法所声明的复现口径**（PDB-14 已有机制），不套用统一容差。当前 `compare_runs` 对非 `tolerance` 口径直接拒绝，因此校验路径**不能整段复用**它：需按其声明分派，或让 `compare_runs` 支持分派。

**理由**：GPU 训练有随机性，同一产物重算都可能超出 1e-8；若写死容差，深度方法一进来就被挡。产方需为随机初始化的方法声明独立协议（锁定环境 + 固定种子 + 结构一致 + 指标容差）。

**本 change 边界**：不登记真实深度方法，"按声明分派"以现有方法（数值容差）与测试夹具覆盖；独立协议的**具体形态**留待 GPU change 冻结。

### D8. 修 `environment()` 的崩溃，并登记一个 `requires` 非空的方法

`environment()` 里 `version(name)` 未捕获 `PackageNotFoundError`，使"登记一个需要额外依赖的方法"一旦被 `run` 使用即抛出未归类异常（`cli.py:64` 只接 `BaselineError`／`OSError`）。修法：把该异常归一到带稳定错误码的领域错误。同时登记一个 `requires` 非空的方法，使这条**至今从未被走过**的路径有实际对象。

**备选与否决理由**：只修崩溃、不登记新方法——该路径仍无真实使用者，回归只能靠夹具构造，容易与实际登记时暴露的问题脱节。两者都做。

### D9. 校验不绑定机器，也不绑定人

校验必须**在任一席位的任一台上（无加速设备的）机器上得到一致判定**，不依赖产方机器、也不依赖某台机器上预先存在的本机运行产物。

**理由**：本项目是共享仓库，评审者是**非作者同学**（`docs/团队分工.md:252`）。若校验结果依赖产方机器或某人的本地状态，"非作者评审"就无从执行，过程证据也站不住。

**落地**：校验只依赖仓库内容（含纳入版本控制的外部产物）与该机器的运行环境；校验输出只写运行工作区 `docs/evidence/_run/`（VEV-01），不进归档、不改产物。

## 协作与仓库约定

本 change 把"谁产出、谁校验、谁审阅"写清，避免死板地按单人仓库设计：

| 角色 | 席位 | 在本次交付中的职责 |
| --- | --- | --- |
| 产方 | GPU 席位 | 在 GPU 机器上训练；**报告**方法标识、冻结超参与其产方环境；以设备中立形态保存；开 `feature/` 分支提交产物 |
| 校验方 | 本席位（算法与实验） | **登记**方法条目（`algorithms.py` 的模型注册表属本席位，见 `docs/团队分工.md:105-115`）；在无 GPU 机器上按 PDB-15～PDB-19 校验；维护契约与错误码 |
| 审阅方 | 任一非作者席位 | 按 `docs/团队分工.md:252` 审阅 PR，意见与修改留在 GitHub |

**方法条目由本席位登记，产方只提供方法与超参**——避免同一件事在两处各自登记而漂移；这也与"具名方法清单"的既有归属一致。

需要与 GPU 席位对齐的三条（均为**仓库内的约定**，不是投递协议）：

1. **以分支 + PR 提交产物**，提交的是整个产物目录（`manifest.json`、`model.joblib`、`test-input.json`、`test-labels.json`、`reference-predictions.json`、`metrics.json`、`source.json`、`split.json`、`summary.json`）。校验需要全部文件，裁剪会破坏 PDB-15 的完整性校验。
2. **环境如实声明**：登记真实训练环境（框架、版本、有无加速设备）。**不得**为让本机校验通过而省略依赖——那会使声明与运行身份不一致（PDB-16）。
3. **设备中立交付与复现口径**：保存前映射到 CPU（PDB-17）；随机初始化的方法自带独立复现协议，不套用 1e-8（PDB-18）。

## Risks / Trade-offs

- [环境语义放宽后放过真正的不兼容] → 缓解：准入改为行为化（**实际加载 + 重算落回**），比"包版本相等"更接近真实不兼容；PDB-17 的"不得以声明代替加载"直接针对这一点。
- [外部产物纳入版本控制后仓库膨胀] → 缓解：当前模型为 KB 级；体积阈值与 LFS／外部存储的切换留作专项（见 Open Questions），且不影响校验行为。
- [外部运行被误当本机运行供服务] → 缓解：PDB-19 的来源标记；服务加载外部运行时的行为需显式，不静默当作本机运行。
- [沿用产方 runId 可能被伪造] → 缓解：校验内部自洽并另记校验信息；**明确不宣称**抗篡改。
- [改动既有运行的行为] → 缓解：PDB-11 的放宽只影响"更松"，既有四项运行不受影响；D8 只新增错误处理，不改既有错误码语义。
- [校验依赖某个人的本机状态] → 缓解：D9 把"只依赖仓库内容 + 该机器运行环境"写成约束，并由 PDB-15 的"任一席位与任一台机器一致判定"场景覆盖。

## Migration Plan

1. 先修 `environment()` 崩溃并登记 `requires` 非空的方法（D8），确认该路径不再崩溃且既有运行不受影响。
2. 再做环境语义拆分（D1、D2）与按来源分派校验（D4），以本机既有运行的校验回归确认为"只松不紧"。
3. 确定外部产物的受控路径与 `.gitignore` 例外（D5），并写明交付流程（协作与仓库约定一节）。
4. 再接本机可加载（D3）与按声明口径重算（D7），补无 GPU 的失败分支回归（D9）。
5. 最后文档（PROTOCOL、README、团队分工、缺陷记录）与端到端验证。

**回滚**：新增的外部产物目录与 `.gitignore` 例外可直接还原；既有运行与 `docs/evidence/` 全程不被写入，回滚不涉及已冻结证据。

## Open Questions

- 外部产物在仓库中的**具体路径名与体积阈值**，留待实现时与 GPU 席位商定；不影响规格与任务分解。
- 校验记录（本机验证环境、校验来源、时间）放在产物内还是运行工作区，实现时按"不覆盖产方声明 + VEV-01 只写运行工作区"的约束确定。
