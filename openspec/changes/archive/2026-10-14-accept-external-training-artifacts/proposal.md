# Proposal

## Why

GPU 席位在**另一台有 CUDA 的机器**上训练深度模型，产物要回到这条链路里。本项目是**四个席位共用的 Git 仓库**，协作走"`feature/` 分支 → PR → 至少一位非作者审阅 → 合入受保护的 main"（`docs/团队分工.md:251-252`）。因此**产物的交接通道就是仓库本身**，不需要另造打包、投递或"收包"协议——那会把同一件事做两遍，还绕开了评审。

真正的卡点在**校验**。链路从生成到校验都假设"训练、校验、服务在同一台机器"：`environment()`（`artifacts.py:46`）记录的是**本机**环境，`check_environment`（`artifacts.py:53`）却把它当**准入条件**——要求平台与 Python **全等**、声明的每个包在本机以相同版本安装。一份在 Linux+CUDA 上训练、声明 `torch` 的运行，在本机（Windows、无 torch）**永远无法通过校验**。

还有一条既有约定在跨机器时不成立：**"正式模型和源文件不入 Git，使用命令重新取得"**（`backend/README.md`、`.gitignore` 忽略 `backend/artifacts/`）。这条对**本机可重算**的产物是对的——克隆仓库后跑 `cli run` 就能重现同样的模型。但 GPU 产物**在本机无法重算**（没有加速设备），于是：既进不了仓库，又取不回来，还进不了 PR 评审。这条约定需要一个**显式例外**，否则 GPU 产物无处分发。

同一分工还带来与已登记的 **D-001 同类**的失效：`Snapshot.load` 以 `joblib.load` 直接反序列化模型（`artifacts.py:250`），在 CUDA 上序列化的张量在无 GPU 机器上加载即失败。D-001 的教训正是"产物**在加载它的那台机器**上能否加载必须被独立校验，不能假定"。

启动时机：**登记一个 `requires` 非空的方法这条路径从未被走过**（两个已登记方法的 `requires` 都是空的），而 `environment()` 在声明的包未安装时**未捕获 `PackageNotFoundError`**，一旦登记即崩溃。这是 GPU 席位登记深度方法的直接前置。

## What Changes

- 明确**外部训练产物经仓库既有流程交付**：以 `feature/` 分支 + PR 进入，与其它工作一致；**不新增打包／投递／接收协议**，不新增独立的"收包"命令——校验复用既有的 `verify`／`compare` 路径。
- 为外部产物确定**在仓库中的受控存放位置与版本控制策略**：为"无法在本机重算"的产物给出显式例外，改动集中在 `.gitignore` 的一个受控路径，并在 README 与团队分工写明交付流程。
- **BREAKING**（仅内部契约）环境声明拆成两个语义：**产方训练环境**（溯源，本机**不做等值判定**）与**本机验证环境**（校验时记录）；准入由"环境相等"改为**行为化**——能否加载、重算是否落回声明口径之内。
- 交付产物必须**在本机（无 GPU）可加载**：不得以在 CUDA 上序列化的形态交付；本机以**可定位错误码**拒绝不可加载的产物，不抛未归类异常、不静默降级为仅收档。
- 外部运行的**来源如实记录**：区分"在产方处训练"与"在本机校验"，可回溯产方声明的运行标识；**不冒充**本机产生的运行。
- **校验必须可由任一席位在任一台机器上执行**（不绑定产方机器、不依赖某个人本机的既存产物），以适配多人协作。
- 修复 `environment()` 在声明依赖未安装时崩溃的问题，并**登记一个 `requires` 非空的方法**，实测"环境声明 → 子集校验 → 无 GPU 加载"这条路径。
- 补**不需要 GPU** 的回归：以替身估计器与模拟外部产物跑通校验及其失败分支。

**本轮已确认边界**：只做"经仓库交付的校验路径 + 环境语义拆分 + 本机可加载契约 + 来源如实记录 + 无 GPU 回归"。**不引入深度学习框架**、不训练任何模型、不做真实设备映射适配层、不新建投递协议、不做签名，不做 SHAP、不替换服务所用的运行、不改 `GET /api/review-batch` 响应契约、不改前端与 `docs/api/openapi.yaml`、不重写既有运行或已冻结证据。

**后续范围**：真实 GPU 产物接入（含产方框架与版本、独立复现协议落地）、CI/CD 中加校验步骤、深度方法覆盖补齐、运行索引、Popt／IFA、SHAP 解释，均由后续 change 承担。

## Capabilities

### New Capabilities

（无。运行记录、环境声明与复现口径的家本来就在 `public-data-baseline`——其 PDB-07 与 PDB-11 正是"运行可追踪与复现"与"依赖按运行声明校验"；另立同类能力会把同一族要求拆到两处，因此本次以修订与新增要求的方式扩展该能力，与上一 change 处理方法契约的做法一致。）

### Modified Capabilities

- `public-data-baseline`: **修订 PDB-11**（环境校验按运行来源区分：产方训练环境为溯源，仅本机运行按原包含关系校验）；**新增 PDB-15～PDB-19**——外部产物的校验（完整性、结构、自洽，不重训；且任一席位与机器得一致判定）、环境声明双语义拆分、交付产物的本机可加载契约与可定位拒绝、按声明口径重算、外部来源如实记录。既有 PDB-01～PDB-10、PDB-12～PDB-14 的语义不变。

## Impact

- **后端代码**：`backend/jit_baseline/artifacts.py`（环境语义、外部运行按来源分派与可加载校验）、`algorithms.py`（登记一个 `requires` 非空的方法）、`cli.py`（复用既有命令，不新增）；`model.py`、`metrics.py` 的既有定义不变。`compare_runs` 的口径分派需处理"对非数值容差直接拒绝"这一边界。
- **仓库与协作流程**：`.gitignore`（外部产物的受控例外）、`docs/团队分工.md` 的交付与校验分工、PR 评审中产方（GPU 席位）与校验方（本席位）的角色。
- **数据与产物**：外部产物目录纳入版本控制，与既有本机运行目录并列；**不重写** `artifacts/baseline`、`artifacts/reproduction`、`artifacts/decision-tree-*`，**不修改** `docs/evidence/` 下已冻结证据。
- **不修改**：`backend/jit_baseline/api.py`、`docs/api/openapi.yaml`、`frontend/**`。
- **依赖**：不引入新依赖（本 change 以 CPU 可加载的替身／经典方法实测契约；真实框架由 GPU change 引入）。
- **测试**：新增无需 GPU 的校验回归（含"不可加载被可定位拒绝""声明依赖未安装不再是崩溃""任一机器一致判定"三条失败／边界分支）；测试输出仍只写运行工作区 `docs/evidence/_run/`。
- **文档**：`backend/PROTOCOL.md`、`backend/README.md`、`docs/团队分工.md`、`docs/缺陷记录.md`。
- **不影响**：`GET /api/review-batch` 的响应契约与前端行为。
