## Context

当前后端收集到 908 项测试、前端有 401 项 Vitest 测试和 15 个浏览器用例，但纯函数、临时 SQLite、真实模型训练、HTTP 和 React 组件测试混在同一测试入口。现有 `unit-results.json` 只保存运行器原始输出；仓库没有覆盖率和测试配置可生成覆盖率，没有 AI 来源标记和提示词目录。现有持续回归负责在 PR 上执行关键检查，现有证据机制只负责冻结内容而不定义单元测试质量。

本设计只生成 Sprint2 单元测试交付包，不把单元测试质量规则长期加入 PR 门禁。

## Goals / Non-Goals

**Goals:**

- 定义一个可审核的核心函数清单，证明每个函数具备正常、边界、异常场景。
- 建立独立于组件、集成和端到端测试的快速单元测试入口。
- 生成后端和前端覆盖率、测试来源统计、提示词归档、机器清单和正式 Markdown 报告。
- 让最终材料可从当前提交重复生成，并通过现有证据冻结机制封存。

**Non-Goals:**

- 不要求全部 908 项后端测试或 401 项前端测试进入一分钟单元套件。
- 不改变产品 API、模型训练、模型发布或运行服务。
- 不新增 PR 覆盖率门禁、分支保护或长期报告发布任务。
- 不把组件交互、临时数据库、真实模型和浏览器旅程伪装成纯单元测试。

## Decisions

### 使用显式核心测试清单

建立机器可读清单，登记核心函数、所属端、用例标识、场景类别、测试文件和来源。审核脚本以清单为准检查每项是否具有三类场景，未进入清单的测试不参与 Sprint2 单元完成度。

替代方案是仅按目录命名区分测试，但同名目录仍可包含集成测试，无法证明核心函数三场景完整。

### 建立独立快速单元测试入口

后端使用明确的单元标记或固定清单，前端使用独立的纯函数测试包含规则。门禁只运行登记的成员，真实模型训练、临时 SQLite、HTTP、React 交互和浏览器旅程继续在现有完整回归中执行。

替代方案是把现有完整测试压缩到一分钟，会删除或弱化有价值的测试，不符合保留证据的目标。

### 覆盖率按核心范围统计

后端和前端分别生成行、分支覆盖率，统计范围由核心测试清单和被测模块集合共同确定。行覆盖率低于 80% 时交付失败；分支覆盖率低于 70% 时报告缺口但不以行覆盖率替代。HTML 报告用于下钻，PDF 或截图用于 Sprint2 展示。

替代方案是统计整个仓库覆盖率；大量页面、迁移和维护工具会稀释核心逻辑，也不能回答课程要求的核心函数覆盖情况。

### AI 来源采用双层记录

每条用例记录来源类别，每个测试文件汇总数量与比例；核心断言人工审核记录和 AI 提示词另行归档。提示词文件按被测模块组织，并记录所用工具、采用范围和人工修改说明。

替代方案是只在报告汇总比例；这会失去从报告回到具体用例和提示词的能力。

### 报告由运行结果生成

单元运行产生原始结果，再由报告脚本计算三场景完整性、通过/失败/跳过、耗时、覆盖率、来源比例和配置身份。Markdown、机器清单和覆盖率截图共同冻结，任何一项与提交或测试配置不一致即标为陈旧。

替代方案是人工手填报告；测试变更后容易产生无法核验的数字漂移。

## Risks / Trade-offs

[为覆盖率而加入低价值测试] → 只统计声明的核心范围，并要求断言针对业务结果，不把行命中当作用例质量。

[样本清单漏掉真正的核心函数] → 在报告中列出选择规则、负责文件和排除项，由人工复核确认清单。

[60 秒限制导致环境波动] → 仅统计已安装锁定依赖后的测试进程，排除依赖安装；使用固定成员和单进程稳定配置，并保留实际耗时。

[AI 来源无法从代码完全推断] → 以文件和用例显式标记、提示词及人工审核记录为事实来源，不根据代码风格猜测。

[一次性报告随后失效] → 报告绑定提交、测试配置和成员清单；Sprint2 修改测试后必须重新生成并重新冻结。
