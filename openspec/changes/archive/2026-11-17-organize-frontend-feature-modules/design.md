# Design

## Context

见 proposal.md。前项负责官方基础组件统一，本项以其已完成结果为前提。现有路由集中在 App 与 navigation，数据请求使用共享 fetch 和部分 TanStack Query；项目、PR、个人资源及管理页面与契约、客户端和状态文件分散。现有测试通过文件相邻导入与源码路径检查约束部分行为和样式。

## Goals / Non-Goals

**Goals:** 从目录即可定位一个业务的页面、请求和测试；布局、基础组件、跨业务工具的依赖方向明确，过大的项目与 PR 页面以编排为主。

**Non-Goals:** 路由格式、后端 API、缓存语义、模型身份、会话、草稿格式和存储键的变化；为了移动文件增加兼容转发层或无实际用途的抽象。此项不改变外部行为，按 schema 声明 `skip_specs: true`。

## Decisions

1. **按业务聚合。** `features/projects`、`reviews`、`datasets`、`training`、`models`、`account`、`admin` 与 `research` 保存各自页面、组件、请求、状态和相邻测试。跨模块共用的 API 错误与请求基础设施留在 `lib`；纯入口、路由和全局 Provider 放在 `app`。不为每个文件强制再造 service/store 层。
2. **共享边界明确。** 官方 `components/ui` 只依赖基础工具；`components/layout` 承载布局形状，角色导航和会话由上层传入；`components/shared` 只放多个业务实际共用的组合，业务页面不进入基础组件层。图表和代码差异按实际使用边界归并，不混入官方组件目录。
3. **移动与拆分分别验证。** 首先机械迁移文件并改写所有静态、动态和测试导入，再拆项目页的结果/记录区与 PR 页的工作单展示区；每个业务文件移动后保持测试随行，保留入口别名并删除不再需要的根目录转发文件。
4. **依赖检查保持适度。** 约束基础组件不反向依赖业务，业务不重新引用退役路径，应用入口只有一处。只检查稳定边界，不用任意行数上限或目录深度代替可维护性。

## Risks / Trade-offs

- [动态导入、测试夹具或路径型检查失效] → 迁移静态与动态引用，检查全部 TypeScript、Vitest、样式守卫和 Vite 构建，保留路由拆包。
- [移动组件触发非预期状态重建] → 保留 key、Provider 作用域、账户 generation 和存储键，执行账号切换及 PR 续审回归。
- [模块之间出现循环] → 共用契约和基础设施归并到明确的共享位置，检查依赖方向，使用构建验证动态边界。

## Migration Plan

前项归档后迁移 app/布局与业务文件，再拆分页面、清理转发和更新目录文档；无数据库升级。回退采用本项之前的前端源码或构建。实际移动范围、检查和未决问题写入 `docs/审计/2026-11-16-frontend-feature-modules.md`。
