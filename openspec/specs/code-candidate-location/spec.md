# code-candidate-location Specification

## Purpose
让审查者看到与固定代码版本绑定、可复核的静态分析候选位置，并明确其与模型风险、缺陷概率和自动修复的区别。

## Requirements

### Requirement: CCL-01 候选位置与证据

系统 SHALL 为固定 PR 快照生成候选位置，每条 MUST 绑定基准或目标侧、文件路径、行号、规则标识、规则版本、消息和可复核证据。候选 MUST 来自实际执行的分析器或固定规则；分析器需要完整文件内容时，MUST 先取得该侧固定 SHA 的内容。分析器不可用、文件不支持、内容未取得或读取失败时 MUST 明确说明，MUST NOT 生成示例位置或猜测行号。

#### Scenario: 生成候选位置

- **WHEN** 对一个固定快照的已取得内容执行受支持的静态分析
- **THEN** 每条候选包含侧别、路径、行号、规则标识与版本、消息和证据，并绑定该快照

#### Scenario: 内容未取得

- **WHEN** 快照只有补丁、完整文件内容尚未取得
- **THEN** 候选状态为未分析并说明原因，不生成候选或猜测行号

#### Scenario: 分析器不可用

- **WHEN** 分析器缺失、版本不兼容或文件无法读取
- **THEN** 返回明确原因和覆盖范围，不生成候选或伪造位置

### Requirement: CCL-02 与模型风险分离

候选位置 MUST 作为独立线索展示，MUST NOT 被换算成行级缺陷概率、提交分数或 PR 整体风险；模型分数也 MUST NOT 被表述为候选位置。两者同时存在时 MUST 分别标注来源、版本和覆盖范围。

#### Scenario: 同时展示两类线索

- **WHEN** 同一 PR 既有模型提交分数又有静态候选位置
- **THEN** 页面分别显示两类线索及各自来源，不合并成单一风险值

#### Scenario: 候选位置缺少模型分数

- **WHEN** 某文件只有候选位置而没有模型分数
- **THEN** 页面保留候选位置并说明模型未覆盖，不把缺失分数当作低风险

### Requirement: CCL-03 人工确认与证据保留

审查者 SHALL 能对候选位置标记确认、驳回或暂缓，并 MUST 填写理由。状态变化 MUST 保留原候选、证据、版本和理由；系统 MUST NOT 因新提交、新分数或候选消失自动解决人工判断。

#### Scenario: 驳回候选

- **WHEN** 审查者把一条候选标记为驳回并填写理由
- **THEN** 原候选和证据保留，状态为驳回，后续轮次仍可核对

#### Scenario: 新版本不自动解决

- **WHEN** 作者推送新提交或重新分析
- **THEN** 原人工判断保持，新轮次单独记录候选变化

### Requirement: CCL-04 覆盖范围与不支持内容

系统 SHALL 记录实际分析的文件、跳过的文件、支持的语言和规则版本。二进制、生成文件、超大文件或不支持的语言 MUST 明确标记为未覆盖，MUST NOT 计为无候选或无缺陷。

#### Scenario: 部分文件未分析

- **WHEN** 快照中有二进制或不支持语言的文件
- **THEN** 覆盖说明列出未分析文件和原因，候选结果不声称覆盖全部文件

### Requirement: CCL-05 不自动修复

首版 MUST NOT 自动生成或应用修复补丁。若后续提供修复建议，MUST 单独标注为建议，MUST 在隔离环境验证并由用户明确确认后才能使用，MUST NOT 把建议表述为已修复或已通过测试。

#### Scenario: 没有修复建议

- **WHEN** 审查者打开一条候选位置
- **THEN** 页面只显示位置、证据和人工处理入口，不显示自动补丁或已修复结论

### Requirement: CCL-06 针对性修复建议

系统 SHALL 为语义明确的规则候选提供针对性修复建议，包含问题证据、建议修改位置、修改理由与必要的人工确认项。建议 MUST 因规则而异，MUST NOT 把不同规则统一替换成另一个不等价实现。系统 MUST NOT 自动修改源码、自动提交修复、自动评论 PR 或把建议表述为已修复或已通过测试；只有在语义明确且上下文充分时 MAY 提供可核对的前后示例或补丁预览。

#### Scenario: 可变默认参数建议

- **WHEN** 候选规则为可变默认参数
- **THEN** 建议说明共享状态风险并给出以 `None` 为默认、在函数体内创建可变的示例

#### Scenario: 裸 except 建议

- **WHEN** 候选规则为裸 except
- **THEN** 建议说明吞掉异常的风险并给出指明具体异常类型的示例

#### Scenario: eval/exec 建议

- **WHEN** 候选规则为 eval 或 exec
- **THEN** 建议要求核对输入来源并给出不执行字符串的替代方向，不统一替换成另一个动态执行函数

#### Scenario: 不自动修复

- **WHEN** 用户查看修复建议
- **THEN** 源码、工作单结论和远端 PR 保持不变，应用修改需要用户自行确认

### Requirement: CCL-07 建议加入问题草稿

审查者 SHALL 能把一条候选及其建议加入既有问题或结论草稿，并复用确认、驳回、暂缓与恢复能力。草稿条目 MUST 记录候选绑定的快照、侧别、路径、行号、规则版本和建议摘要；重复分析 MUST NOT 重复堆叠同一候选，MUST 保留已有的人工判断。

#### Scenario: 加入草稿

- **WHEN** 审查者把候选建议加入问题草稿
- **THEN** 草稿条目记录候选身份与建议摘要，可继续编辑、确认、驳回、暂缓或恢复

#### Scenario: 重复分析

- **WHEN** 对同一快照重复执行候选分析
- **THEN** 相同候选不重复生成草稿条目，已有判断保持不变

#### Scenario: 快照更新

- **WHEN** PR 快照更新后原候选不再出现
- **THEN** 原草稿条目与其行号保持原快照引用，不静默迁移到新行

### Requirement: CCL-PRV 只读预览直接分析候选

PR 只读预览 SHALL 允许对当前快照的受支持文件直接执行静态候选分析并展示候选、证据、建议与覆盖原因，不需要先创建个人工作单。候选结果 MUST 仍属共享分析事实，MUST NOT 混入个人判断。

#### Scenario: Python 文件候选
- **WHEN** 用户在只读预览中对 Python 文件点击“分析代码候选”
- **THEN** 显示候选位置、规则、证据和修复建议，不创建个人草稿

#### Scenario: 不支持语言
- **WHEN** 对 Rust、TypeScript 等未支持文件执行候选分析
- **THEN** 明确显示未覆盖及原因，不显示示例位置

### Requirement: CCL-AUTO 首次加入问题创建工作单

用户在只读预览中把候选加入问题草稿时，系统 SHALL 自动创建当前固定快照的个人工作单并保存该问题；已有工作单 MUST 直接复用，不得丢失先前判断。确认、驳回与暂缓仍在工作单中完成。

#### Scenario: 首次加入问题
- **WHEN** 用户在没有工作单时把候选加入问题草稿
- **THEN** 自动创建工作单并保存问题，不要求先点“创建审查工作单”

#### Scenario: 已有工作单
- **WHEN** 用户已有当前快照的工作单
- **THEN** 直接写入该工作单，旧判断保留

### Requirement: CCL-COMPLETE 完整候选总体上的定位指标

代码候选定位 SHALL 在事先声明的完整候选总体上评价，并与抽样研究结果分开报告。指标 MUST 表述为弱标签上的排名评价，未获人工复核前 MUST NOT 声称真实缺陷检出率；并列、预算取整与无正例提交的处理 MUST 明确记录。

#### Scenario: 查看完整候选定位结果

- **WHEN** 用户查看一轮完整候选评价
- **THEN** 报告候选规模、正例覆盖、排除数、IFA 与预算召回，并标明标签为弱标签

#### Scenario: 无正例提交

- **WHEN** 某个提交的候选组不含正例
- **THEN** 该组数量与处理方式单独报告，不删除或补造正例
